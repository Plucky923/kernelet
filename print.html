Building Kernelets on Linux

How to read this book

Building Kernelets on Linux explains the design and implementation of the kernelet: a complete OS kernel that runs inside another kernel, and does so safely.

The book has two parts:

  • Accepted Design describes the design the project currently endorses, its implementation in prototype/, and its limitations. These chapters build up the working system step by step.
  • Design Proposals is the place to develop and review optimizations, alternative designs, and new material. A proposal is an idea under discussion, not a promise about the accepted design or the prototype’s behavior. Anyone can contribute a proposal, including the book’s author.

An accepted proposal is incorporated into Accepted Design and, where applicable, the prototype. Declined or withdrawn proposals remain available with the reasons for the decision, so future contributors can learn from the discussion. Acceptance is what separates the two parts; authorship does not.

Start with Accepted Design to understand the system. To suggest a change, read Contributing a design proposal and use the proposal template. Each proposal’s title and filename begin with its original submission date, such as 2026-10-27 Improve syscall performance and 2026-10-27-improve-syscall-performance.md.

The companion prototype patches and extends Linux. With those changes small Rust kernels written against OSTD, the framework at the bottom of the Rust kernel Asterinas, can run inside Linux, scheduled and stopped by Linux without Linux’s own code needing to understand the kernel it runs.

By the end you will know how every part of that prototype works, down to the C and Rust that do it. You will also have run it; the prototype’s README says how.

Who this is for

The book assumes three things: what one operating-systems course teaches, the ability to read C, and a fair command of Rust. From the course you know what a process is, what virtual memory and a page table are, what a system call does, and what an interrupt and a context switch are, in the abstract.

It assumes nothing about the Linux source. Background knowledge beyond the course, whether about Linux, ELF, compiler behavior or processor details, is explained the first time it is needed in a background box. Each box begins with a subject and a topic, such as Linux: control groups or ELF: relocations. It explains the concept, the names used for it in the relevant code or format, and why it matters to the kernelet design.

Linux: control groups. A control group is a set of tasks that Linux accounts and limits together. The prototype puts a sandbox’s carrier tasks in one group so that Linux can account for their resource use together.

If you already know a box’s topic, you can continue with the main text. The same box style is used for every subject; the label tells you which background knowledge it introduces.

Why a kernel of your own

A cloud provider, the operator of its machines, must keep its customers, called tenants, from reading or corrupting each other’s data, or starving each other of the machine. The business is profitable only because one physical computer runs programs from many tenants. Tenants do not trust each other, and the operator trusts none of them.

There are two established ways to keep them apart. This chapter introduces a third.

Two ways to share a machine

A virtual machine separates tenants strongly, at the price of a second layer of everything. It gives each tenant a whole simulated computer, in which the tenant installs a kernel and runs programs on that kernel. A layer underneath, the hypervisor, shares the real machine among the simulated ones. The separation is the hardware’s own: the processor refuses to let a guest touch anything outside its simulated machine. The second layer is a second kernel per tenant, a second translation of every memory address (once through the guest’s page table, once through the hypervisor’s), and a trap into the hypervisor whenever a guest touches a device the hypervisor simulates.

A container costs almost nothing, but separates tenants only as deeply as the shared kernel is correct. It gives each tenant a slice of one kernel; what separates tenants is bookkeeping inside it, which hides one tenant’s processes and files from another’s. There is one kernel and one translation of every address, which is why it is cheap. But every tenant can call nearly every system call of the shared kernel, in practice Linux, which is built from tens of millions of lines of C, and a bug anywhere in that surface is a hole between tenants.

A kernel inside the kernel

The third panel is the kernelet: a tenant’s own kernel, loaded into the kernel that runs the machine, the host kernel, and run there in kernel mode beside the host’s own code. Each tenant gets a kernel of its own, as with a virtual machine, but with no hypervisor and no simulated hardware: a kernelet is an ordinary piece of code that the host loads into its own memory.

A component of the host kernel, the endovisor, creates, serves and destroys kernelets, as a hypervisor does its guests, but from inside the host rather than beneath it.

A kernel of its own means one that no other tenant shares, not one the tenant wrote. The operator, not the tenant, compiles every kernelet. Code in kernel mode can do anything: read any memory, write any page table, halt the machine. Loading a binary a tenant supplied would hand the tenant the whole computer. So the operator builds each kernelet from source, with a compiler the operator trusts, and offers tenants a choice among those kernels.

A kernelet must keep even its own bugs inside its tenant. Compiling the kernelet does not make it correct, and the tenant’s programs are hostile. A kernelet has two layers, described in the next section: a large one, the kernel proper, which implements the system calls the tenant’s programs make and certainly has bugs, and a small one underneath it. What has to hold is that even a kernel proper that a tenant’s program has taken over through such a bug cannot touch anything outside its own tenant: a bug in a kernelet should hurt only the tenant it serves. The next two sections show why the way a kernelet’s source is written makes that true.

A kernel in two layers

A kernelet’s source is written the way Asterinas is: as a framekernel, split into two layers with a hard rule between them. Asterinas is a Rust kernel that aims to run the programs Linux runs.

  • OSTD, the framework, is the small part of the kernel that may use Rust’s unsafe. It wraps the machine (page tables, tasks, interrupts, entry to user mode) in an interface that cannot be misused to corrupt memory.
  • The kernel proper is everything else: system calls, file systems, the network stack, process and memory management. It is written entirely in safe Rust against OSTD’s interface, in every one of its crates.

So the kernel proper can reach the machine only through OSTD’s interface. It cannot read through a forged address, because safe Rust cannot dereference one. It cannot execute a privileged instruction, because that takes inline assembly, which is unsafe. It can change a page table only by asking OSTD, which checks every request before carrying it out.

The libraries the kernel proper uses must not give it a way around OSTD either. Every crate from outside the kernel proper must offer no safe function that does what only unsafe code should, such as running a privileged instruction or handing the hardware an unchecked physical address. Rust’s core, alloc and compiler_builtins are the exception: they contain unsafe code that every Rust program trusts.

Asterinas’s own kernel proper does not yet keep that rule in every crate it links. Its default build pulls in a confidential-computing crate whose safe functions hand the hardware an unchecked physical address, which Asterinas’s own source marks as a fault to fix, and a processor-support crate whose safe functions run privileged instructions. A kernelet build must leave both out.

This book’s kernels link nothing beyond core, alloc, compiler_builtins, one small helper crate shared with OSTD, and vOSTD.

The kernel proper’s confinement to OSTD’s interface rests on a property of OSTD called soundness: no safe Rust code written against its interface can break memory safety, whatever that code does. Soundness is the foundation of kernelets, as the next section shows.

OSTD’s soundness is argued, not proved. Its authors lay out the argument in a written soundness analysis and rely on review; research on Asterinas adds fuzzing, model checking and a verified memory-management design.

The same kernel, a different framework

Now give the kernel proper a different OSTD, one that confines every request it passes to the host to one tenant’s resources. It keeps the same interface, so the kernel proper needs no change at all. Underneath, most operations that would touch hardware become requests to the host, and the few that are harmless to it, such as reading the cycle counter, the framework still does itself. The book calls that framework vOSTD, virtual OSTD, as a virtual machine is a virtual computer. The kernel proper is linked with vOSTD into one image, which is what runs as a kernelet.

Whether a kernelet can corrupt the host, and through it another tenant, then comes down to four things being right: vOSTD, which is new code that uses unsafe as OSTD does; the unsafe code inside core, alloc and the library crates; the compiler; and the host’s handling of each request. OSTD’s soundness analysis does not carry over to vOSTD, so the chapters that build vOSTD argue its soundness piece by piece.

That covers corruption, and reads the program asks for. Side channels, by which code learns what it may not read through timing or speculative execution, are not stopped by the language; this book treats them as out of scope.

A kernelet reaches the host in only a few fixed ways, because its boundary is the language, not a hardware mode. What the kernel proper can call or refer to is only what is linked into its image: its own crates; Rust’s core, alloc and compiler_builtins; the library crates it depends on; and vOSTD. The image calls no symbol of the host’s. What vOSTD can ask of the host is a fixed list of functions, the service table, that it is handed when it starts. Besides those calls, vOSTD touches the host’s memory only where the host hands it a place: the arguments it is started with; the memory its services hand it; a few words of the host’s own; one shared record per virtual CPU (one of the fixed number of processors a kernelet is given) and per tenant address space; the tenant’s page tables, which the host keeps; and the host’s direct map, its mapping of all physical memory, through which vOSTD reaches the tenant’s pages and must reach nothing else. The chapter on the kernelet ABI lists them.

The language confines what a kernelet can touch, not how long it holds a processor. Keeping a kernelet from starving its neighbors is the host’s job: the endovisor’s per-processor timer takes a processor back even from kernelet code running in kernel mode. The kernel proper can hold that off only through vOSTD’s guards, which the timer overrides after about two ticks. The chapters on virtual interrupts and on sharing a processor show how.

What the book builds

Any kernel that implements the service table and hands over those places could host kernelets; in this book the host is Linux. Hosting kernelets costs it a small patch, two configuration settings, and the endovisor as one kernel module. The operator rebuilds Linux 6.12 for x86-64 with the patch’s option on and with vsyscall emulation off, which would otherwise let a tenant have Linux run a system call the endovisor never sees; runs it with four-level page tables and without indirect branch tracking, since the image carries no branch-target markers; and loads the module.

The book runs five small teaching kernels as kernelets inside that Linux. Through them it exercises the hardest parts of OSTD’s interface with the real Linux mechanisms. The first is a teaching example from the Asterinas project, run with its source unchanged: a kernel of about a hundred lines of safe Rust that runs one user program and serves its two system calls, write and exit. The other four, written for the prototype, exercise what the hundred lines do not reach: a scheduler of the kernelet’s own, the host taking a processor back from kernel code, exceptions and being stopped, and a tenant address space under load. A sixth kernel tests the PIE image format by running concurrent instances with shared code and private state.

The prototype gives each sandbox a fixed grant of 2 or 4 MiB of physical memory and has no devices. Its PIE image format lets sandboxes of the same kind run concurrently, sharing physical code pages through separate virtual mappings while keeping their writable data private. The tests exercise this separation; they do not constitute a proof of isolation against every possible kernel bug.

Its kernels and vOSTD are smaller than Asterinas’s. Its vOSTD offers the part of OSTD’s interface that its kernels use, plus a small instrumentation module, outside OSTD’s interface, that one test kernel uses to read counters and to slow one service down. None of its kernels is Asterinas’s full, Linux-compatible kernel proper, which has not yet run as a kernelet.

Recap. A kernelet is a tenant’s own kernel: a kernel proper in safe Rust, compiled by the operator, over a framework, vOSTD, that offers the same interface as the real framework but confines every request to the tenant’s own resources. A bug in it should hurt only the tenant it serves. The endovisor UAPI

The endovisor’s user-space interface, its UAPI, is one header, prototype/linux/endovisor/uapi/endovisor.h: one device node, three kinds of file descriptor, and one rule about who creates the tasks. Linux calls the set of system calls, device nodes and file formats that user space may use its UAPI, the user-space application programming interface, and keeps the headers that define it in a directory of that name. Everything the rest of the book builds is behind this interface, and nothing a tenant does ever touches it.

This chapter first shows the interface in use, by the prototype’s own holder program, then says why it has the shape it has, and then specifies every operation.

A prototype kernelet runtime

The program that drives a kernelet sandbox is its holder: the one process of the kernelet runtime that creates the sandbox, keeps its descriptor open for as long as the sandbox lives, and closes it to release the sandbox. A container runtime has such a process per container; the prototype’s is holder.c, a static C program of two commands, register and run, around the client functions of sandbox.c, which the prototype’s test drivers share. The prototype’s tests run through the interface: the holder registers each kernel’s image and runs the sandbox, and a self-test run before the hello kernel boots exercises every operation.

Linux: device nodes, ioctl and anonymous files. A device node is a file under /dev that stands for a driver rather than for data; opening it gives a descriptor on which the driver answers read, write and, for everything that is neither, ioctl: one system call that takes a descriptor, a command number and an argument, and hands both to whatever code is behind the descriptor. A driver’s interface is therefore a list of command numbers, and a module may define its own.

A descriptor need not come from a file system at all: a module can make an anonymous file, with operations of its choosing, and hand out a descriptor on it. The sandbox descriptor below is one of those; the exec descriptor is a third sort, a descriptor on a file that exists only in memory.

The operator’s step. Once per boot, someone with the right to load kernel code registers each kernelet image the machine will run, one file holding a compiled kernelet (its format is given with KLET_KIND_REGISTER below), and names it:

Simplified from prototype/host/runtime/sandbox.c: open_system, register_kind.

int open_system(void)
{
	int sys_fd = open("/dev/endovisor", O_RDWR | O_CLOEXEC);

	if (ioctl(sys_fd, KLET_GET_API_VERSION) != KLET_API_VERSION)
		exit(127);                                  /* an interface this program does not know */
	return sys_fd;
}

int register_kind(int sys_fd, const char *name, const char *image_path)
{
	struct klet_kind_register reg = { .image_fd = open(image_path, O_RDONLY | O_CLOEXEC) };

	snprintf(reg.name, sizeof(reg.name), "%s", name);  /* the name KLET_KIND_LIST reports; unique */
	return ioctl(sys_fd, KLET_KIND_REGISTER, &reg);    /* the kind's identifier */
}

A registered image is a kind, and a kind is what sandboxes are made of. Registering it is the privileged act, and it happens once; creating sandboxes of it is not privileged and happens as often as the runtime likes.

Linux: control groups. A control group is a set of tasks that Linux accounts and limits together: their share of the processors, their memory, and more. Groups form one tree, the unified hierarchy of cgroup v2, which this book means throughout. A process joins a group when its identifier is written into the group’s cgroup.procs file, and a child starts in its parent’s group. Containers are built on them, and so is a sandbox: because every task of the sandbox is in the sandbox’s group, the processor time the kernelet burns and the memory Linux allocates for it are charged to the tenant by machinery Linux already has.

The holder’s step. To run a sandbox, the holder creates it, gives it its console and log, and then makes one carrier per virtual CPU:

Simplified from prototype/host/runtime/sandbox.c: run_sandbox, wait_sandbox.

int run_sandbox(int sys_fd, const char *name, unsigned int nr_vcpus, const char *cmdline,
		const struct sandbox_opts *opt)
{
	struct klet_create create = {
		.kind = find_kind(sys_fd, name),               /* KLET_KIND_LIST, matched by name */
		.nr_vcpus = nr_vcpus,
		.memory_initial = opt->memory_initial,        /* 4 MiB unless asked otherwise */
		.memory_max = opt->memory_max,
		.max_tasks = opt->max_tasks,
		.cmdline = (__u64)(unsigned long)cmdline,
		.cmdline_len = strlen(cmdline),
	};
	struct sandbox sb = { .sys_fd = sys_fd, .nr_vcpus = nr_vcpus };
	int out = 1, err = 2;

	if (opt->cgroup)
		join_cgroup(opt->cgroup);                   /* before the create: this group becomes the sandbox's */
	sb.fd = ioctl(sys_fd, KLET_CREATE, &create);        /* the sandbox descriptor */
	ioctl(sb.fd, KLET_SET_CONSOLE, &out);               /* the sandbox's console: our standard output, or a file */
	ioctl(sb.fd, KLET_SET_LOG, &err);                   /* its kernel log: our standard error, or a file */
	/* a disk would be attached here: KLET_ATTACH_DEVICE with its open file */

	for (i = 0; i < nr_vcpus; i++) {
		int exec_fd = ioctl(sb.fd, KLET_GET_VCPU_EXEC_FD, &i);

		sb.pids[i] = fork();
		if (sb.pids[i] == 0)
			start_carrier(exec_fd, i, opt);         /* the child; does not return */
		close(exec_fd);
	}

	wait_sandbox(sb.fd, sb.pids, nr_vcpus, &sb.ex);     // Poll, then read the exit record.
	// The helper also watches the children: a child that dies before its exec
	// never became a carrier, so the holder kills the sandbox itself if one does.
	for (i = 0; i < nr_vcpus; i++)
		waitpid(sb.pids[i], NULL, 0);               /* the carriers died by SIGKILL */
	close(sb.fd);                                  // The last close releases the exited sandbox.

	switch (sb.ex.how) {
	case KLET_END_EXITED:   return sb.ex.code;      /* the kernel proper's exit code */
	case KLET_END_PANICKED: return 128;
	default:                return 129;             /* killed */
	}
}

The loop in the middle is the heart of the interface. A carrier, chapter 1’s term for a Linux task that carries one of the sandbox’s virtual CPUs and may run the tenant’s programs, is not made by the kernel. The holder forks a child for it, the child arranges itself with ordinary system calls, and then the child executes a descriptor the sandbox handed out:

Simplified from prototype/host/runtime/sandbox.c: start_carrier, join_cgroup.

void start_carrier(int exec_fd, unsigned int vcpu, const struct sandbox_opts *opt)
{
	char *argv[] = { "carrier", NULL }, *envp[] = { NULL };

	if (opt->pin) {                                 /* virtual CPU i on processor i */
		cpu_set_t set;
		CPU_ZERO(&set);
		CPU_SET(vcpu, &set);
		sched_setaffinity(0, sizeof(set), &set);
	}
	prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0);         /* the endovisor insists on it */
	if (opt->seccomp_kill_nr >= 0)                  /* a filter bounds what the tenant may ask of its kernelet */
		install_seccomp_kill(opt->seccomp_kill_nr);
	execveat(exec_fd, "", argv, envp, AT_EMPTY_PATH);   /* the endovisor takes it from here */
	die_child("execveat");                           /* reached only if the exec failed */
}

void join_cgroup(const char *dir)                    /* write our process identifier into cgroup.procs */
{
	mkdir(dir, 0755);                                /* made if it does not exist: a runtime's job, done here */
	snprintf(path, sizeof(path), "%s/cgroup.procs", dir);
	fd = open(path, O_WRONLY | O_CLOEXEC);
	n = snprintf(pid, sizeof(pid), "%d\n", getpid());
	write(fd, pid, n);
	close(fd);
}

Between the fork and the execveat the child is an ordinary process of the holder’s user, and anything Linux lets a process set on itself can go there: the processor it is pinned to, as here; its priority or scheduling class; the user it runs as; the namespaces it is in; its resource limits; a seccomp filter, which bounds what the tenant may ask of its kernelet. All of it survives the exec, because these are properties of the task and not of the program it runs, and all of it is per carrier, so two virtual CPUs can be pinned to two processors and given two priorities.

In summary, the whole life of a sandbox is, in order:

  1. When the machine is set up, the operator registers each kind with KLET_KIND_REGISTER.
  2. The runtime makes a control group for the sandbox with the limits the operator chose, and starts the holder in it, or the holder moves itself in before it creates anything, as the prototype’s does when given a group (join_cgroup).
  3. The holder creates the sandbox with KLET_CREATE, opens the disk image and whatever else the sandbox is to have and passes each with KLET_ATTACH_DEVICE, and passes its console and log with KLET_SET_CONSOLE and KLET_SET_LOG.
  4. For each virtual CPU, the holder asks for the exec descriptor with KLET_GET_VCPU_EXEC_FD and forks a child, which arranges itself and executes the descriptor. The first of those execs loads the kind’s image as this sandbox’s instance. From now on, the carrier no longer executes the holder’s code, but the kernelet’s.
  5. The sandbox runs. Linux schedules each carrier with the processors and the class its creator gave it; the kernelet schedules its own tasks on them.
  6. The kernel proper powers off, or the holder calls KLET_KILL, or a carrier is killed. The endovisor records why, marks the kernelet dying and stops every carrier; when the last of them is gone, the sandbox has exited. The sandbox descriptor becomes readable. The holder reads the exit record, reaps the carriers, closes the sandbox descriptor to release its remaining resources, and exits; the runtime removes the group.

Why it is shaped so

The endovisor UAPI is designed with four requirements in mind:

  1. Every carrier task is created and configured by user space just like an ordinary Linux task. A carrier is a special task, since its system calls go to the kernelet and not to Linux, but it is still a task, and the host’s tools for tasks, sched_setaffinity, setpriority, sched_setattr, control groups, namespaces, resource limits, /proc, must apply to it as to any other. And only user space can apply them before the task carries a virtual CPU.
  2. Resources reach a sandbox as descriptors. A disk image, a network interface, a console and a log file are things the runtime opens itself, under its own user’s permissions, and passes down. Nothing is named by path inside the kernel, and a sandbox can reach exactly what its runtime could open. This is good for both security and flexibility.
  3. A sandbox dies whole, and dies with its runtime. Nothing a crashed runtime held keeps a sandbox alive.
  4. An image contains privileged kernel code and one copy of it should serve every sandbox of it. Loading an image is a privilege of the admin who ought to make sure that the image is obtained from a trusted origin. The process of image loading involves format validation and thus should be done once.

Learning from the KVM UAPI

Linux already has one interface that meets the first three requirements, that of KVM, Linux’s hypervisor, and it is the one to draw on. The KVM module runs virtual machines whose virtual processors are ordinary user threads: a program such as QEMU opens /dev/kvm, asks it for a descriptor that stands for a virtual machine, asks that for a descriptor per virtual processor, and runs each virtual processor from a thread of its own by calling an operation on its descriptor (KVM_CREATE_VM, KVM_CREATE_VCPU, KVM_RUN). The threads are QEMU’s: it created them, it can pin them and renice them, ps shows them, and the machine dies when QEMU does, because closing the last descriptor destroys it.

Differing from the KVM UAPI

The UAPI of the endovisor differs from that of KVM in two major aspects.

First, the endovisor has a dedicated API for image registration, whereas KVM leaves loading the guest’s kernel to user space or to the guest’s own boot loader. KVM is given guest memory and virtual CPU state; the kernel image is just bytes in that memory, and hardware virtualization confines the guest even if those bytes are hostile. A kernelet’s image, by contrast, becomes executable code inside the host kernel. Its isolation rests on safe Rust and vOSTD, so the operator must trust how the image was built; checking its format cannot establish that trust. KLET_KIND_REGISTER therefore requires the right to load kernel code, while KLET_CREATE lets an unprivileged runtime create a sandbox from an already registered kind. Separating the two also lets the endovisor validate the image once and retain one copy of its code for all sandboxes of that kind. Each sandbox maps those shared code pages at its own virtual address and gets private data pages, whose pointers are relocated for that address.

Second, the endovisor uses the execveat syscall to run a vCPU, whereas KVM does the KVM_RUN ioctl. The reason is that a carrier must start with an address space that holds nothing of the host’s, and only an exec gives it one. A carrier is to the kernelet what a processor is to an ordinary kernel: the kernelet runs its tenant’s processes on it, one at a time. Those processes run in Linux’s own user mode, on Linux’s own page tables, so at every switch the kernelet switches the carrier’s address space to the current process’s, and the carrier’s address space is always one of the tenant’s. It must therefore start holding nothing of the host’s: not the holder’s program, not its heap, not a stack with the holder’s secrets on it. The one operation in Linux that gives a process a fresh address space is execve. So the exec descriptor is not called; it is executed.

Linux: what exec keeps. A new program gets a new address space, and begin_new_exec() resets what belongs to the old one: signal handlers, timers, the descriptors marked close-on-exec, and a few registrations by which Linux would later write into user memory. It does not touch the task’s control group, its user and group identities, its namespaces (bar a time namespace chosen for its children, which it enters), its processor mask, priority, resource limits, the no-new-privileges bit or the seccomp filter; those are properties of the task, not of the program, and the two last are kept by design so that a program cannot shed them by executing another. Three things it does recompute: the task’s capabilities, of which a process that is not root keeps only those it marked ambient; whatever domain the host’s security module assigns the new program; and whether the process is dumpable, below. That is what makes the holder’s child work: everything it set on itself is still set when the endovisor sees it, and nothing it could not have had is added.

The image format and its requirements

The image passed to KLET_KIND_REGISTER contains the kernel proper and vOSTD in one file. Its format tells the endovisor how to load it; its code and data layout determine whether it can serve independent sandboxes. Those are separate concerns: a file being relocatable does not make its code position-independent, and neither property alone gives each sandbox private state.

A self-contained PIE image

The image must be a little-endian, 64-bit x86 position-independent executable, or PIE, marked ET_DYN in its ELF header. It contains the kernel proper and vOSTD, fully linked together. The build compiles position-independent code and performs the final link before registration, fixing the relative positions of code and data. The endovisor loads this image itself; it does not execute a user-space ELF interpreter or resolve symbols from Linux or other libraries.

The image contract has four requirements:

  • A fixed relative layout. The ELF program headers describe page-aligned loadable segments, PT_LOAD, with separate executable, read-only and writable regions. Each sandbox maps the same layout at its own base address. No segment may be both writable and executable, and segments must not overlap.
  • Shared pages need no runtime patches. The linker resolves references within the shared code and read-only data. Runtime relocations may modify only private writable data, including pointer tables. Data containing instance-dependent pointers belongs in that private region even if an ordinary executable might make it read-only after relocation.
  • Only relative runtime relocations. Each relocation is an x86-64 R_X86_64_RELATIVE record with an explicit addend. It writes the sandbox’s load base plus the addend into a private 64-bit field. Its symbol index must be zero, its destination must lie wholly within writable image data, and its resulting pointer must refer to the image. There is no external symbol lookup.
  • An explicit entry table. By this image ABI’s convention, ELF’s e_entry identifies kernelet_entry_table, a data object rather than an instruction to execute. After relocation, its function pointers must point into that sandbox’s executable segment, and its ABI version must match the endovisor’s. The table is described in the kernelet ABI.

The prototype rejects images requiring an ELF interpreter, external libraries, TLS, or automatic constructor and destructor execution. It also rejects unsupported dynamic relocation formats and relocations into shared pages. Common symbols must have been assigned storage by the final linker. TLS and automatic initialization are implementation restrictions rather than requirements of kernelet isolation: initialization currently runs explicitly during sandbox boot, and registration runs no image code.

At registration, the loader in prototype/linux/endovisor/image.c validates the image and retains its shared pages and pristine data template. When a sandbox starts, it creates a mapping at the segment offsets specified by the linker, using the kind’s physical pages for code and read-only data and fresh physical pages for writable data. It copies the data template, zeroes uninitialized storage, applies the private relocations and sets the mapping’s permissions. The kind’s shared pages stay alive until every sandbox of that kind has been destroyed and the kind is unregistered.

These checks establish compatibility with the image contract. They do not establish that arbitrary machine code obeys the safe-Rust and vOSTD boundary. That still depends on the trusted build, which is why registering an image requires the right to load kernel code.

ELF: relocations. ELF, the Executable and Linkable Format, records how code and data refer to addresses that may not yet be known. A relocation is an instruction to a linker or loader to patch a field. A call between two sections, a reference to a global variable, or a function pointer stored in a table may need such a patch. Build-time relocations and runtime relocations do different work: the final linker can resolve distances within the image, while the loader must still fill in absolute pointers that depend on the chosen load address.

Let S be a symbol’s address, P the address of the field being patched, A an explicit addend, and B the image’s load base. Some relevant x86-64 relocation calculations are:

RelocationValue writtenRole in this image format
R_X86_64_PC32S + A - P, signed 32 bitsResolved by the build-time linker for references within the image
R_X86_64_64S + A, 64 bitsAn absolute reference the linker must resolve or convert into a supported runtime relocation
R_X86_64_RELATIVEB + A, 64 bitsThe only runtime relocation the endovisor accepts; it patches private data

The name RELATIVE here means relative to the load base, not relative to the instruction pointer. It produces an absolute pointer, so its result differs between sandbox mappings. It is suitable for private pointer tables, not shared code pages. Instruction-relative references such as PC32 instead encode distances: when the target and the field being patched move by the same amount, their distance stays unchanged.

Requirements for sharing code across sandboxes

The endovisor maps the same physical code pages at a different kernel virtual address for each sandbox, with private data at the offsets established by the final linker. This requires instruction bytes that work at every mapping, without patches that differ between sandboxes: position-independent code, or PIC.

ELF: PIC. Position-independent code can execute at different load addresses without changing its instruction bytes to suit each address. On x86-64, one technique is to address code or data relative to the instruction pointer, RIP. When the instruction and its target move by the same amount, the encoded displacement remains valid. The same instructions can therefore reach a different instance’s private data when that data has the same position relative to its code mapping. Position independence does not itself allocate or separate those instances’ data.

A global offset table, or GOT, provides indirection for addresses that cannot be reached using a fixed displacement alone. Instead of embedding the target’s absolute address in an instruction, the code reads it from a table entry. On x86-64, the code can reach that entry relative to RIP; the loader fills the entry with the target’s address. The instruction bytes can stay shared while the table entries differ between instances, provided each code mapping reaches its own table. Entries that depend on an instance must be private, even if the table becomes read-only after loading. A GOT is one technique used by PIC, not a requirement for every reference: references within an image can often use relative addressing directly.

PIC can still need relocations during linking and when initializing private data. It is a property of the generated code, separate from the ELF file type: an ET_REL object can contain PIC. A position-independent executable, PIE, is a linked executable that can run at different load addresses. It is another possible way to package the code, rather than an additional requirement for sharing.

The precise sharing rule is that every relocation applied to a physically shared page must produce identical bytes for every mapping. An absolute relocation whose value depends on the sandbox’s load address violates that rule. Absolute relocations can still appear in private data, such as a table of pointers to that sandbox’s code mapping, or in shared pages when the resulting value is identical for all instances. Relative relocations remain identical only when the referenced target stays at the same distance from the field being patched. Merely banning the absolute relocation types from the whole image would therefore be both too restrictive for private data and insufficient to guarantee sharing.

The PIE format makes those relative positions part of the image. The endovisor preserves them when mapping each sandbox and puts every runtime relocation in private pages. Consequently, concurrent sandboxes of the same kind can execute the same physical code while changing their globals and pointer tables independently. Their carrier entry points, interrupt upcalls and executable-address checks all use the individual sandbox’s mapping.

A sandbox’s mapping remains valid throughout its carriers’ execution. Destroying that sandbox releases its mapping and private pages; it does not release shared pages still owned by the registered kind. The shared pages can be released only after all sandboxes are destroyed and the kind is unregistered.

Duplicated or inherited copies keep the descriptor alive until they too are closed. This ties cleanup to the holder’s lifetime, including when it crashes.

Reading and polling the sandbox descriptor

After a termination request, the sandbox exits when every carrier is gone; if it has no carriers, it exits immediately. Reading the sandbox descriptor then returns a struct klet_exit describing the outcome. Before exit, read waits interruptibly; with O_NONBLOCK set, it fails with EAGAIN instead. A zero-length read returns zero immediately. A nonzero buffer smaller than the record fails with EINVAL; a buffer large enough receives exactly sizeof(struct klet_exit) bytes.

The record is a persistent result, not a stream: reads do not consume it or advance to an end-of-file condition. The descriptor is not seekable; lseek fails with ESPIPE. Each successful read returns the same complete record. The descriptor becomes readable to poll, select and epoll after exit and stays readable. A runtime can therefore wait for the sandbox alongside its carriers’ process descriptors, then read its final result. KLET_GET_STATS also includes this record once its reported state is KLET_STATE_EXITED.

// After a termination request, the sandbox exits when every carrier is gone;
// if it has no carriers, it exits immediately.
// A blocking `read` waits interruptibly for that state;
// with `O_NONBLOCK`, it fails with `EAGAIN` until the sandbox has exited.
// A caught signal can interrupt the wait with `EINTR`.
//
// A read buffer must hold at least one `struct klet_exit` (`EINVAL` otherwise).
// A successful read copies one complete record and returns its size in bytes.
// A zero-length read returns zero immediately.
// An invalid destination fails with `EFAULT`.
// Reads do not consume the record: repeated reads return the same result.
// The descriptor is not seekable (`ESPIPE` from `lseek`).
//
// `poll`, `select`, and `epoll` report readability once the sandbox has exited.
// `poll` reports `POLLIN | POLLRDNORM`; readiness persists after a read.
// After readiness notification, either `read` or `KLET_GET_STATS` retrieves the exit record.
// `how` identifies which of three things ended the sandbox:
//
// - `KLET_END_EXITED`: `code` is the kernel proper's exit code.
// - `KLET_END_PANICKED`: `message` is the panic message.
// - `KLET_END_KILLED`: `reason` is the caller's reason from `KLET_KILL`,
//   `KLET_KILLED_REQUESTED` if the last copy of the sandbox descriptor closed,
//   or another `KLET_KILLED_*` reason if the endovisor killed it.
//
// `message` is empty when there is no panic message.
//
// # Prototype limitations
//
// The prototype reports a panic as `KLET_END_EXITED`, as a power-off, with no message.
// Of the endovisor's own reasons, it detects only `KLET_KILLED_CARRIER_LOST`.
enum klet_end {
	KLET_END_EXITED	= 1,		// the kernel proper powered off
	KLET_END_PANICKED	= 2,		// a panic nothing in it caught
	KLET_END_KILLED	= 3,		// the host decided
};
#define KLET_KILLED_REQUESTED	0x80000000u	// the last copy of the descriptor closed
#define KLET_KILLED_CARRIER_LOST	0x80000001u	// a carrier died: `SIGKILL`, the OOM killer
#define KLET_KILLED_FAULT		0x80000002u	// a fault in kernelet code
#define KLET_KILLED_STACK		0x80000003u	// a kernelet stack nearly exhausted
#define KLET_KILLED_HOST_COUNT	0x80000004u	// Linux's preemption count found wrong
struct klet_exit {
	__u32	how;				// `enum klet_end`
	__s32	code;
	__u32	reason;
	__u32	pad;
	char	message[KLET_MESSAGE_LEN];
};

On the exec descriptor

The exec descriptor is returned by KLET_GET_VCPU_EXEC_FD on the sandbox descriptor and identifies one virtual CPU of that sandbox. Its operation is execveat(fd, "", argv, envp, AT_EMPTY_PATH): the calling process becomes that virtual CPU’s carrier. The holder passes the descriptor to a child it has forked and configured, and the child executes it. A successful exec never returns to the holder’s code; the arguments and environment are discarded.

The descriptor grants the right to start that virtual CPU once, subject to the checks below. It refers to a file that exists only in memory, owned by root and execute-only. The endovisor recognizes the file by its identity, not its contents: copying its bytes into another file grants no right to start a virtual CPU. The descriptor is a path-only one (O_PATH), which execveat accepts but read, write and fchmod refuse. Duplicating it does not grant another start: once the virtual CPU has started, executing any copy fails with EBUSY.

Executing the descriptor. The caller must be in the sandbox’s control group and have no new privileges set, or the exec fails with EPERM. A killed sandbox refuses the exec with ESRCH. The endovisor implements these checks in a handler registered with Linux as an executable format. On success, the handler gives the process a fresh address space and empties it, including the pages holding the arguments, so that it holds only what the kernelet puts there. It marks the task as a carrier and gives it a lifeline, an open file whose closing tells the endovisor that the carrier has died. The first carrier starts the sandbox’s instance; the kernelet boots once every virtual CPU has a carrier. On the way back from the exec to user mode, the endovisor takes control and starts running kernelet code on the task.

Controlling the resulting carrier. Once the exec has succeeded, the runtime controls the virtual CPU through its Linux task. The task is named kernelet/<slot>/<i>, identifying the sandbox’s slot and the virtual CPU’s index; KLET_GET_STATS on the sandbox descriptor reports its process identifier. ps and top list the carriers, and taskset and chrt change their processor affinity and scheduling class while the sandbox runs. The host sees the holder and one child per virtual CPU in the sandbox’s control group. The tenant’s own processes are known only to the kernelet.

The exec changes two aspects of how those task interfaces work. First, the carrier is not dumpable: sharing its user identity does not permit attaching a debugger or reading its memory through /proc, which could expose the tenant’s memory. Linux normally makes a process non-dumpable when it executes a file it cannot read (begin_new_exec()), but root can read an execute-only file, and the rule also depends on fs.suid_dumpable. The handler therefore clears the dumpable bits itself, for the carrier and for every address space later made for the tenant. Root can still inspect and profile the carrier.

Second, signals control the carrier’s execution but do not deliver events to the tenant. SIGSTOP stops the virtual CPU until SIGCONT; SIGKILL to any carrier ends the whole sandbox. Other signals are discarded. The runtime can therefore stop the sandbox through kill -KILL on a carrier or cgroup.kill on its group, as well as through KLET_KILL on the sandbox descriptor.

What this book’s prototype leaves out. The interface is written for a full endovisor, and the header’s comments say where this book’s falls short of it. It has no devices, so KLET_ATTACH_DEVICE fails with EOPNOTSUPP. Its console carries output only, so the input half of KLET_SET_CONSOLE does not exist, and a sandbox given no console or log file has both printed to the host’s kernel log. Its memory is one fixed grant of 2 or 4 MiB, selected by memory_initial at creation; memory_max is recorded, but there is no mechanism to grow the grant. A panic ends the kernelet as a power-off does, with no message in the exit record, and of the endovisor’s own kill reasons it detects only a lost carrier. Each of those is named where the book reaches the place it would go.

Recap. The endovisor’s user-space interface is one device node and three kinds of descriptor. The system descriptor, from /dev/endovisor, is where an operator with the right to load kernel code registers an image file, one that can name nothing outside itself, as a kind whose code every sandbox of it shares, and where anyone with the node creates a sandbox of a kind. The sandbox descriptor is what the holder keeps: through it the holder attaches files, asks for one exec descriptor per virtual CPU, reads the exit record and closes the descriptor. Closing its last copy requests termination if needed and releases the remaining resources once the sandbox has exited. An exec descriptor is executed, not called, by a child the holder forked and configured with Linux’s ordinary system calls, because a carrier needs an address space that holds nothing of the host’s; the endovisor checks the child’s control group and its no-new-privileges bit, starts each virtual CPU once, and turns the child into its carrier. The holder’s control group is the sandbox’s, its main thread owns the tenant’s address spaces, and every task of a sandbox is one that user space made and can govern.

It makes two system calls with the syscall instruction, using Linux’s numbers, as Asterinas does: write is 1 and exit is 60.

The kernel places the program in memory rather than loading it. A real kernel reads an executable’s headers and maps each segment where they say; this kernel reads no headers. include_bytes!("../hello") embeds the assembled executable, headers and all, and the kernel copies the whole file into fresh frames and maps them from 0x400000. That works because the program is linked as a static executable at 0x400000, with its code at 0x401000, the first page after the headers, and the linker placed each segment at its file offset from that address, so the code lands at 0x401000 and the message at 0x402000. The kernel hard-codes the first two, 0x400000 and 0x401000.

main builds an address space holding the program, makes it current on this processor with activate, creates a task to run the program, and puts the task on the scheduler’s queue with run(). #[ostd::main] marks it as the function the framework calls once it has booted, and generates the entry, __ostd_main, that calls it.

The address space main activates is still active when the task runs. main runs before any task exists; the task first runs when main returns, on the same processor, and nothing in between switches address spaces.

What it asks of the machine: an entry called after boot; a heap; a notion of current address space; and a way to start a task.

Piece 2: building the address space

Simplified from prototype/kernels/hello/src/lib.rs: create_vm_space.

fn create_vm_space(program: &[u8]) -> VmSpace {
    let nbytes = program.len().align_up(PAGE_SIZE);
    let user_pages = {
        let segment = FrameAllocOptions::new()
            .alloc_segment(nbytes / PAGE_SIZE)
            .unwrap();
        segment.write_bytes(0, program).unwrap();
        segment
    };

    let vm_space = VmSpace::new();
    const MAP_ADDR: Vaddr = 0x0040_0000;
    let preempt_guard = disable_preempt();
    let mut cursor = vm_space
        .cursor_mut(&preempt_guard, &(MAP_ADDR..MAP_ADDR + nbytes))
        .unwrap();
    let map_prop = PageProperty::new_user(PageFlags::RWX, CachePolicy::Writeback);
    for frame in user_pages {
        cursor.map(frame.into(), map_prop);
    }
    drop(cursor);
    vm_space
}

Three framework ideas appear here.

Frames. The kernel holds physical memory only through handles; a physical address gives it no way to touch the frames. FrameAllocOptions::new().alloc_segment(n) allocates n physically contiguous pages of RAM and returns a Segment, a handle to them. write_bytes copies the program into them. Iterating a Segment yields its frames one by one, and .into() turns each into an untyped frame, one holding plain bytes rather than a kernel object, the only kind a user mapping may hold.

The address space. An address space, VmSpace, is edited only through a cursor over a range of virtual addresses. VmSpace::new() creates an empty one; on a machine, that is, when OSTD runs the hardware itself, that is a fresh page table. cursor_mut opens a cursor, and each map call puts one frame at the cursor’s address, with the given permissions, and advances the cursor one page. PageProperty::new_user with PageFlags::RWX makes the pages readable, writable and executable from user mode. CachePolicy::Writeback makes them ordinary cached memory.

The cursor holds the range locked while it exists, so two parts of a kernel cannot map the same page at once; dropping it releases the range.

The preemption guard. disable_preempt() returns a guard; while it lives, the framework’s scheduler will not switch this processor to another task. OSTD calls code running under such a guard atomic mode, and the cursor demands it. OSTD frees an unmapped page-table page only after every processor has passed a point where it might be switched to another task, so under the guard the pages the cursor walks stay alive, and the cursor can hold the page-table locks of the paragraph above without being switched out. No other task exists yet, but cursor_mut’s signature demands the guard regardless.

What it asks of the machine: physical frames to allocate; a page table per address space, which the kernel edits one page at a time through a cursor; and a way to switch off task preemption.

Piece 3: the task and the loop

Simplified from prototype/kernels/hello/src/lib.rs: create_user_task, create_user_context.

fn create_user_task(vm_space: Arc<VmSpace>) -> Arc<Task> {
    fn user_task() {
        let current = Task::current().unwrap();
        let mut user_mode = {
            let user_ctx = create_user_context();
            UserMode::new(user_ctx)
        };

        loop {
            let return_reason = user_mode.execute(&DummyUserHooks);
            let user_context = user_mode.context_mut();
            if ReturnReason::UserSyscall == return_reason {
                let vm_space = current.data().downcast_ref::<Arc<VmSpace>>().unwrap();
                handle_syscall(user_context, &vm_space);
            }
        }
    }

    Arc::new(TaskOptions::new(user_task).data(vm_space).build().unwrap())
}

fn create_user_context() -> UserContext {
    let mut user_ctx = UserContext::default();
    const ENTRY_POINT: Vaddr = 0x0040_1000;
    user_ctx.set_rip(ENTRY_POINT);
    user_ctx
}

A task is the framework’s unit of execution, like a thread: a function, a stack, and saved registers. TaskOptions::new(user_task) describes one that will run the function user_task; .data(vm_space) attaches the address space to it so the function can find it later; build() creates it.

Inside the function, the task finds its address space again: Task::current() is the running task, and data() returns what was attached, recovered as the Arc<VmSpace> by downcast_ref.

A UserContext is a user program’s register file. Its register part is the sixteen general registers, the instruction pointer and the flags, eighteen words; it also records which exception, if any, ended the last run.

The task sets the instruction pointer and leaves the rest zero. Left zero, the flags would run the program with interrupts off, so execute sets the interrupt flag itself. The stack pointer stays zero, which is harmless because the program never uses a stack.

The loop calls user_mode.execute(...), which enters user mode and returns each time the processor comes back into the kernel with something for the kernel to handle: a system call, or a CPU exception such as a page fault. Interrupts it handles itself; then, after giving the scheduler a chance to switch tasks, it goes back to user mode. DummyUserHooks is the empty set of hooks: it asks to be told of no other event, so execute returns for nothing else.

When execute returns, the kernel has the reason and the program’s registers. The return value says what happened. The context now holds the program’s registers as they were at that moment. The kernel reads and changes them through context_mut() before calling execute again. On an exception this loop ignores the reason and calls execute again, so a faulting program would fault forever; this one never faults.

So a user program, to this kernel, is a function call that returns now and then. The code that serves the program, user_task, lives inside a loop, on a kernel stack, and its local variables survive every trip the program makes to user mode and back. Keep that picture: Linux does not share it.

Linux: the empty kernel stack. In Linux a task’s kernel stack is empty whenever the task is in user mode. A system call builds frames on it, and returning to user mode discards them. Reconciling that with the picture above is the work of the chapters on two stacks and on the round trip into user mode.

Piece 4: the system calls

Simplified from prototype/kernels/hello/src/lib.rs: handle_syscall.

fn handle_syscall(user_context: &mut UserContext, vm_space: &VmSpace) {
    const SYS_WRITE: usize = 1;
    const SYS_EXIT: usize = 60;

    match user_context.rax() {
        SYS_WRITE => {
            let (_, buf_addr, buf_len) =
                (user_context.rdi(), user_context.rsi(), user_context.rdx());
            let buf = {
                let mut buf = vec![0u8; buf_len];
                let mut reader = vm_space.reader(buf_addr, buf_len).unwrap();
                reader
                    .read_fallible(&mut VmWriter::from(&mut buf as &mut [u8]))
                    .unwrap();
                buf
            };
            println!("{}", str::from_utf8(&buf).unwrap());
            user_context.set_rax(buf_len);
        }
        SYS_EXIT => poweroff(ExitCode::Success),
        _ => unimplemented!(),
    }
}

The handler dispatches on the system call number, which is in rax by Linux’s convention; the arguments are in rdi, rsi, rdx. write prints the program’s buffer and returns the byte count in rax; the file descriptor in rdi is ignored, since every write goes to the console. exit powers the machine off, which in a kernelet stops the sandbox, not the host.

The kernel never dereferences a user address. For write it must read buf_len bytes of the program’s memory at buf_addr, so it asks the address space for a reader over that range; reader refuses a range outside user space, and refuses an address space that is not the one active on this processor, which is why piece 1’s activate matters. read_fallible copies through the reader into a kernel buffer, wrapped as a VmWriter.

A bad buffer ends in a panic, never in a stray access. Under vOSTD an unmapped page makes read_fallible return an error rather than fault; the kernel then calls unwrap on it and panics. On a machine, OSTD turns the page fault into that error only if the kernel has registered a page-fault handler, which this one has not, so OSTD panics in its fault handler instead. A kernelet’s panic, like poweroff, ends only its sandbox.

What it asks of the machine: a safe way to copy from a user address, which may be bad; a console; and power-off.

The kernelet ABI

The previous chapter was the view from above the framework: a kernel that allocates frames, maps pages and enters user mode. This chapter is the view from below: what is in the image file that the holder registered, and how the code in it talks to the host. Nothing in it runs yet; it is the shape that the next chapters fill in.

A kernelet image is two layers of code compiled into one file, held together by a third thing, an interface.

  1. The kernel proper, the hundred-line kernel of the last chapter: safe Rust, never edited.
  2. vOSTD, a Rust crate whose library name is ostd, so that the kernel proper’s use ostd::... lines resolve to it. It offers every type and function the kernel proper uses, with the same names and signatures as the real OSTD. It is in prototype/vostd/.
  3. The image ABI (an application binary interface is the exact layout of what two separately compiled pieces of code pass each other), a few C-layout structures that both vOSTD and the endovisor know: what the host tells the kernelet at start, which functions the kernelet may call, and which functions the host may call. It is in prototype/vostd/src/abi.rs on the Rust side and prototype/linux/endovisor/kernelet.h on the C side, and the two must agree byte for byte.

The first two are the image’s contents; the third is this chapter’s subject.

Registering an image validates the restricted PIE format described in the endovisor UAPI. The build links the kernel proper and vOSTD into one self-contained ET_DYN image, whose program headers fix the relative layout of code and data. The image imports no host symbols; it calls Linux through the service table supplied at entry. The ELF header’s e_entry identifies the entry-table object below, which the endovisor reads rather than executing as an instruction.

The registered kind owns one physical copy of the code and read-only data and a pristine template for writable data. Each sandbox gets a separate virtual mapping of that layout: shared physical pages for code and read-only data, fresh pages for writable data and zero-initialized storage. R_X86_64_RELATIVE relocations initialize its private pointers using its own load base. The entry table therefore contains addresses within that sandbox’s code mapping. Multiple sandboxes of one kind can run concurrently; the code is shared, while globals, pointer tables and vOSTD’s state are private.

Linux: modules and exported symbols. A kernel module, code loaded into the running kernel with insmod, may call only the kernel functions that the kernel marks as exported (EXPORT_SYMBOL in the source); the rest are private to the kernel even though they are in the same address space. The endovisor is a module. A few functions it needs are not exported in a stock kernel, which is one of the two reasons for the patch in the next chapter.

vOSTD is the only crate in the image that can reach the service table, which it keeps private, so only vOSTD can call a service.

Two rules shape every service. Arguments are integers or pointers into the kernelet’s own memory: a space number, a virtual address, a physical address, a buffer to log. The one exception is mem_free, whose pointer is into host memory that mem_alloc returned, below; the endovisor checks it against a table of the blocks it handed out, kept where the kernelet cannot reach, reads the block’s number below the pointer with a read that tolerates a fault, and refuses what it does not recognize (a stale pointer to a block that was freed and handed out again at the same address is the one case it cannot tell apart). And the host writes into the kernelet only through the two pointers vOSTD hands it for that purpose, the user context that user_run is given and the area that fpu_save is given, and keeps no other. Both keep a buggy vOSTD from steering the endovisor into writing wherever the kernelet says.

The grant and the direct map

The endovisor gives a kernelet a grant: one physically contiguous block of RAM, the memory_initial of the holder’s create request (4 MiB from the prototype’s holder; a request is rounded up to 2 MiB and may not exceed 4 MiB), taken from Linux’s page allocator when the sandbox starts, charged to the sandbox’s control group, and described in the boot arguments by its physical address and length.

Simplified from prototype/linux/endovisor/sandbox.c: klet_sandbox_start.

int klet_sandbox_start(struct klet_inst *inst)
{
	unsigned int order = get_order(inst->memory_initial);       /* 2^10 pages for 4 MiB */

	int err = klet_image_start(inst);                          // Shared code, private data and relocated pointers.
	if (err)
		return err;

	if (!pages)
		return -ENOMEM;
	inst->grant_pages = pages;
	inst->boot.abi_version = KLET_ABI_VERSION;
	inst->boot.grant_paddr = page_to_phys(pages);
	inst->boot.grant_len = PAGE_SIZE << order;
	inst->boot.linear_map_base = (u64)(unsigned long)__va(0);
	inst->boot.nr_vcpus = inst->nr_vcpus;
	/* ... the FPU area's size, the cycle counter's rate, the image's text range, and more in later chapters */
	return 0;
}

Linux: the direct map. Linux maps all of physical memory, in order, into one region of the kernel’s address space, called the direct map or linear map. Turning a physical address into a pointer the kernel can dereference is therefore one addition: __va(paddr) is paddr + base. kmalloc and the page allocator hand out direct-map memory, so for them a kernel pointer and a physical address are two names for the same bytes; vmalloc, from which the endovisor takes kernelet stacks, is the exception, because it maps scattered pages into a separate region. The line __va(0) above is simply the base.

vOSTD’s frame allocator plays over the grant the part OSTD’s plays over a machine’s RAM, more simply: where the allocator shipped with OSTD is a buddy system, vOSTD’s is a bitmap with one bit per 4 KiB frame, a first-fit search for n contiguous free frames, and a reference count per frame (the count matters once tenant pages sit on Linux’s page tables). When the kernel proper’s FrameAllocOptions asks for a segment, this is what answers.

Simplified from prototype/vostd/src/mm/frame.rs: alloc, FrameAllocOptions.

    let guard = Guard::lock();                 // a spin lock over the bitmap
    let bits = guard.bits();
    let mut start = 0;
    'outer: while start + nframes <= total {
        for i in start..start + nframes {
            if test(bits, i) { start = i + 1; continue 'outer; }   // in use: look further
        }
        for i in start..start + nframes {
            bits[i / 64] |= 1u64 << (i % 64);
            REFS[i].store(1, Ordering::Relaxed);                     // one reference: the handle
        }
        return Some(BASE + start * PAGE_SIZE);
    }
    None
}

The console and the log. println! collects a line and hands it to console_write, the sandbox’s console; vOSTD’s own lines, among them a panic’s message, go to log_write, the sandbox’s kernel log. How the kernelet starts

The endovisor enters the image at kernelet_entry with the two tables. vOSTD records them, sets up what the chapter has described, and calls the kernel proper’s main.

pub(crate) unsafe extern "C" fn kernelet_entry(boot: *const BootArgs, svc: *const Services) {

What remains unexplained is where kernelet_entry is called from: on which Linux task, on which stack, and how that task later enters user mode for the kernelet. Those are the next four chapters.

Recap. A kernelet talks to the host through three C-layout tables: boot arguments in, a service table of function pointers out, and an entry table the host calls. Its memory is a grant of a few MiB whose frames it reaches through Linux’s direct map, its heap is kmalloc behind a service, and its console and log go to files the holder sets, or to printk if it sets none. The endovisor starts it by calling kernelet_entry, which ends in the kernel proper’s main.

Carrier hooks and patch overview

Left alone, Linux answers a tenant’s system calls itself. A kernelet’s user program runs in user mode on a real processor. When it executes syscall, the processor jumps into whatever the hardware’s system-call entry register points at, and on a Linux machine that is Linux’s entry code. Linux would then look the call number up in its own table and run write. Nothing in the hundred-line kernel would ever hear of it.

So the design needs a way to hand a system call to a kernelet before Linux handles it. It also needs, for reasons this chapter builds up to, a way to run kernelet code just before one of its tasks enters user mode, whatever brought the task into the kernel. Linux has no such interface. This chapter adds one that does both: two hooks, which Linux calls only for the tasks that carry a kernelet.

To Linux, a carrier is a task with one new field: a pointer to its carrier event hooks, a table of two functions. A carrier is a Linux task that carries one of a sandbox’s virtual CPUs: it runs the kernelet’s code and enters user mode for it (chapter 1’s table; chapter 2 showed how one is made). Linux calls the two functions at the two events through which every crossing between a carrier’s user mode and the kernel passes: a system call from the carrier’s user mode, and the carrier’s return to user mode with work pending. For an ordinary task the pointer is null, and nothing in the patch is reached.

The table is the whole interface by which Linux’s core calls into the endovisor. The core knows the type of the two functions and the two places to call them, and nothing of what is behind them; the endovisor implements the functions, puts a table into the record it keeps for each carrier, and finds that record from the table’s address when a hook is called.

Where Linux can be hooked

Linux: tasks and the entry path. Linux’s unit of execution is the task (struct task_struct); a thread is a task, a single-threaded process is a task.

While a task is in the kernel, its user registers sit in pt_regs. When a task enters the kernel from user mode, the entry code saves the user registers at the top of the task’s kernel stack in a structure called pt_regs, and restores them from there on the way back. To change what a task does when it returns to user mode, change its pt_regs.

On x86-64 every system-call instruction, after a few lines of assembly and one architecture-specific C function, reaches architecture-independent C in kernel/entry/common.c, the generic entry layer. On the way in, if the task has any bit set in a per-task mask called its syscall work, the layer calls syscall_trace_enter(), which runs Linux’s interception mechanisms in order: Syscall User Dispatch, ptrace, and seccomp, the filter by which a process restricts which system calls it and its descendants may make. Any of them may declare the call answered, in which case Linux skips its own handler. On the way out, if the task has pending work such as a signal, the layer runs exit_to_user_mode_loop() until none is left, then restores pt_regs.

Linux thus already has three stages that can intercept a system call. All three are controlled from user space, and none lets kernel code answer a call. The syscall hook is a fourth stage that does, and the resume hook is its counterpart on the way out.

Two hooks, one for each direction

On the way in. The hook answers the question the chapter opened with: the tenant made a system call, so give it to the kernelet. It runs last among the interceptors, and if the kernelet answers the call, Linux’s table is skipped.

On the way out. A system call is the only reason a tenant asks for its kernel, but it is not the only reason the kernel must run before the tenant does. Three more appear in later chapters:

  • A carrier has just been created. It is a fresh Linux task heading for user mode, and nothing of the kernelet has run on it yet. The kernelet must boot, build the tenant’s address space and choose the registers the task will enter user mode with, all before that first entry, and there has been no system call to hook.
  • The tenant has faulted. It executed an instruction it may not, or touched a page that is not mapped. Linux handles the exception and, as for every process, turns it into a signal to deliver on the way back to user mode. The kernelet must take that exception for itself before Linux delivers the signal.
  • Someone else wants the kernelet. A timer fired, or another virtual CPU has a task for this one, while the carrier is in user mode. It must be brought into the kernel and then into kernelet code before it continues.

In every case the task is inside the kernel, on its way back to user mode, and someone has set a flag saying there is work to do before it gets there. Linux already has exactly that moment: the exit loop, which runs whenever a task with pending work is about to return to user mode. The way-out hook is placed at its top. The job it gives the kernelet is the same every time: the tenant is about to run; find out why you were called, and run kernelet code first if there is any to run.

The patch, hunk by hunk

A table of hooks and a pointer per task. A new header defines the table, two function pointers, and struct task_struct gains a pointer to one. A task whose pointer is null is unaffected by anything else in the patch.

Simplified from prototype/linux/patches/0001-carrier-hooks.patch: carrier_event_hooks.

/* include/linux/kernelet.h (new) */
struct carrier_event_hooks {
	/* Called from syscall_trace_enter(), after seccomp, for a system call
	 * issued by a carrier's user mode; regs hold the number and the
	 * arguments. Returns true if the kernelet serviced the call: regs then
	 * hold what the task returns to user mode with, return value included,
	 * and Linux's own dispatch is skipped. Returns false to let Linux
	 * dispatch the call as for any other task. */
	bool (*on_syscall)(struct pt_regs *regs);

	/* Called from exit_to_user_mode_loop(), after the TIF_NOTIFY_RESUME
	 * work and before signals are delivered, whenever a carrier is about
	 * to return to user mode with exit work pending: for a reason of the
	 * kernelet's own (a carrier's first entry, a tenant's fault, a virtual
	 * interrupt) or for one of Linux's (a reschedule, a signal). No reason
	 * is passed, and several may be pending at once: whoever requested the
	 * call recorded why in the endovisor's record for the task, and the
	 * hook reads it there. The loop may call it more than once on one
	 * return.
	 *
	 * Runs in process context with no lock held; it may sleep, and may run
	 * kernelet code for as long as it likes. It may rewrite regs, which are
	 * what the task returns to user mode with, and must leave them alone
	 * when it has nothing to do. */
	void (*on_resume)(struct pt_regs *regs);
};

/* include/linux/sched.h, inside struct task_struct */
	struct carrier_event_hooks	*carrier_hooks;	/* NULL for every ordinary task */

One bit of syscall work. The patch adds a syscall-work bit, SYSCALL_WORK_KERNELET, so that Linux calls syscall_trace_enter() for a carrier. Linux calls that function only for tasks with a bit set in their syscall-work mask, and the new bit is included in the set that triggers the call on entry. A task that is not a carrier pays nothing: the fast path does not even test the pointer.

The syscall hook. Inside syscall_trace_enter(), directly after seccomp:

Simplified from prototype/linux/patches/0001-carrier-hooks.patch: SYSCALL_WORK_KERNELET.

/* kernel/entry/common.c, syscall_trace_enter() */
	if (work & SYSCALL_WORK_KERNELET) {
		if (current->carrier_hooks->on_syscall(regs))
			return -1L;
	}

Returning -1 from this function is Linux’s existing convention for “an earlier stage has answered this call; do not dispatch it”, and do_syscall_64() then skips the table.

Seccomp comes first. Because the hook is placed after seccomp, the filter a sandbox was started with runs on every one of the tenant’s system calls before the kernelet sees them. That is a tool for the kernelet runtime, the host program that creates sandboxes (chapter 2), with a sharp edge. A filter that allows a call lets the kernelet serve it. One that returns an error answers the call in Linux, and the kernelet never hears of it. One that kills ends a carrier, and with it, by the endovisor’s rule that a lost carrier kills its sandbox, the whole sandbox. A filter for a sandbox therefore bounds what the tenant may ask of its kernelet, and must be written for that, not copied from a host process.

The prototype’s holder installs a filter only in one boot of make probe, which checks that a killing filter ends the sandbox.

The resume hook. The patch’s second call is on the way out. A task reaches exit_to_user_mode_loop() only when it has exit work pending, and the hook sits at the top of that loop, after interrupts are enabled and before Linux delivers signals. The loop, and the flag that most often sends a task into it, are Linux’s own:

Linux: the exit work flags and TIF_NOTIFY_RESUME. A task carries a word of thread flags, and a few of them mean “do something before this task next returns to user mode”: TIF_SIGPENDING (a signal to deliver), TIF_NEED_RESCHED (the scheduler wants the processor back), and TIF_NOTIFY_RESUME, the general-purpose one, which stands for any other deferred work. The entry layer tests the whole set at once (EXIT_TO_USER_MODE_WORK) and enters exit_to_user_mode_loop() only if one of them is set.

TIF_NOTIFY_RESUME stands for deferred work, run by resume_user_mode_work(), which clears the flag first. It is set by set_notify_resume(), and by task_work_add(), which queues a function for a task to run on its own way out to user mode. The flag’s work, resume_user_mode_work(), clears the flag, runs the queued task work, reclaims memory for a control group over its high limit, throttles block I/O if the task owes some, and tells a restartable sequence that it was interrupted. That it clears the flag first is what the excerpt below depends on.

The hook, with Linux’s own work for that flag placed before it:

Simplified from prototype/linux/patches/0001-carrier-hooks.patch: resume_user_mode_work.

Linux’s own notify-resume work goes first because its first act is to clear the flag that requested it. Run after the hook, it would clear a request the endovisor made from another processor while the hook was looking elsewhere, and the carrier would enter user mode with that request pending.

The hook runs before signal delivery so that the kernelet can take a tenant’s exceptions away from Linux, when the round trip into user mode is built.

The hooks are inherited. Nothing in the patch copies the pointer into child tasks, and nothing needs to: Linux creates a task by copying the parent’s whole task_struct (dup_task_struct()), the new field included, and the syscall-work bits are inherited the same way. A child of a carrier therefore has the hooks before it executes its first instruction, and there is no moment at which it could make a system call that Linux would answer. A carrier never forks through Linux, since the kernelet answers its system calls, so a child that shared its parent’s record never arises. This is the difference between a field Linux does not know about, which it copies, and a setting Linux knows about, such as Syscall User Dispatch, which it deliberately resets at fork and exec.

Two helper functions. kernel/fork.c gains two functions that the endovisor cannot write itself because everything they touch is private to the core kernel: kernelet_mm_alloc(), which creates an empty address space with a chosen owner, and kernelet_switch_mm(), which makes the calling task run in a different address space. Both belong to tenant memory, built on Linux’s page tables later in the book; they are mentioned here only so that the patch’s contents are complete.

Six exports. Functions the endovisor needs that Linux does not already export to modules, each one EXPORT_SYMBOL_GPL line. flush_tlb_mm_range is for vm_flush, the flush of a tenant’s address space. Four are for the image loader of chapter 4: set_memory_rox, which makes shared code mappings read-only and executable; set_memory_ro, which makes shared data mappings read-only; set_memory_rw, which restores backing-page writability before the pages are freed; and modules_disabled, the setting by which an operator forbids module loading, which registering an image checks as init_module does. kernel_clone is exported too; nothing in the endovisor calls it.

A configuration option. CONFIG_KERNELET guards the hooks, the field, the helpers and two of the exports, and selects CONFIG_PREEMPT_NOTIFIERS, which the endovisor uses. The prototype’s kernel configuration turns it on. A kernel built without it differs from a stock kernel only in exporting the four symbols of the image loader, whose export lines are unconditional; every other line the patch adds to a function is inside #ifdef CONFIG_KERNELET, and what remains outside are the include lines, a forward declaration, the new header (the hooks’ type and two prototypes), the bit’s name and a macro that expands to zero.

A precondition. The kernel must be built without the legacy vsyscall page (CONFIG_X86_VSYSCALL_EMULATION unset). A program that jumps to that page’s fixed address gets three system calls answered by Linux’s own page-fault handler, without ever reaching the entry path, so the syscall hook would never see them. The module refuses to load on a kernel built with it.

What the patch does not do

It adds no new system call, no boot parameter, and no change to Linux’s scheduler or memory manager. For a task whose carrier_hooks pointer is null, which is every task on a machine without a loaded endovisor, the two hooks are never reached. Its whole effect is to let some kernel code, named by a pointer in the task, see a task’s system calls before Linux does and run once more before the task returns to user mode. Who installs that pointer, and on which tasks, is the next chapter.

Recap. The carrier event hooks are two functions that Linux’s generic entry layer calls for a carrier, selected by a pointer in task_struct and a syscall-work bit: on_syscall runs after seccomp and can answer the call so that Linux’s table is skipped; on_resume runs on the way back to user mode, before signals are delivered, and gives the kernelet the last word before the tenant runs, for everything that is not a system call: a carrier’s first entry, a tenant’s fault, a timer or another virtual CPU wanting it. A child inherits the pointer because Linux copies the task structure. The rest of the patch is two helpers and six exports for other chapters.

Carriers

Chapter 5 attached two hooks to a Linux task. This chapter is about those tasks: where they come from, what they inherit, and how the endovisor learns when one dies.

A carrier is a Linux task that carries one of a sandbox’s virtual CPUs: it runs the kernelet’s code and enters user mode on the kernelet’s behalf, and a virtual CPU is one of the processors the kernelet believes it has. Linux schedules carriers like any tasks; it does not know what they carry. A sandbox has a fixed number of them, one per virtual CPU, chosen when it is created, and nothing else of the sandbox is a task: the holder of chapter 2, which created the sandbox, is a process of the runtime and runs no kernelet code. What a virtual CPU is in full comes with the kernelet’s own scheduler; for now, a sandbox with one virtual CPU, like the hundred-line kernel’s, has one carrier.

Why a carrier is not a kernel thread

A carrier is an ordinary user task, not a kernel thread, because it must enter user mode. Linux has a kind of task that runs only kernel code, the kernel thread, and it is the natural first thought for “a task that runs the kernelet”. It is the wrong one. A kernel thread has no user address space and can never return to user mode, and a carrier must: entering user mode to run the tenant’s program is the one thing the kernelet cannot do for itself. So a carrier has an address space and a pt_regs, and happens to spend most of its time in kernel mode.

A carrier is born by fork and exec

Linux: how tasks are made. Almost every task is created by one function, kernel_clone(), which underlies fork, clone and kernel-thread creation. It copies the parent’s task structure and then, depending on flags, shares or copies the address space, open files and so on. A child made by fork is therefore a copy of its parent in every property Linux keeps on the task: control group, credentials, namespaces, processor mask, priority, resource limits, seccomp filter, and the hooks pointer the patch added.

A task gets a fresh address space only from execve. Linux offers the file to each registered binary-format handler (struct linux_binfmt) in turn, and the one that recognizes the file replaces the process’s address space and sets its starting registers. A module can register a handler of its own. What exec keeps of the task and what it resets is the box of chapter 2.

A carrier has whatever its process set on itself before the exec, because exec keeps the task’s properties and replaces only its program. For each virtual CPU the holder asks the sandbox for an exec descriptor, forks a child, and the child, after arranging itself with ordinary system calls, executes the descriptor with execveat. What the child set is what the carrier has: its control group, which the holder joined before creating the sandbox; its processor mask and priority; its seccomp filter, if the runtime installed one. The prototype’s child sets the no-new-privileges bit, which the endovisor insists on, and pins itself or installs a filter if its options ask.

A sandbox is charged through its control group: every carrier is in it, so the kernelet’s processor time and accounted memory are the tenant’s. Chapter 2’s box introduced control groups, and KLET_CREATE records the holder’s group and refuses the exec of an exec descriptor from any other. A child starts in its parent’s group, and exec does not change it. The processor time the kernelet burns is therefore charged to the tenant by machinery Linux already has, and so is any memory allocated on a carrier with the flag that asks for it (__GFP_ACCOUNT). Linux charges the tenant’s page tables that way by itself, to the carrier whose fault or mapping causes them; the endovisor charges the grant, the pages of the kernelet’s stacks and its heap with the same flag (GFP_KERNEL_ACCOUNT), all of them allocated on a carrier of the sandbox.

The endovisor’s half is the binary-format handler, where the child becomes the carrier:

Simplified from prototype/linux/endovisor/main.c: klet_load_binary, klet_empty_mm, klet_ignore_signals.

static int klet_load_binary(struct linux_binprm *bprm)
{
	if (memcmp(bprm->buf, KLET_EXEC_MAGIC, KLET_EXEC_MAGIC_LEN) != 0)
		return -ENOEXEC;                        /* not ours: the next handler's turn */
	inst = klet_exec_lookup(bprm, &vcpu);       /* which sandbox and virtual CPU, by the file's inode */
	if (!inst)
		return -ENOEXEC;
	err = klet_exec_claim(inst, vcpu);          /* not killed; not started; the sandbox's group; no new privileges */
	if (err)
		return err;                             /* ESRCH, EBUSY or EPERM: the exec fails and the process lives on */

	begin_new_exec(bprm);                       /* the point of no return: a fresh address space, signal handlers reset */
	klet_personality_64bit();
	setup_new_exec(bprm);
	klet_empty_mm();                            /* unmap the one area exec left: the argument stack */
	set_binfmt(&klet_format);
	finalize_exec(bprm);
	start_thread(current_pt_regs(), 0, 0);      /* valid 64-bit user registers, though it never uses them */
	klet_ignore_signals();                      /* every signal that can be ignored is: chapter 8 says why */
	set_mask_bits(&current->mm->flags, MMF_DUMPABLE_MASK, SUID_DUMP_DISABLE);   /* not dumpable, whoever the holder is */
	snprintf(comm, sizeof(comm), "kernelet/%d/%u", inst->slot, vcpu);          /* the name ps shows */
	strscpy_pad(current->comm, comm, sizeof(current->comm));

	c = klet_carrier_new(inst, vcpu);
	klet_carrier_attach(c);                     /* the hooks and the lifeline */
	mmget(current->mm);                         /* keep a reference to the empty address space ... */
	c->blank_mm = current->mm;                  /* ... dropped when a tenant's replaces it, with tenant memory */
	inst->vcpus[vcpu] = c;

	if (!inst->started)                         /* the first arrival starts the sandbox: */
		klet_sandbox_start(inst);               // The private image mapping, the grant, the boot arguments.
	inst->arrived++;
	wake_up_all(&inst->arrive_wq);              /* virtual CPU 0 may be waiting for this one */

	set_thread_flag(TIF_NOTIFY_RESUME);         /* make the resume hook run on the way out */
	return 0;
}

The calls from begin_new_exec to start_thread are what every program loader makes, with one difference. The ELF loader would now map the program and its stack into the new address space; this handler maps nothing, and even unmaps the temporary page that holds the execveat arguments, so that the address space is empty. Nothing of the host’s is left in it for a tenant to read.

One line undoes what the holder’s identity would otherwise leave: the carrier is made non-dumpable. Linux makes a process that executed a file it cannot read dumpable only as fs.suid_dumpable allows, which by default is not at all, but root can read an execute-only file, so for a root holder the rule would leave the carrier dumpable; the handler clears the dumpable bits itself, for the carrier and, later, for every address space the kernelet creates.

start_thread gives the task a valid 64-bit user register frame, as every loader must; the resume hook will overwrite it before the task ever reaches user mode.

The last line hands the carrier to the resume hook. The carrier returns from the handler and heads for user mode, as every execve does. On the way it passes through the exit loop, and because the flag is set, the resume hook runs. The carrier never arrives in user mode on its own account: from here on it goes there only when the kernelet sends it. Setting TIF_NOTIFY_RESUME on a carrier, by a plain flag-set on the current task or by set_notify_resume() on another, which also nudges the processor that task is on, is what the book calls flagging the carrier.

Entering the kernelet

The resume hook is where a new carrier enters the kernelet, once its virtual CPU may start. Its first trip through the hook finds the carrier in the state NEW:

static bool klet_vcpu_await(struct klet_carrier *c)
{
	if (c->vcpu == 0)                           /* virtual CPU 0 boots the kernelet, once every carrier has arrived */
		wait_event_state(inst->arrive_wq, inst->arrived == inst->nr_vcpus || inst->dying,
				 TASK_KILLABLE | TASK_NOLOAD);
	else                                        /* the others wait for the kernel proper to start their processor */
		wait_event_state(c->idle_wq, c->boot_requested || inst->dying,
				 TASK_KILLABLE | TASK_NOLOAD);
	return !inst->dying && !fatal_signal_pending(current) &&
	       (c->vcpu == 0 ? inst->arrived == inst->nr_vcpus : c->boot_requested);
}

The kernelet boots only when every virtual CPU’s carrier has arrived, because a kernel that starts its other processors expects each of them to answer.

Carriers wait in a killable, no-load sleep. wait_event_state is Linux’s ordinary way to sleep until a condition holds: a waker wakes the queue the sleeper named, and the sleeper checks its condition again. The sleep is killable, ended only by SIGKILL, because a SIGSTOP sent to a carrier stays pending until the carrier next heads for user mode and must not end the wait early; and no-load, so that a waiting carrier is not counted in the load average.

klet_enter runs the kernelet until it asks to run a user program, or leaves for good. For virtual CPU 0 it leads to kernelet_entry from chapter 4, and so to the kernel proper’s main; for the others, to vcpu_entry, once the kernel proper has asked for that processor through the service vcpu_boot. When the carrier returns from klet_enter with a program to run, the hook’s loop puts the right registers in place and lets Linux return to user mode. klet_enter itself is the subject of the next chapter.

Lifelines

The endovisor must hear of a carrier’s death however it happens, because a sandbox cannot continue without one of its processors. A carrier can die without the endovisor’s involvement: the operator kills it, or Linux’s out-of-memory killer does. Losing a carrier is losing a processor with whatever the kernelet was doing on it. Linux offers a clean way to hear of it.

Linux: descriptors and release. When a task exits, Linux closes its open files, and the last close of a file runs the file’s release operation. Every process has a table of open file descriptors, and a task’s exit closes them all, whatever the reason for the exit. A module can make an open file of its own with anon_inode_getfile(), with whatever operations it likes.

So each carrier holds, in its descriptor table, one open file of the endovisor’s that nothing ever reads or writes: its lifeline. Its release is the death notice.

Simplified from prototype/linux/endovisor/carrier.c and prototype/linux/endovisor/main.c: klet_carrier_attach, klet_lifeline_release.

int klet_carrier_attach(struct klet_carrier *c)
{
	struct file *file = anon_inode_getfile("[kernelet-carrier]", &klet_lifeline_fops, c, O_RDWR);
	int fd = get_unused_fd_flags(0);
	fd_install(fd, file);                       /* into this task's own table, which the exec made sure no other task shares */

	current->carrier_hooks = &c->hooks;         /* attach the hooks ... */
	set_syscall_work(KERNELET);                 /* ... and ask for the syscall hook */
	return 0;
}

static int klet_lifeline_release(struct inode *inode, struct file *file)
{
	klet_carrier_lifeline_closed(file->private_data);   /* the carrier is gone */
	return 0;
}

Only the carrier’s death can close its lifeline. It is installed after the exec, so no other task holds a copy of it: the exec made sure the child’s table is shared with no other task. A tenant cannot close it, because closing a descriptor is a Linux system call, and the syscall hook takes those. A copy taken later with pidfd_getfd, which needs CAP_SYS_PTRACE against a non-dumpable task, delays the notice until that copy closes.

A closed lifeline ends the sandbox, and the last one to close marks it exited. When a lifeline closes, the endovisor takes the carrier off its lists. If the sandbox was still running, whichever carrier’s lifeline it was, the sandbox is over: the endovisor marks the kernelet dying and ends every other carrier. When the last lifeline closes, no carrier is left and the sandbox has exited, which makes the sandbox descriptor readable and wakes the holder waiting for its exit record.

Recap. A carrier is an ordinary Linux user task that runs kernelet code and enters user mode for it. The holder forks one child per virtual CPU, and each child executes that virtual CPU’s exec descriptor, which the endovisor’s binary-format handler claims: it checks the child’s control group and its no-new-privileges bit, gives it an empty address space, ignores every signal that can be ignored, makes it non-dumpable, names it, and attaches the hooks and a lifeline. The child keeps what it set on itself before the exec, by the ordinary rules of exec. On its way out the resume hook holds it until every carrier has arrived, then enters the kernelet. Every carrier holds a lifeline, an open file whose release tells the endovisor that the carrier has died.

Two stacks

Chapter 3 drew a picture: the kernel proper’s handler for a user program is a loop inside a function, and its local variables live on a kernel stack across every trip to user mode. This chapter is about why Linux cannot give a carrier such a stack, and how the endovisor gives it one anyway.

Two kernels, two opinions about the stack

Linux: a task’s kernel stack. A Linux task’s kernel stack, 16 KiB on x86-64, is empty whenever the task is in user mode. The stack is used whenever the task runs in kernel mode, and it is empty while the task is in user mode: a system call builds a few frames on it, and returning to user mode discards them. Linux’s exit path relies on this; nothing in Linux can be “in the middle of a function” while its task runs user code. The saved user registers, pt_regs, sit at the very top of the stack and are the one thing that survives.

The kernel proper is built the other way around. Its execute call must return when the program makes a system call, into a function whose frame was there before the program ran. If kernelet code used the carrier’s Linux stack, that frame would be discarded the moment the carrier returned to user mode.

The resolution is to give kernelet code stacks of its own. A kernelet stack is a block of kernel memory that the endovisor allocates and that the kernelet’s tasks run on. The carrier switches onto a kernelet stack to run kernelet code and back onto its Linux stack to let Linux return to user mode. Linux’s stack is empty exactly when Linux expects it to be, and the kernelet’s stack holds the suspended loop exactly as the kernel proper expects.

Linux tolerates one task with two stacks better than one might fear:

  • Linux’s scheduler saves and restores only the stack pointer when it switches tasks, so a carrier can be preempted while on a kernelet stack and resumed there.
  • Linux finds the current task through a per-processor pointer, not through the stack.
  • An interrupt that arrives while the carrier is on a kernelet stack pushes its frame there and then moves to Linux’s per-processor interrupt stack, as it would from any kernel stack.
  • pt_regs are found from the top of the Linux stack, which does not move.

What Linux does not tolerate is kernelet code calling into Linux while on a kernelet stack, for any length of time. Linux’s code assumes its own stack: its unwinder and backtraces, its checks that a buffer lies on the task’s stack, and its idea of how much room is left. So the rule is: kernelet code runs on a kernelet stack, and nothing the kernelet or the endovisor calls of Linux runs there; only Linux’s own interrupt and exception entry, and preemption on their way out, use it, and the endovisor’s own code runs there only in the few lines that switch.

The switch

The switch is a few lines of assembly, the oldest trick in the book of coroutines: save the registers the calling convention makes the callee responsible for, swap the stack pointer, restore the other side’s registers, and return. Because ret pops from the new stack, the function returns into whatever code was suspended there.

Simplified from prototype/linux/endovisor/switch.S: klet_switch.

/* void klet_switch(void **save_sp, void *new_sp) */
klet_switch:
	pushq	%rbp
	pushq	%rbx
	pushq	%r12
	pushq	%r13
	pushq	%r14
	pushq	%r15
	movq	%rsp, (%rdi)      /* remember where this stack stopped */
	movq	%rsi, %rsp        /* and continue on the other one */
	popq	%r15
	popq	%r14
	popq	%r13
	popq	%r12
	popq	%rbx
	popq	%rbp
	RET

The six pushed registers are the ones the x86-64 calling convention says a called function must preserve; the others may be clobbered by any call, so the compiler never expects them to survive one. To the compiler, klet_switch is an ordinary function that happens to return much later, on another stack.

A fresh kernelet stack has to look as if klet_switch had already been called on it once, so that the first switch “returns” into the right place. The endovisor plants that frame by hand:

Simplified from prototype/linux/endovisor/carrier.c: klet_coro_prepare.

static void klet_coro_prepare(struct klet_carrier *c)
{
	u64 *sp = (u64 *)((char *)c->stack + KLET_STACK_SIZE);   /* the top of the stack */

	*--sp = 0;                              /* a fake return address */
	*--sp = (u64)klet_coro_trampoline;      /* what klet_switch's `ret` will jump to */
	*--sp = 0;                              /* rbp */
	*--sp = 0;                              /* rbx */
	*--sp = (u64)c;                         /* r12: the carrier, for the trampoline */
	*--sp = 0;                              /* r13 */
	*--sp = 0;                              /* r14 */
	*--sp = 0;                              /* r15 */
	c->coro_sp = sp;
}

The first klet_switch onto a new stack lands in the kernelet’s entry point, through a trampoline. The trampoline moves the carrier pointer from r12 into the first-argument register and calls klet_coro_main, which for virtual CPU 0 is the call to kernelet_entry from chapter 4, on a stack the kernelet owns.

The endovisor wraps the switch in two functions, one for each direction:

Simplified from prototype/linux/endovisor/carrier.c: klet_enter, klet_leave.

/* On the Linux stack: give control to the kernelet. */
static void klet_enter(struct klet_carrier *c, u64 run_ret)
{
	c->run_ret = run_ret;                   /* what user_run will return, if that is where it stopped */
	c->state = KLET_RUNNING;
	c->depth = 0;
	klet_mirror_in(c);                      /* note Linux's preemption count, for the mirror built later */
	klet_watch_arm(c);                      /* the watch timer on this processor, built later */
	klet_switch(&c->linux_sp, c->coro_sp);  /* returns when the kernelet leaves */
}

/* On a kernelet stack: give control back to Linux. */
static void klet_leave(struct klet_carrier *c, enum klet_cstate state)
{
	klet_mirror_out(c, state == KLET_DEAD); /* what the kernelet lent Linux's preemption count, taken back */
	c->state = state;
	klet_switch(&c->coro_sp, c->linux_sp);  /* returns when the kernelet is next entered */
}

klet_enter is called from exactly two places, the two hooks: the resume hook, which also makes a new carrier’s first entry on its way out of the exec (chapter 6), and the syscall hook. Each of those is a frame on the Linux stack, and klet_switch parks that frame until the kernelet leaves.

Where the stacks come from

Linux: vmalloc. Linux has two kinds of kernel memory: the direct map, physically contiguous, from kmalloc and the page allocator; and the vmalloc area, where the kernel builds virtually contiguous ranges out of scattered pages with vmalloc(). Each range is followed by an unmapped guard page, so running off the end of one faults instead of silently overwriting its neighbor.

A kernelet stack is 256 KiB from vmalloc, with an unmapped page before and after it, since every vmalloc range is followed by one.

What the guard page buys is less than it seems. A stack that runs off its end faults with a stack pointer that is already bad; delivering a fault pushes a frame onto the very stack that has run out, so the processor cannot deliver it, and Linux halts the machine on the double fault that results. A check at every function entry of the image would catch it before the end; this prototype has no such check, so a kernel proper with unbounded recursion would halt the host, and the test kernels are written not to recurse.

The endovisor keeps a pool of stacks per sandbox: a freed stack goes back to the pool, not to Linux, and the pool is returned whole when the sandbox’s last carrier is gone. The reason is a Linux detail a tenant could otherwise turn against the machine: freeing vmalloc memory is batched, and the batch ends in a TLB flush on every processor, so a kernel that created and ended tasks in a loop would tax processors it is not allowed to run on.

Simplified from prototype/linux/endovisor/carrier.c: klet_kstack_alloc, klet_kstack_put.

u64 klet_kstack_alloc(struct klet_inst *inst)
{
	list_for_each_entry(k, &inst->kstack_all, link)     /* a free one in the pool? */
		if (!k->busy) { k->busy = true; return (u64)k->base; }

	if (inst->kstack_made >= inst->kstack_max)          /* the pool is bounded: max_tasks + nr_vcpus stacks, from KLET_CREATE */
		return 0;                                       /* vOSTD turns 0 into an out-of-memory error */
	inst->kstack_made++;
	base = __vmalloc(KLET_STACK_SIZE, GFP_KERNEL_ACCOUNT);   /* else grow the pool; charged to the sandbox (chapter 6) */
	k = kzalloc(sizeof(*k), GFP_KERNEL);
	k->base = base; k->busy = true;
	list_add_tail(&k->link, &inst->kstack_all);
	return (u64)base;
}

void klet_kstack_put(struct klet_inst *inst, u64 base)
{
	list_for_each_entry(k, &inst->kstack_all, link)
		if ((u64)k->base == base) { k->busy = false; return; }
}

The real function holds the instance’s lock around the search and the reservation, so that two virtual CPUs cannot both take the last stack.

Every kernelet stack comes from this pool: the carrier’s first one and each task’s. The kernelet reaches the pool through two services, kstack_alloc and kstack_free. The carrier’s own first stack, the one klet_coro_prepare sets up, comes from the pool; so does the stack of every task the kernel proper creates.

Services run on the Linux stack

A crossing, in this book, is one service call: from kernelet code into the endovisor and back, switching stacks twice. A service call is kernelet code calling the endovisor, and by the rule above it must switch stacks. It cannot use klet_enter and klet_leave, which hand control over; it needs to call a function and come back. The endovisor has a second, smaller switch for that:

Simplified from prototype/linux/endovisor/switch.S: klet_run_on_linux_stack.

/* void klet_run_on_linux_stack(void *linux_sp, struct klet_svc_args *args) */
klet_run_on_linux_stack:
	pushq	%rbp
	movq	%rsp, %rbp            /* remember the kernelet stack */
	movq	%rdi, %rsp            /* jump onto the Linux stack, below the parked frame */
	andq	$-16, %rsp
	movq	%rsi, %rdi
	call	klet_svc_body         /* the service, on Linux's stack */
	movq	%rbp, %rsp            /* and back */
	popq	%rbp
	RET

A service runs on the Linux stack just below the frame klet_enter parked. linux_sp is where klet_enter’s klet_switch parked the Linux stack, that is, the lowest byte of it in use; everything below is free, and the service runs there.

Every service in the table except one, user_run, goes through a stub: a stub packs the arguments into a small structure, calls klet_run_on_linux_stack, and unpacks the result.

Simplified from prototype/linux/endovisor/carrier.c: klet_svc_enter, klet_svc_log_write, klet_svc_body.

static u64 klet_svc_enter(u64 op, u64 a0, u64 a1, u64 a2)
{
	struct klet_carrier *c = klet_current_carrier();
	struct klet_svc_args args = { .op = op, .a0 = a0, .a1 = a1, .a2 = a2 };

	klet_run_on_linux_stack(c->linux_sp, &args);
	return args.ret;
}

static void klet_svc_log_write(const char *ptr, u64 len)     /* what the service table points at */
{
	klet_svc_enter(KLET_SVC_LOG_WRITE, (u64)ptr, len, 0);
}

void klet_svc_body(struct klet_svc_args *args)                /* runs on the Linux stack */
{
	struct klet_carrier *c = klet_current_carrier();

	c->depth++;                      /* "inside the host": the timer and the sweep read this */
	switch (args->op) {
	case KLET_SVC_LOG_WRITE:
		klet_do_out_write(c->inst, &c->inst->log, (const char *)args->a0, args->a1);   /* to the holder's log file, through a ring */
		break;
	case KLET_SVC_MEM_ALLOC:
		args->ret = (u64)klet_do_mem_alloc(c->inst, args->a0, args->a1);
		break;
	/* ... every other service ... */
	}
	c->depth--;
}

The endovisor finds the calling carrier from Linux’s current task and the hooks pointer in it: klet_current_carrier() is container_of(current->carrier_hooks, struct klet_carrier, hooks) (given a pointer to a field, container_of subtracts the field’s offset to get the enclosing structure). No service takes a “which kernelet” argument, so a kernelet cannot claim to be another.

The depth counter is 1 while a service body runs on the kernelet’s behalf, when the carrier may hold Linux’s locks. The endovisor’s per-processor timer and the sweep that takes a processor back from a stopped sandbox, both built later, read it, with the carrier’s state, before touching a carrier’s instruction pointer.

Two services do not simply return: user_run, which leaves the kernelet stack and does not come back until the next hook brings the carrier in, as the next chapter shows; and stop, which uses the stub like any service and then leaves forever.

Recap. Linux empties a task’s kernel stack on every return to user mode; the kernel proper keeps a loop’s frame alive across them. So kernelet code runs on kernelet stacks, 256 KiB each, from a per-sandbox pool over vmalloc, and the carrier switches between them and its Linux stack with klet_switch, a six-register coroutine switch. klet_enter hands control to the kernelet and klet_leave hands it back; every service call hops onto the Linux stack with klet_run_on_linux_stack, runs klet_svc_body there with the depth counter raised, and hops back.

Into user mode and back

Everything is now in place for the hundred-line kernel to run its program. The kernel proper’s task calls execute, which in vOSTD is the service user_run. This chapter follows that call out of the kernelet, through Linux, into user mode, and back in again on the program’s first system call. At the end the kernel prints Hello, world.

Leaving: the user_run service

UserContext::execute in vOSTD, which UserMode::execute calls, keeps OSTD’s signature and loop: where OSTD enters user mode with its own assembly and decodes the trap number, vOSTD calls user_run with a pointer to the context, and interprets the number it returns.

Simplified from prototype/vostd/src/arch/cpu/context.rs: execute.

fn execute<T: UserModeHooks>(&mut self, hooks: &T) -> ReturnReason {
    self.user_context.general.rflags |= RFLAGS_IF | RFLAGS_ID;
    loop {
        match self.user_context.run() {         // the user_run service
            0 => return ReturnReason::UserSyscall,
            1 => {
                self.exception = CpuException::new(trap_num, error_code, fault_addr);
                return ReturnReason::UserException;
            }
            _ => {                              // 2: something to look at, then try again
                crate::vcpu::deliver_no_switch();
                if hooks.has_kernel_event() { return ReturnReason::KernelEvent; }
            }
        }
    }
}

So user_run returns 0 for a system call, 1 for an exception and 2 for “an event happened; the kernel may want to know, then call me again”. The third case is how a virtual interrupt reaches the kernel while its program runs.

The context it is given is a RawUserContext: the eighteen registers of chapter 3, in a fixed order, followed by three fields for exceptions.

On the endovisor’s side, user_run is the one service that does not use the stub of the last chapter. It records the context, switches to the Linux stack, and does not come back until a hook brings the carrier into the kernelet again:

Simplified from prototype/linux/endovisor/carrier.c: klet_svc_user_run.

static u64 klet_svc_user_run(struct klet_user_ctx *ctx)
{
	struct klet_carrier *c = klet_current_carrier();

	c->ctx = ctx;                               /* where the registers are, and where to put them later */
	WRITE_ONCE(c->state, KLET_USER);            /* "in, or on the way to, user mode" */
	smp_mb();                                   /* the state is published before the pending word is read: see virtual interrupts */
	if (atomic_read(&c->vrec.pending)) {        /* a virtual interrupt arrived meanwhile */
		WRITE_ONCE(c->state, KLET_RUNNING);
		return KLET_RUN_EVENT;
	}
	klet_mirror_out(c, false);                  /* give Linux its preemption count back: the mirror, built later */
	klet_switch(&c->coro_sp, c->linux_sp);      /* to the Linux stack, inside whichever hook entered us */
	return c->run_ret;                          /* ... much later, with the reason the hook recorded */
}

The switch lands inside the klet_enter that last entered the kernelet on this carrier, which returns into its caller. That caller is always one of the two hooks: on the very first trip it is the resume hook, running on the carrier’s way out of the execveat that made it (chapter 6), and on every later trip it is whichever hook brought the carrier in.

Putting the registers where Linux will find them

Whoever klet_enter returns into now has one job: copy the context into the carrier’s pt_regs, so that when Linux returns to user mode, it returns to the tenant’s program.

Simplified from prototype/linux/endovisor/carrier.c: klet_ctx_to_regs.

static void klet_ctx_to_regs(struct klet_carrier *c, struct pt_regs *regs)
{
	struct klet_user_ctx *x = c->ctx;

	regs->ax = x->rax; regs->bx = x->rbx; regs->cx = x->rcx; regs->dx = x->rdx;
	regs->si = x->rsi; regs->di = x->rdi; regs->bp = x->rbp; regs->sp = x->rsp;
	regs->r8 = x->r8;  /* ... through r15 ... */
	regs->ip = x->rip;
	regs->flags = (x->rflags & KLET_RFLAGS_USER) | X86_EFLAGS_IF | X86_EFLAGS_FIXED;
	regs->cs = __USER_CS;
	regs->ss = __USER_DS;
	regs->orig_ax = -1;      /* no system call in progress: Linux must not try to restart one */
}

Three details keep this safe. The flags are sanitized: the interrupt-enable bit is forced on and the privilege-level bits are cleared, so a tenant cannot talk its kernel into giving it a program that runs with interrupts off. The code and stack segment selectors are fixed to Linux’s user segments. And orig_ax, Linux’s record of which system call is in progress, is set to -1, which switches off Linux’s system-call restart logic; restarting is the kernel proper’s business.

The first trip needs nothing special. The carrier arrived by a system call, so the registers Linux will restore are the pt_regs of that call, and the resume hook overwrites them as it will on every later trip; the registers the exec had prepared for the carrier’s own program, which does not exist, are simply never used.

Coming back by a system call

The tenant runs, and executes syscall. Linux saves its registers in pt_regs, finds the task’s hooks, and calls the syscall hook:

Simplified from prototype/linux/endovisor/carrier.c: klet_on_syscall, klet_regs_to_ctx.

static bool klet_on_syscall(struct pt_regs *regs)
{
	struct klet_carrier *c = klet_current_carrier();

	if (c->state != KLET_USER || !c->ctx)
		return false;                           /* not a carrier in user mode: not ours */
	if (regs->cs != __USER_CS || in_compat_syscall()) {
		/* a 32-bit entry instruction: report roughly what a machine would raise, a #GP (general-protection fault) */
		c->exc_trap = X86_TRAP_GP; c->exc_pending = true;
		set_thread_flag(TIF_NOTIFY_RESUME);
		return true;
	}

	klet_regs_to_ctx(c, regs);                  /* pt_regs -> the kernelet's context */
	c->user_live = false;                       /* the context is now the authority on the registers */
	regs->orig_ax = -1;
	klet_enter(c, KLET_RUN_SYSCALL);            /* run the kernelet: user_run returns 0 there */

	/* ... the kernelet handled the call and called user_run again ... */
	if (c->state == KLET_USER) {
		klet_space_adopt(c, c->vrec.space);     /* the right address space: built with tenant memory */
		klet_ctx_to_regs(c, regs);              /* its new registers */
		c->user_live = true;                    /* from here on pt_regs is the authority, until the next hook */
	} else {
		klet_carrier_die(c);                    /* the kernelet stopped instead */
	}
	return true;                                /* Linux: do not dispatch this call */
}

static void klet_regs_to_ctx(struct klet_carrier *c, struct pt_regs *regs)
{
	x->rax = regs->orig_ax;                     /* the call number as issued; ax itself holds -ENOSYS by now */
	x->rbx = regs->bx; /* ... every register ... */ x->rip = regs->ip; x->rflags = regs->flags;
	x->trap_num = 0; x->error_code = 0; x->fault_addr = 0;
}

The klet_enter in the middle of the hook runs the kernel proper’s whole handling of the call. klet_enter switches to the kernelet stack, where user_run is waiting inside klet_switch; user_run returns 0; execute returns UserSyscall; the kernel proper’s loop handles the call and calls execute again; user_run switches back to the Linux stack, which lands here, just after klet_enter. Then the hook copies the kernelet’s new registers out, returns true, and Linux returns to user mode with them, skipping its own system-call table entirely.

The kernel proper sees exactly the registers it would see on a machine. The syscall instruction itself overwrites two registers on the way in: it puts the return address in rcx and the flags in r11. pt_regs holds them as the instruction left them, and the call number is in orig_ax, where Linux’s entry code put it.

Note what the sequence does not say: that the task which comes back is the one that left. Between the two switches the kernelet’s own scheduler may have run another task, and then it is that task’s execute that leaves, with another thread’s registers. Nothing in Linux’s exit path minds, because everything Linux will restore from the stack is in pt_regs, and the hook overwrites all of it.

The thread-pointer base is not in pt_regs, so in the prototype every tenant thread on a carrier shares the carrier’s. A program keeps a pointer to its thread’s private variables in a segment register (%fs on x86-64), and Linux saves that register’s base per task, in its own record, not on the stack. The prototype’s context carries no such base; a full vOSTD would carry one per thread and have the endovisor set it on each trip.

Coming back by an exception

A tenant’s fault must reach the kernel proper as execute returning UserException, with the trap number and, for a page fault, the address. A tenant’s instruction can fault: divide by zero, an illegal instruction, a touch of an address with no mapping. On a machine, OSTD’s trap handler would fill those in from the hardware.

Linux: exceptions become signals. When a user instruction faults, Linux’s exception handler records the trap number, error code and address in the task’s thread structure, queues a signal on the task (SIGSEGV, SIGILL, SIGFPE, and so on) with force_sig(), and heads for user mode. For a fault, Linux’s handlers queue the signal with force_sig_fault(), whose si_code says what kind of fault it was.

Signals are acted on in the exit loop: Linux either kills or stops the task or arranges for a handler in the program to run. Two signals cannot be caught or blocked: SIGKILL and SIGSTOP.

The endovisor takes the signals off the queue itself, in the resume hook, which runs at the top of that loop before Linux delivers anything:

Simplified from prototype/linux/endovisor/carrier.c: klet_drain_signals.

static bool klet_drain_signals(struct klet_carrier *c)
{
	sigset_t mask = current->blocked;
	sigaddset(&mask, SIGKILL);                  /* the two signals nobody may take are left in the queue, */
	sigaddset(&mask, SIGSTOP);
	/* ... and so is any signal Linux has made fatal and immutable (SA_IMMUTABLE): a seccomp kill's SIGSYS */

	spin_lock_irq(&current->sighand->siglock);
	while ((signr = dequeue_signal(&mask, &info, &type)) != 0) {
		spin_unlock_irq(&current->sighand->siglock);
		if (!sig_kernel_only(signr))            /* Linux forced it, un-ignoring it on the way: ignore it again */
			kernel_sigaction(signr, SIG_IGN);   /* (which takes the lock itself) */
		if (klet_is_fault_signal(signr, info.si_code) && !exception) {   /* raised by a trap handler for this task's own fault */
			c->exc_trap = current->thread.trap_nr;
			c->exc_error = current->thread.error_code;
			c->exc_addr = (unsigned long)info.si_addr;
			c->exc_pending = true;
			exception = true;
		}
		/* anything else Linux forced (a seccomp trap's SIGSYS) is dropped */
		spin_lock_irq(&current->sighand->siglock);
	}
	spin_unlock_irq(&current->sighand->siglock);
	return exception;
}

A fault signal is recognized by its number and its si_code together. The number is one of SIGSEGV, SIGBUS, SIGILL, SIGFPE and SIGTRAP, and the code is one a trap handler uses: positive, and below SI_KERNEL, the code Linux puts on signals it sends on its own account. Four more signals are accepted with SI_KERNEL, because some of x86’s trap handlers have no finer code to give and send SI_KERNEL themselves (arch/x86/kernel/traps.c): SIGSEGV for a general-protection fault, an invalid task-state segment, an overflow trap (int 4), a bounds-check fault from 32-bit code, and the fault a processor raises on a disabled extended-state feature; SIGBUS for a segment-not-present and a stack fault; SIGTRAP for a breakpoint (int3); and SIGFPE for the coprocessor segment overrun that no current processor raises. In the extended-state case the trap number Linux left in the thread structure is stale, and the kernel proper sees whatever the last exception was. No process can forge that code, since kill sends SI_USER.

Every other signal the drain finds is discarded, with one exception left for Linux. A signal sent by a process is dropped: on the host side that is a process allowed to signal the carrier, since a tenant’s kill is a system call and the syscall hook takes those. So is a signal Linux sends for a reason of its own, once a fault has reset its action. One kind is left alone: a signal Linux has made fatal and marked immutable, which is what a seccomp filter’s kill action does to its SIGSYS; the drain leaves it in the queue, Linux delivers it on the same pass, and the carrier’s death ends the sandbox.

SIGKILL and SIGSTOP are left in the queue. The first is how the operator and the endovisor end a carrier, and Linux acts on it in the same loop. The second takes effect at the carrier’s next return to user mode, where Linux stops it as it stops any task; a stopped carrier is a stopped virtual CPU until SIGCONT, and a virtual CPU that does not return to user mode, because it is idle or runs only kernel tasks, keeps running with the stop pending.

Most signals never reach the queue at all, and that is arranged earlier. The binary-format handler of chapter 6 sets every signal but SIGKILL and SIGSTOP, which cannot be, to be ignored, and clears the signal mask, in every carrier, since each arrives by an exec of its own. An ignored signal is discarded the moment it is sent, so an operator’s SIGTERM, SIGQUIT or SIGTSTP to a carrier does nothing.

The drain alone would not do, for two reasons. A signal whose default action is to end the task without a core dump, SIGTERM, SIGINT, SIGPIPE and their kind, is fatal at the moment it is sent: the sender sees that nothing will catch it and turns it into a SIGKILL on the spot (complete_signal()), before any drain. And the drain runs at the top of one pass of the exit loop, while Linux delivers signals later in the same pass if one was pending when the pass began, so a SIGQUIT that arrived between the two would dump core and end the carrier.

The fault signals are ignored too, and still arrive. Linux sends a fault with force_sig_info_to_task(), which first sets an ignored signal back to its default action, so the signal is queued and the drain sees it. The drain then ignores it again, so that the next fault is forced the same way and a SIGSEGV a process sends in between is discarded.

The resume hook brings the exception into the kernelet:

Simplified from prototype/linux/endovisor/carrier.c: klet_on_resume.

static void klet_on_resume(struct pt_regs *regs)
{
	struct klet_carrier *c = klet_current_carrier();

	for (;;) {
		if (c->state == KLET_DEAD || c->inst->stopped || c->inst->dying) {
			klet_carrier_die(c);                                 /* stopping a kernelet, later */
			return;
		}
		if (c->state == KLET_NEW) {                              /* the first time, out of the exec: wait for the sandbox's start, then enter (chapter 6) */
			if (!klet_vcpu_await(c)) { klet_carrier_die(c); return; }
			klet_enter(c, KLET_RUN_EVENT);
			continue;
		}
		if (c->state == KLET_USER && !c->exc_pending && klet_drain_signals(c) && c->user_live) {
			klet_regs_snapshot(c, regs);                         /* the faulting registers, into ctx */
			c->user_live = false;                                /* ctx is the authority again */
		}
		if (c->exc_pending) {                                    /* from a signal, or from the endovisor's own fault handler, later */
			c->exc_pending = false;
			if (c->state == KLET_USER && c->user_live) {
				klet_regs_snapshot(c, regs);                     /* same: ctx must hold the registers of the faulting instruction */
				c->user_live = false;
			}
			klet_ctx_set_exception(c);                           /* trap, error code, address -> ctx */
			klet_enter(c, KLET_RUN_EXCEPTION);                   /* user_run returns 1 */
			continue;
		}
		if (atomic_read(&c->vrec.pending)) {                     /* a virtual interrupt: the next chapter but one */
			if (c->state == KLET_USER && c->user_live) {
				klet_regs_snapshot(c, regs);                     /* the interrupted registers, into ctx */
				c->user_live = false;
			}
			klet_enter(c, KLET_RUN_EVENT);                       /* user_run returns 2 */
			continue;
		}
		if (c->state == KLET_USER && c->user_live)               /* nothing for the kernelet, and the tenant's registers */
			return;                                              /* are live in pt_regs: work of Linux's own brought us here */
		/* KLET_USER with a context the kernelet has just handed over: it wants user mode */
		klet_space_adopt(c, c->vrec.space);
		klet_ctx_to_regs(c, regs);
		c->user_live = true;
		return;
	}
}

The loop shape matters: each klet_enter returns when the kernelet calls user_run again, and the hook then goes around once more to see whether anything else is pending before it finally applies the registers and returns to Linux.

Before an exception is reported, by either route, the hook copies the current pt_regs into the context, so that the kernel proper sees the faulting instruction’s registers. The copy, klet_regs_snapshot, is needed because the context still holds the registers of the previous trip. user_live says which of the two copies is the authority: it is set when the context is applied to pt_regs, and cleared when pt_regs is copied back into the context, by the syscall hook or by a snapshot; so the snapshot is taken exactly once per trip, and never over registers the kernelet has already seen.

The same flag keeps the hook from rewinding a tenant when it runs for Linux’s own work. The exit loop runs the hook for work of Linux’s own as well, a reschedule, a signal the drain dropped, a stop and a continue, and then nothing is pending for the kernelet and the registers in pt_regs are the tenant’s live ones. Applying the context over them would send the tenant back to the return of its last system call, a rewind of everything it had done since, so the hook leaves them alone and returns. The hook therefore runs for every kind of exit work, not only the kernelet’s, and is written to find nothing of its own to do.

One of the memory tests, make mem-kill, runs a tenant that keeps a count in a register and the same count in memory and reports the first moment they part, while it is preempted, signaled, and stopped and continued.

Page faults on tenant memory take a shorter path through the endovisor’s own fault handler, which sets exc_pending directly, as the chapter on tenant memory shows. What the kernel proper sees is the same in both cases: execute returns UserException, with a CpuException::PageFault carrying the address.

Tasks and virtual CPUs

This chapter gives the kernelet what a real kernel has: thousands of tasks and a scheduler that decides which runs where. The hundred-line kernel has one task. A real kernel has a thread per tenant process, kernel threads for its own work, and a scheduler over them all. The chapter is shorter than you might expect, because the kernelet brings its own.

Two levels

The design has two levels. Linux schedules a sandbox’s virtual CPUs, a handful per sandbox, and knows nothing else about it. On each virtual CPU, the kernelet’s own scheduler decides which kernelet task runs, for how long, and what preempts what.

A virtual CPU is one of the processors a sandbox is given when it is created; a carrier carries one of them for the sandbox’s whole life. Whatever the virtual CPU does, that Linux task does it: it runs the kernelet’s tasks one after another, enters user mode for whichever tenant thread the kernelet picked, and sleeps in Linux when the virtual CPU has nothing to run. Which physical processor the carrier is on is Linux’s business and changes without notice; the virtual CPU moves with it.

The kernelet’s tasks are its own

vOSTD’s task layer is the real OSTD’s code: a task is a function, a stack and a saved register set; switching tasks saves one set of callee-saved registers and loads another; waiting is a matter of OSTD’s own wait queues. None of it involves Linux, which never sees a kernelet task at all. The two places where the machine shows through are the stack and the context switch, and both are familiar from chapter 7.

Simplified from prototype/vostd/src/task/mod.rs and prototype/vostd/src/task/kernel_stack.rs: build, KernelStack.

pub fn build(self) -> Result<Task> {
    let kstack = KernelStack::new_with_guard_page()?;          // the kstack_alloc service
    let mut ctx = TaskContext::new();
    ctx.set_instruction_pointer(kernel_task_entry_wrapper as usize);   // where the first switch lands
    ctx.set_stack_pointer(kstack.end_vaddr() - 16);
    Ok(Task { func: ..., data: ..., ctx, kstack, ... })
}

impl KernelStack {
    pub(super) fn new_with_guard_page() -> Result<Self> {
        let base = unsafe { (svc().kstack_alloc)() } as Vaddr;  // from the endovisor's pool
        if base == 0 { return Err(Error::NoMemory); }
        Ok(Self { base, size: KERNEL_STACK_SIZE })
    }
}

The context switch is OSTD’s switch.S, byte for byte: save eight words (the stack pointer, six callee-saved registers and the return address), load eight, return on the other stack. It is the same idea as the endovisor’s klet_switch, written on the Rust side, and it switches between two kernelet stacks, which is why the endovisor neither sees nor cares which of the kernelet’s tasks is current. The endovisor remembers only where the kernelet was when it last left, and resumes there.

The kernel proper chooses the policy. It implements OSTD’s Scheduler trait, a run queue per CPU with enqueue, pick_next and update_current, and registers it with inject_scheduler before it creates any task; OSTD calls those functions without knowing the type, which is how a scheduler written for a bare-metal kernel runs unchanged in a kernelet. If the kernel proper registers none, OSTD’s own first-in-first-out scheduler is used, which is what the hundred-line kernel gets.

A test shows that the policy is the kernelet’s and not Linux’s. The test kernel in prototype/kernels/sched/src/lib.rs injects a strict-priority scheduler with round-robin inside each level, a policy that Linux’s fair scheduler, under which every carrier runs, would never produce, and the test make sched-policy checks every one of its switches against a model of the policy.

The virtual CPU record

A carrier and the kernelet need a small amount of shared state per virtual CPU, and they need the kernelet to find it fast, since “which CPU am I on” is on the hottest path a kernel has. The virtual CPU record is that state: a C-layout structure the endovisor owns and both sides write.

Simplified from prototype/linux/endovisor/kernelet.h: klet_vcpu_rec.

struct klet_vcpu_rec {
	u32 vcpu_id;            /* which virtual CPU this is: CpuId::current() reads it */
	u32 nr_vcpus;
	atomic_t pending;       /* virtual interrupts raised and not yet taken: the next chapter */
	u32 preempt_info;       /* OSTD's preemption word: guard count and need-preempt bit */
	u32 irq_off;            /* the virtual interrupt flag, inverted */
	u32 mirrored;           /* the mirror of Linux's preemption count, two chapters on */
	u64 virq_ip;            /* where an upcall interrupted the kernelet: the next chapter */
	u64 space;              /* the tenant address space this vCPU has activated: see tenant memory */
	u64 stack_limit;        /* the bottom of the current task's kernelet stack */
	u64 stolen_ns;          /* how long Linux kept this vCPU off a processor */
};

The record’s place is what makes it fast to find: it is embedded in the endovisor’s per-carrier structure, directly after the table of hooks that task_struct points at.

Linux: per-processor data and %gs. Linux keeps a block of per-processor variables, and on x86-64 the segment register %gs points at the current processor’s block, so that reading one of them is a single mov with a %gs: prefix, whichever processor the code is on. Two of those variables matter here: the pointer to the current task, and the preemption count, the nesting depth of preempt_disable(), which Linux raises around code that must not be preempted. The block’s layout is Linux’s own, so a module learns the offsets at run time.

When a sandbox starts, the endovisor publishes the offsets that lead from %gs to the record. It computes the %gs-relative offset of the current-task pointer, checks it by reading the pointer back and comparing it with current, and publishes it in the boot arguments together with the offset of the hooks pointer inside task_struct, the offset of the record from the hooks, and the offset of Linux’s preemption count. vOSTD then finds its record with two dependent loads and no call:

Simplified from prototype/vostd/src/vcpu.rs: vrec.

pub(crate) fn vrec() -> &'static VcpuRec {
    let task: usize;
    unsafe { asm!("mov {t}, gs:[{o}]", t = out(reg) task, o = in(reg) GS_CURRENT_TASK) };
    let hooks = unsafe { core::ptr::read((task + TASK_HOOKS_OFF) as *const usize) };
    unsafe { &*((hooks + HOOKS_VREC_OFF) as *const VcpuRec) }
}

The two loads are right even if the carrier moves between them: whichever processor the carrier is on, %gs names that processor’s block, the block’s current task is this carrier, and this carrier’s hooks lead to this virtual CPU’s record.

Everything OSTD keeps per CPU, such as the scheduler’s run-queue locks and the timer callbacks, is in vOSTD an array with one slot per virtual CPU, indexed by the vcpu_id in the record. The one per-CPU word that must be updated with single instructions, OSTD’s preemption word (a guard count and a need-preempt bit meaning “switch tasks at the next chance”), lives in the record itself, for a reason the next chapter gives.

Starting, idling, kicking

A machine’s processors are started at boot, halted when idle, and interrupted when another processor wants their attention. A virtual CPU does the same three things through three services.

Starting

Virtual CPU 0 starts with the sandbox, and the others start when the kernel proper asks for them, as secondary processors do on a machine. The carrier of virtual CPU 0 enters the image at kernelet_entry. The others wait in the resume hook’s first trip (chapter 6) until the kernel proper, as it would on a machine, registers an entry function for the secondary processors with register_ap_entry. vOSTD then calls vcpu_boot(i) for each, the endovisor wakes the waiting carrier, and it enters the image at vcpu_entry, runs the registered function, and falls into the idle loop below.

Idling

A virtual CPU with nothing to run calls vcpu_idle, and its carrier sleeps in Linux until something is pending. Spinning would burn the sandbox’s share of a real processor for nothing. The sleep is killable, so that SIGKILL ends it, which is how a sandbox is stopped.

Simplified from prototype/linux/endovisor/carrier.c: klet_do_vcpu_idle.

static void klet_do_vcpu_idle(struct klet_carrier *c, u64 deadline_ns)
{
	set_current_state(TASK_KILLABLE | TASK_FREEZABLE | TASK_NOLOAD);   /* 1. announce the sleep: killable, may be frozen for suspend, not counted in the load average */
	WRITE_ONCE(c->idle, true);                            /* 2. mark the vCPU idle */
	smp_mb();
	if (!atomic_read(&c->vrec.pending) && !inst->dying)   /* 3. only then look */
		schedule_hrtimeout(&timeout, HRTIMER_MODE_REL);   /*    and sleep, at most until the deadline */
	__set_current_state(TASK_RUNNING);
	WRITE_ONCE(c->idle, false);
	atomic_or(KLET_VIRQ_TICK, &c->vrec.pending);          /* time passed: the timer callbacks are owed a run */
}

The order of the first three lines is the one every Linux sleep uses so that no wake-up is lost: the sleeper marks itself, then checks; the waker sets the bit, then checks the mark. One of the two always sees the other.

The scheduler’s code shows where both of the remaining services are called: reschedule idles this virtual CPU when its run queue is empty, and set_need_preempt kicks another. reschedule takes the scheduling decision as a closure, so that yield_now, park_current and the others share its loop and differ only in the decision.

fn reschedule<F>(mut f: F)                       // the heart of every scheduling decision
where F: FnMut(&mut LocalRunQueue) -> ReschedAction {
    open_resched_window();                       // clears need-preempt; the next chapter says what else it does
    let next_task = loop {
        match f(local_run_queue) {
            ReschedAction::DoNothing => return,
            ReschedAction::Retry => {            // nothing runnable here
                spins += 1;
                if spins >= IDLE_SPINS { crate::vcpu::idle(0); } else { spin_loop(); }
            }
            ReschedAction::SwitchTo(next) => break next,
        }
    };
    processor::switch_to_task(next_task);
}

Retry means the run queue is empty: the virtual CPU spins a little, in case a sibling is about to enqueue something, and then calls vcpu_idle (a deadline of zero means at most one millisecond, the length of a tick). When the sleep ends, vcpu_idle has marked a tick pending, so the timer callbacks run, the closure runs again, and either finds a task or sleeps again.

Kicking

When the kernelet’s scheduler puts a task on another virtual CPU’s run queue, that virtual CPU should notice soon, as a machine would be told by an inter-processor interrupt. vOSTD calls vcpu_kick(i), which sets a KICK bit in the target’s record and does whichever of three things gets it seen: wakes the carrier if it is asleep in vcpu_idle, flags it if it is in user mode, or, if it is running kernelet code on another processor right now, sends that processor an interrupt that makes the kick be delivered at once instead of at the watch timer’s next tick. set_need_preempt above is where the scheduler calls it.

One carrier, many threads

A carrier runs many tenant threads in turn, so two things a thread owns must change with it: its address space and its floating-point and vector registers.

A virtual CPU runs the threads of many tenant processes in turn, and each process has its own address space. The kernel proper, as on a machine, activates the right VmSpace before it runs a thread; in vOSTD, activate records the space in the virtual CPU’s record (the space field above), and the carrier switches to that process’s Linux address space on its next trip to user mode. The switch itself is klet_space_adopt, which the chapter on tenant memory builds, and which both hooks of chapter 8 call just before they apply the registers.

The floating-point and vector registers belong to a tenant thread too. To Linux they are the carrier’s user state: Linux saves them when it switches the carrier out and restores them, lazily, before the carrier next returns to user mode, and it does not know that the kernelet has put a different thread on the carrier in between.

OSTD already has the type for a thread’s own copy, FpuContext, which the kernel proper saves when a thread leaves user mode and loads before it returns. vOSTD implements its save and load with two services, fpu_save and fpu_load. Each first makes the registers live, if Linux had deferred restoring them, and then executes the same xsave or xrstor instruction a machine would.

The instruction never touches the kernelet’s buffer directly. xrstor reads a header from the buffer and acts on it, and the kernelet’s buffer may lie in a frame that the kernelet has also mapped into a tenant, which could rewrite it between a check and the instruction. So the endovisor copies the buffer to a page of its own, validates the copy, and runs the instruction on that.

Recap. Linux schedules a sandbox’s virtual CPUs, each carried by one Linux task; on each, the kernelet’s own scheduler, injected by the kernel proper, picks which kernelet task runs. Tasks, stacks and the context switch are OSTD’s own code; only the stack memory comes from the endovisor. Each virtual CPU has a record that vOSTD finds through Linux’s per-processor current-task pointer in two loads. A virtual CPU is started with vcpu_boot, sleeps in Linux with vcpu_idle under a lost-wake-up-proof protocol, and is prodded with vcpu_kick.

Virtual interrupts

The kernelet’s scheduler needs interrupts, and Linux leaves it none; this chapter gives it virtual ones. A time slice ends because a timer interrupt fires, and a wake-up on another processor is noticed because an interrupt arrives there. But Linux owns the interrupt controller, the vector table and every physical line, and nothing in vOSTD can register a handler for any of them.

Bits in a record

A virtual interrupt is a bit in the pending word of a virtual CPU’s record (chapter 9). The endovisor sets it from interrupt context or from another processor. The kernelet’s handler for it runs as kernelet code on that virtual CPU’s carrier, never in Linux’s interrupt context, soon after. Two bits are raised in this prototype; a third, LINES, is reserved for devices:

TICKthis processor’s watch period (the watch timer’s one-millisecond period, below) expired while this carrier was current; also raised whenever the virtual CPU wakes from vcpu_idlethe watch timer, below; vcpu_idle on waking
KICKanother virtual CPU wants this one to look at its run queuethe vcpu_kick service

Each bit stands in for a hardware interrupt the kernel proper already handles. The kernel proper’s timer callbacks, functions it registers with OSTD to run on every timer interrupt, run from TICK as they would from a hardware timer interrupt. One of them, registered by OSTD when the kernel proper calls enable_preemption_on_cpu, calls the injected run queue’s update_current(Tick) and sets need-preempt, a bit in OSTD’s preemption word meaning switch tasks at the next chance, if the run queue asks for it. KICK does what a reschedule interrupt does on a machine: it makes the virtual CPU ask its scheduler whether something more urgent has become runnable.

vOSTD computes the kernelet’s jiffies, its count of ticks since boot, from the cycle counter rather than by counting ticks, because a virtual CPU that Linux has not scheduled gets none.

When the handler runs depends on what the virtual CPU is doing when the bit is set, and above all on whether it is in a critical section. A virtual CPU is in a critical section when the kernelet task on it holds at least one preemption guard or spin lock, or has its virtual interrupts masked. The chapter’s closing section lists the paths by which a bit reaches its handler; each path has a section of its own first.

The watch timer

Linux: high-resolution timers and preemption notifiers. An hrtimer is a timer whose callback runs in interrupt context, normally on the processor that armed it. A pinned timer is guaranteed to stay there. A hard one runs in the interrupt itself even on a real-time kernel, a kernel built to run most interrupt work in threads. A callback returns HRTIMER_RESTART to run again, after moving its expiry forward by whole periods past now with hrtimer_forward_now(), or HRTIMER_NORESTART to stop. hrtimer_active() says whether a timer is queued or its callback is running, hrtimer_cb_get_time() gives the time a callback runs at, and hrtimer_set_expires() sets the next expiry directly.

A timer callback can make the interrupted code resume somewhere else. The timer interrupt publishes the registers of whatever it interrupted, and a callback reads them with get_irq_regs(), which is how Linux’s profiler samples programs; a callback that changes the saved instruction pointer makes the interrupt return somewhere else.

A preemption notifier (preempt_notifier_register()) is a pair of callbacks Linux runs for one task every time it switches that task out of a processor and in to one; KVM, Linux’s own hypervisor, uses it to load a virtual CPU’s state onto the processor it is switched in on and to save it when it is switched out. Notifiers are compiled in only if another configuration option requires them (CONFIG_PREEMPT_NOTIFIERS cannot be turned on by itself); the patch’s CONFIG_KERNELET requires it.

The watch timer, a pinned, hard, one-millisecond hrtimer on each processor, is armed while the task running there is the carrier of a virtual CPU, and for at most one more period after it leaves. Each carrier registers a preemption notifier when it starts. The notifier’s switch-in callback arms the timer of whatever processor the carrier has just landed on, and so does every entry into kernelet code and every return from a service, which no switch-in need precede. The timer’s own callback re-arms itself if it interrupted the carrier of a virtual CPU of a live sandbox, and stops otherwise. So a carrier that Linux migrates is watched wherever it lands, and a processor that has no carrier is soon unwatched.

Every time a period expires, the callback raises TICK and then decides how to deliver whatever is pending:

Simplified from prototype/linux/endovisor/watch.c: klet_watch_fn.

static enum hrtimer_restart klet_watch_fn(struct hrtimer *timer)
{
	struct pt_regs *regs = get_irq_regs();      /* the interrupted registers; NULL if whatever ran this callback did not publish them */
	struct klet_carrier *c;
	bool tick = true;

	if (this_cpu_read(klet_watch_requested)) {  /* a kick asked for this firing (below): it counts as a tick only if the period it cut short has run out */
		this_cpu_write(klet_watch_requested, false);
		tick = !ktime_before(hrtimer_cb_get_time(timer), this_cpu_read(klet_watch_period_end));
	}

	if (!current->carrier_hooks)                     /* not a carrier any more: stop */
		return HRTIMER_NORESTART;
	c = klet_current_carrier();

	if (tick)
		klet_virq_raise(c, KLET_VIRQ_TICK);     /* 1. the tick */

	if (!regs || user_mode(regs) || !klet_in_image_text(regs->ip) || !klet_in_kernelet(c)) {
		/* no registers, user mode (klet_virq_raise flagged the carrier), a service, or Linux: leave it pending */
	} else if (!klet_critical(c)) {
		klet_virq_redirect(c, regs);            /* 2. in kernelet code, not in a critical section: deliver now */
	} else {
		/* in a critical section: the kernelet delivers it itself when the section ends */
	}
	/* 3. the bound on critical sections: the next chapter */

	if (!tick) {                                /* a requested firing goes back to its period's own expiry */
		hrtimer_set_expires(timer, this_cpu_read(klet_watch_period_end));
		return HRTIMER_RESTART;
	}
	hrtimer_forward_now(timer, ns_to_ktime(KLET_WATCH_INTERVAL_NS));
	return HRTIMER_RESTART;
}

The callback’s two tests keep it from redirecting anything but kernelet code. klet_in_image_text asks whether the interrupted instruction lies in the kernelet image’s code; Linux’s code and the endovisor’s never do. klet_in_kernelet asks whether the carrier is running kernelet code and not a service: state RUNNING, depth 0, not asleep in vcpu_idle, and not evicted, that is, not already being forced out of kernelet code by the endovisor, as happens when the sandbox is being stopped. A carrier inside a service call is never redirected, because it may hold Linux’s locks.

klet_virq_raise sets the bit and does the two cheap things that get it noticed. It wakes the carrier if it is asleep in vcpu_idle. It flags the carrier (chapter 6) if it is in user mode, so that it comes back through the resume hook and user_run returns 2.

When the carrier is in kernelet code outside a critical section, the endovisor delivers at once, as a machine would, by changing one saved register:

Simplified from prototype/linux/endovisor/watch.c: klet_virq_redirect.

bool klet_virq_redirect(struct klet_carrier *c, struct pt_regs *regs)
{
	if (user_mode(regs) || !klet_in_image_text(regs->ip) || !klet_in_kernelet(c))
		return false;
	if (klet_irq_off(c))                         /* interrupts masked: wait */
		return false;
	limit = READ_ONCE(c->vrec.stack_limit);
	if (!limit || regs->sp < limit || regs->sp - limit < KLET_UPCALL_HEADROOM)
		return false;                            /* no limit published, or not enough stack for the handler */

	WRITE_ONCE(c->vrec.virq_ip, regs->ip);       /* where we interrupted the kernelet */
	WRITE_ONCE(c->vrec.irq_off, 1);              /* mask, as hardware clears IF when it takes an interrupt */
	regs->ip = (unsigned long)kernelet_entry_table.virq_entry;   /* return there instead */
	return true;
}

The redirect is refused when interrupts are masked or when the task’s kernelet stack has too little room. vOSTD publishes each task’s stack limit at every task switch. The endovisor requires 32 KiB below the interrupted stack pointer (KLET_UPCALL_HEADROOM): 16 KiB for the upcall and the callbacks it runs, and 16 KiB reserved for Linux, which runs on whatever stack it interrupts until it switches to its interrupt stack, runs its scheduler there when it preempts the carrier on the way out of an interrupt, and runs the whole handler of a kernel-mode exception there.

The upcall

When the timer interrupt returns, it lands not on the interrupted instruction but in the kernelet’s upcall stub: the kernelet’s own interrupt handler, which only a redirected interrupt enters.

The stub, in vOSTD’s assembly, saves everything on the current task’s kernelet stack, calls a Rust function, and returns to the interrupted instruction. It is assembly because it is entered between two arbitrary instructions and must put every general register and the flags back exactly.

Two build settings keep the stub short. The kernelet is built without vector instructions, so there is no vector state to save. The kernelet, like Linux, is compiled without a red zone, the 128 bytes below the stack pointer that user-mode code may use without moving it, so the stub may push below the interrupted rsp.

The excerpt is in Intel syntax, destination first, as Rust’s global_asm! has it; chapter 7’s switch was in AT&T syntax, the GNU assembler’s default, source first.

Simplified from prototype/vostd/src/vcpu.rs: klet_virq_entry, klet_virq_body.

klet_virq_entry:
    lea rsp, [rsp - 8]       ; a slot for the interrupted instruction pointer (lea, not sub: sub would change the flags)
    pushfq                   ; the flags, exactly as the interrupted code left them
    push rax ... push r15    ; every general register but rsp
    mov rbp, rsp
    and rsp, -16             ; align for the call
    call klet_virq_body      ; returns the instruction pointer to resume at
    mov rsp, rbp
    mov [rsp + 128], rax     ; into the slot: 15 registers and the flags (128 bytes) above rsp
    pop r15 ... pop rax
    popfq
    ret                      ; to the interrupted instruction

extern "C" fn klet_virq_body() -> u64 {
    let rec = vrec();
    let ip = unsafe { read_volatile(rec.virq_ip.get()) } as usize;   // copied to this frame first: the record's field may be reused
    assert!(IMAGE_TEXT_LO <= ip && ip < IMAGE_TEXT_HI);   // never resume at an address the host made up

    let owns_mirror = get_guard_count() == 0;            // this upcall begins a critical section of its own
    if owns_mirror { host_preempt_inc(); }               // the mirror of the next chapter: tell Linux so

    run_handlers(rec);                                   // TICK: the timer callbacks; KICK: a look at the run queue

    let host_wants_cpu = if owns_mirror { host_preempt_dec_and_test() } else { false };
    unsafe { write_volatile(rec.irq_off.get(), 0) };     // unmask: what a machine's interrupt return would do
    if host_wants_cpu { host_yield(); }                  // Linux was waiting for this processor
    if get_guard_count() == 0 {                          // kernel-mode preemption: switch if the scheduler wants to
        crate::task::scheduler::might_preempt();
    }
    ip as u64
}

fn run_handlers(rec: &VcpuRec) {
    loop {
        let pending = rec.pending.swap(0, Ordering::AcqRel);
        if pending == 0 { break; }
        if pending & VIRQ_TICK != 0 { crate::timer::call_timer_callback_functions(); }
        if pending & VIRQ_KICK != 0 { cpu_local::set_need_preempt(); }
    }
}

The check against the image’s text range catches a bug in the endovisor’s bookkeeping, so that a wrong address stops the kernelet instead of being jumped to. The host is trusted, so this is not a defense against it.

Four lines raise Linux’s preemption count while the handlers run, so that Linux does not take the processor in the middle; the next chapter explains them. owns_mirror is always true, since the endovisor redirects only when no guard is held (below); the test keeps the function correct if that ever changes.

The might_preempt at the end adds kernel-mode preemption, which OSTD on a machine lacks: the handler may switch to another task before returning. That is how a tick ends a time slice in the middle of a kernel task’s computation, as it does on a machine with a preemptible kernel.

A switch inside the upcall is safe for the interrupted address because the body’s first act copies virq_ip into a local variable, so the address lives in this frame, on the task’s own stack. The record’s field is free for the next upcall on this virtual CPU. The stub copies the local into the slot only once the body has returned, perhaps much later. The interrupted task resumes from the same frame.

vOSTD assumes that a preempted task resumes on the virtual CPU that preempted it. On a machine a per-CPU word is one gs: instruction, so it cannot straddle a switch; vOSTD finds the slot first and touches it second, so a task preempted between the two and resumed on another virtual CPU would write the first virtual CPU’s slot. The schedulers of this book’s kernels, like Asterinas’s, never move a task they preempted, but OSTD allows a scheduler that balances load, and nothing in vOSTD enforces the assumption: it is a requirement vOSTD places on the kernel proper’s scheduler.

Kernel-mode preemption has a hazard of its own with floating-point state. From a thread’s FpuContext::load until user_run, and from execute’s return until save, the thread’s floating-point and vector registers are live on the processor, and a switch there, by an upcall or by a guard drop that delivers a bit, would let the next task’s restore of its own registers overwrite them. A kernel proper must therefore save them in its pre-schedule handler, as Asterinas does; this book’s kernels do not, so those windows are open in the prototype, and no test shows them closed.

Preemption inside a scheduling decision

An upcall must not preempt inside reschedule, between its decision and its switch. reschedule holds no preemption guard, since on a machine nothing preempts OSTD’s kernel code, so an upcall can land between the two. By then the run queue’s bookkeeping already names the chosen task current and has put the still-running task back among the waiting. A second decision could pick the running task. Before switching to a task, OSTD waits until the processor that last ran it has finished saving it, so a task that waits for itself waits forever and the processor hangs.

So vOSTD flags that window and defers any preemption to its end. open_resched_window, the first thing reschedule does, runs whatever virtual interrupts are already pending, without switching, so that whatever they ask for is answered by the decision about to be made; then it clears need-preempt and sets a flag in the virtual CPU’s local storage. While the flag is set, might_preempt only records a note, because need-preempt alone would wait for the next upcall, the bit that asked for it having been consumed. Whoever closes the window (the completed switch, the decision to do nothing, or the retry that decides again) acts on the note at once, by preempting or, for the retry, by deciding again instead of sleeping. A preemption is deferred by the window and never by more.

The window costs one reschedule each time a kick is taken inside it. When virtual CPU A puts a task on B’s run queue and kicks B while B is already deciding, B often picks the task before the kick is taken; the kick is then taken inside the window, by the guard drop that releases the run queue or by an upcall, and leaves a note. If B was idle, the note costs one reschedule that finds nothing to do; if B was switching away from a running task, it costs a switch back.

Interrupts off, and guards

Two separate fields in the record stand for the two ways a kernel defers work. On a machine, masking interrupts holds off the handler, and a preemption guard holds off only the task switch; in vOSTD both hold off the upcall, because the upcall cannot know in advance whether it will switch. The fields stay separate because OSTD’s interface has two guards.

  • irq_off is the virtual interrupt flag, inverted. vOSTD sets it where OSTD’s interrupts-off guard, irq::disable_local(), would clear the processor’s flag, and clears it when the guard drops; the endovisor sets it when it redirects into the upcall, and the upcall clears it at the end. While it is set, nothing is delivered.
  • The guard count, the low bits of preempt_info, is how many preemption guards are held, counting spin locks that disable preemption; a lock that disables interrupts sets irq_off instead. What a guard means is that no task switch happens on this virtual CPU while it is held; how that is enforced is that the watch timer never redirects a task that holds one, so the upcall, the one place a switch could happen underneath kernelet code, is never entered under a guard.

irq_off has two writers, but plain stores are enough. The endovisor writes a 1 only when it finds a 0, only from an interrupt on the carrier’s own processor, so the two writers never run at once, and the upcall it diverts into always clears that 1 again before the interrupted code resumes.

The guard word is updated only by its own virtual CPU, with single read-modify-write instructions (add, sub, and, or), because the guard count shares its word with the need-preempt bit, which the upcall’s handlers set. If a guard’s increment compiled to a load, an add and a store, an upcall could land between the load and the store, because the count was still zero, and the store would erase the need-preempt bit the upcall had just set; a single add to memory cannot be split by an interrupt.

Delivery at the end of a critical section

When a critical section ends, vOSTD delivers whatever was left pending in it, whenever it arrived. Two places check: the interrupts-off guard when it unmasks, and the drop of the last preemption guard, for a bit that arrived under the guard, in kernelet code or in a service. Only the upcall checks the stack’s headroom; these paths run the same handlers as a function call on whatever stack the task is on. The unmask:

pub(crate) fn handle_virq() {                   // the same handlers, called as a function
    if IN_VIRQ.load() { return; }               // already inside (one flag per virtual CPU): the guard's own drop below calls back here; the outer loop takes any bit raised before its last swap
    IN_VIRQ.store(true);
    {
        let _guard = crate::irq::disable_local();
        run_handlers(vrec());
    }
    IN_VIRQ.store(false);                       // cleared before the switch below, which may not come back here
    crate::task::scheduler::might_preempt();
}

Delivery on the return from user mode

A carrier in user mode takes its virtual interrupts on the way back, without a task switch. execute’s loop runs the handlers before it re-enters user mode, through deliver_no_switch: the same handle_virq as above without the final might_preempt, the call that switches tasks if need-preempt is set and no guard is held.

vOSTD does not switch at that point, unlike OSTD, because the tenant thread’s floating-point and vector registers are still live on the processor, and this book’s kernels save them only after execute returns and not at a switch, so another task’s restore of its own would overwrite them.

So under vOSTD a tenant thread that stays in user mode is never preempted. Its slice ends and need-preempt is set, but nothing acts on it until the thread enters the kernel and its kernel code reaches a call to might_preempt: an upcall, a guard drop or unmask that finds a bit pending, a spawn, or the kernel proper’s next yield or sleep. OSTD on a machine does preempt such a thread, by calling might_preempt before every entry to user mode, and Asterinas’s kernel proper relies on that; its has_kernel_event hook reports only signals. This is a difference from OSTD’s documented behavior, which the prototype has not closed.

Neither the flag nor the bit can be lost in a race. A flag set while the hook is already running is not lost, as chapter 5 arranged. user_run publishes KLET_USER and then reads pending, while klet_virq_raise sets the bit and then reads the state; as with idling, one of the two always sees the other, so a bit raised just as the carrier leaves is never stranded.

The kick’s interrupt

A kick to kernelet code on another processor makes that processor’s watch timer fire at once, through an inter-processor interrupt, instead of waiting up to a millisecond for its next tick. The endovisor sends it with smp_call_function_single(), which runs a function on a named processor, in interrupt context there, through an inter-processor interrupt; the last argument, 0, means the caller does not wait. The function it runs there cannot redirect anything itself, because that kind of interrupt does not publish the interrupted registers; what it can do is restart the watch timer with zero delay (klet_watch_fire_now), so that the timer interrupt, whose callback does see the registers, arrives as soon as the cross-processor call returns, and delivers the kick:

Simplified from prototype/linux/endovisor/sched.c: klet_kick_remote, klet_kick_ipi.

void klet_kick_remote(struct klet_carrier *c)
{
	if (c->state != KLET_RUNNING || c->depth != 0 || !klet_task_on_cpu(c->task))
		return;                                 /* not in kernelet code on a processor: the bit will be found */
	smp_call_function_single(task_cpu(c->task), klet_kick_ipi, c, 0);
}

static void klet_kick_ipi(void *arg)            /* runs in interrupt context on that processor */
{
	struct klet_carrier *c = arg;
	if (current->carrier_hooks == &c->hooks)          /* still the same carrier there? */
		klet_watch_fire_now();                  /* then make the watch timer fire, and it will redirect */
}

A requested firing is not a tick, unless the period it cut short has already run out: the callback raises no TICK for it, does not count toward the next chapter’s bound on critical sections, and puts the timer back on the expiry of the period it cut short, so a kick neither raises an extra tick nor delays the next one.

A kick whose bit is already set does nothing at all, so a thousand kicks before the bit is taken cost one delivery.

When a bit is delivered

A virtual interrupt reaches its handler by whichever of four paths comes first: the upcall, at a watch firing that finds the kernelet in kernelet code outside a critical section with stack to spare; the end of a critical section, at the unmask or the drop of the last guard; the return from user mode; or the start of the next scheduling decision. A bit left pending for any reason, because the carrier was in a service that held no guard, had too little stack, or was off its processor, is delivered by the first of those that comes, usually the next guard drop, or by a later watch firing that can redirect.

The firing comes within one period if the carrier is on its processor when that period expires; there is no bound while Linux keeps the carrier off a processor, or takes it off before each period ends.

Recap. Virtual interrupts are bits in the virtual CPU’s record: TICK from the watch timer, KICK from vcpu_kick. The watch timer is a pinned, hard, one-millisecond hrtimer per processor, armed by each carrier’s preemption notifier whenever Linux puts the carrier on that processor. When it finds the carrier in kernelet code outside a critical section, with room on the task’s stack, it points the interrupted frame at the image’s upcall stub, which saves everything on the task’s stack, runs the handlers, and may switch tasks before returning: kernel-mode preemption, held off by a guard and, inside a scheduling decision, by the window. A carrier in user mode is flagged and runs the handlers on its way back without switching; one in a critical section delivers the bit itself when the section ends; the next scheduling decision runs whatever is pending; a kick to another processor makes its timer fire at once; anything else waits for the next firing that can deliver it.

Sharing a processor politely

This chapter resolves three conflicts between a kernelet and Linux over who holds a processor, and adds one backstop. Linux wants a processor back from a carrier whenever its own policy says so, because the sandbox’s turn is over or a host task with a better claim woke up, but it cannot always take it. The watch timer gives the processor up on behalf of a kernelet that cannot give it up itself (Problem 1). vOSTD copies the kernelet’s critical sections into Linux’s own preemption count (Problem 2). The watch timer bounds how long that copy may hold Linux off (Problem 3). A last section keeps a waiting virtual CPU from spinning on a lock whose holder Linux has descheduled.

Problem 1: a Linux that does not preempt kernel code

Linux: preemption models. Linux’s preemption models differ in when a task that should give way does so. Linux decides that a task should give way by setting a flag on it, need_resched, which the scheduler does at a timer tick when the task’s slice is used up, or when a task with a better claim wakes; the models differ in when the flag is acted on. A kernel is built with one of several models; one built with the full model and the option PREEMPT_DYNAMIC, as this book’s is, can be switched at boot to none, voluntary or full with the parameter preempt=. Under full a task running kernel code can be rescheduled at almost any instruction, on return from an interrupt. Under voluntary and none, common on servers, a task in kernel mode keeps its processor until it sleeps, returns to user mode, or reaches one of the many places where Linux’s own code calls cond_resched(), the voluntary preemption point.

Under preempt=none, a kernelet task that computes holds its processor for as long as it computes, against every other task that wants it, because kernelet code contains no call to cond_resched(): it cannot call Linux.

The remedy is for the watch timer to do what a call to cond_resched() would: give the processor up on the kernelet’s behalf when Linux wants it. The two forms below exist for the configurations in which Linux does not preempt kernel code; on a Linux that does, Linux reschedules by itself on the way out of the interrupt, and neither has anything left to do.

The first form is the upcall of chapter 10: on its way out, if Linux has set need_resched meanwhile, vOSTD calls vcpu_yield, which reschedules in Linux. vOSTD notices without calling Linux, by the decrement-and-test of its mirror, under Problem 2; with the mirror off, only the stub below yields. The Linux built for this book is configured for full preemption and booted with preempt=none for this test, so it still keeps its preemption count, and it folds need_resched into that count (the box under Problem 2).

The second form is a yield stub in the endovisor, for when the upcall cannot be taken because the interrupted task’s stack has too little room left, or its bound is unknown. The timer points the interrupted frame at the stub by rewriting the frame’s instruction pointer, as it does for the upcall.

The stub fits where the upcall does not. The upcall needs 32 KiB left on the stack, 16 KiB for its own frames and 16 KiB reserved for a Linux interrupt on the same stack. The stub needs a few dozen words, the slot it reserves, the sixteen words it pushes and one small C frame, and the reschedule itself runs on the Linux stack. Nothing checks for those few words; running out halts the host on a double fault, as chapter 7 explains.

The watch callback’s non-critical branch becomes the following, which replaces chapter 10’s call to klet_virq_redirect. again is the callback’s last lines, which re-arm the timer and return:

unsigned long klet_yield_body(void)
{
	struct klet_carrier *c = klet_current_carrier();
	struct klet_svc_args args = { .op = KLET_SVC_VCPU_YIELD };
	unsigned long ip = c->yield_ip;

	klet_run_on_linux_stack(c->linux_sp, &args);   /* klet_svc_body -> klet_do_yield, on the Linux stack */
	if (args.ret || c->doomed)                      /* the kernelet stopped, or this carrier was killed */
		return 0;
	return ip;
}

static void klet_do_yield(struct klet_carrier *c)
{
	if (!cond_resched() && need_resched())
		schedule();
}

The stub never returns into a kernelet that died while the carrier was away. klet_svc_body sets ret for this service when the sandbox is stopped or dying, or this carrier has been evicted. .Lleave then abandons the kernelet stack and returns to Linux.

klet_do_yield must yield under every model, and it serves every yield: the upcall’s, the stub’s, and the forced one of Problem 3. cond_resched() does nothing under the full model. So when it has not rescheduled and Linux still wants the processor, schedule() is called directly.

The test make yield shows the remedy working. The test kernel in prototype/kernels/yield/src/lib.rs computes for seconds. The test runs it twice on a kernel booted with preempt=none, with a competing host process pinned to the same processor: once with the watch timer turned off (the module parameter klet_watch=0) and once with it on. With the timer off, the competitor gets nothing for the kernelet’s whole computation, 4.4 s in the last run. The competitor prints a progress line about every 250 ms, so the test resolves nothing finer; with the timer on, the longest gap between two lines was 271 ms in the last run, barely more than the print interval, and the test asserts under a second.

The test also shows that the upcall loses no register: a checksum the kernel computes over a long run in ten live variables comes out identical, and equal to a user-space reference, whether the kernelet was diverted through the upcall thousands of times or never.

The stub’s unforced path, taken only when the stack is short, runs in no test: the yield kernel’s computation is shallow, so every tick that finds it in kernelet code outside a critical section finds room for the upcall. The stub itself runs, in the forced form of Problem 3, in make sched-coop, where no checksum is taken.

Problem 2: a lock holder loses its processor

If Linux preempts a carrier while the kernelet task on it holds a spin lock, every other virtual CPU that wants that lock spins until Linux runs the first one again, which may be a whole time slice later. This is lock-holder preemption. There are two families of remedy: tell the host when not to preempt, and make waiting cheap when it preempted anyway. This section is the first remedy; the backstop at the end of the chapter is the second.

Linux: the preemption count. Linux keeps a per-processor preemption count, which preempt_disable() and every spin lock raise and their counterparts lower; on return from an interrupt, Linux reschedules kernel code only if the count is zero. The word is a set of bit fields: the low eight bits are the preemption depth, and the bits above count software- and hardware-interrupt nesting, which is how Linux knows it is in an interrupt. It lives in the per-processor block that %gs points at.

On x86-64 one decrement tests both conditions at once, because a copy of the current task’s need_resched flag is folded, inverted, into the top bit of the same word (PREEMPT_NEED_RESCHED): a single decrement yields zero exactly when the count is zero and a reschedule is wanted, which is what preempt_enable() tests. In numbers: with one guard held and no reschedule wanted the word is 0x80000001, and a decrement gives 0x80000000, not zero; if Linux has cleared the top bit to ask for the processor, the word is 0x00000001, and the decrement gives zero.

The rule, then: the kernelet’s critical sections are Linux’s critical sections. vOSTD records in Linux’s count, as one extra unit, whether the kernelet is in a critical section; the book calls that unit the mirror.

vOSTD mirrors entry and exit with Linux’s own instructions: an increment on entry, a decrement and zero test on exit. When the kernel proper enters a critical section, by taking a preemption guard, a spin lock or an interrupts-off guard while it held none, vOSTD executes the same single instruction Linux’s preempt_disable() does, an increment of the per-processor word through %gs, at the offset the boot arguments published. When the section ends, it executes the matching decrement. If that leaves the word at zero, Linux is waiting for this processor, and vOSTD hands it over at once with the service vcpu_yield: the same decrement and zero test as Linux’s preempt_enable(), except that vOSTD yields whatever the preemption model.

Every processor’s count gets back exactly what it was given. Linux does not move a task whose count is raised. Every path on which the carrier can leave the processor takes the increment out first and puts it back wherever the carrier resumes.

Simplified from prototype/vostd/src/vcpu.rs and prototype/vostd/src/task/preempt/cpu_local.rs: host_preempt_inc, host_preempt_dec_and_test, inc_guard_count, dec_guard_count.

pub(crate) fn host_preempt_inc() {
    if mirrored() { return; }                                    // already up: idempotent
    unsafe { asm!("inc dword ptr gs:[{o}]", o = in(reg) GS_PREEMPT_COUNT) };
    set_mirrored(true);                                          // after, so the flag never claims more than the count holds
}

pub(crate) fn host_preempt_dec_and_test() -> bool {
    if !mirrored() { return false; }
    set_mirrored(false);                                         // before, for the same reason
    let zero: u8;
    unsafe { asm!("dec dword ptr gs:[{o}]", "setz {z}", o = in(reg) GS_PREEMPT_COUNT, z = out(reg_byte) zero) };
    zero != 0                                                    // zero: no guards left, and Linux wants the processor
}

pub(crate) fn inc_guard_count() {
    let was_critical = in_critical_section();
    add_assign(1);                                               // the kernelet's own count
    if !was_critical { vcpu::host_preempt_inc(); }               // the first guard raises Linux's
}

pub(crate) fn dec_guard_count() {
    let leaving = get_guard_count() == 1 && !irq_is_off();
    let host_wants_cpu = if leaving { vcpu::host_preempt_dec_and_test() } else { false };
    sub_assign(1);
    if host_wants_cpu { vcpu::host_yield(); }                    // the vcpu_yield service: schedule()
    if leaving { vcpu::deliver_if_pending(); }                   // a virtual interrupt that arrived meanwhile
}

Linux’s count rises by one however deeply the kernelet’s guards nest, and that is deliberate. Linux’s count has only eight bits for the preemption depth, and a kernel proper that nested more guards than that would spill into the fields that say “in an interrupt” and make Linux misjudge its own state.

vOSTD raises and lowers Linux’s count according to a flag, mirrored, in the virtual CPU’s record, rather than by pairing each guard’s entry with its exit: the increment happens when a critical section begins and the flag is clear; the decrement when one ends and the flag is set. Raising twice is a no-op, and so is lowering when nothing is raised.

A pairing would not do, because the code that ends a critical section is often not the code that began it: a section can begin with a guard and end with an unmask, or begin in the upcall, and OSTD’s switch_to_task takes a guard that the next task, not the one that took it, drops. We could not show that every lowering meets exactly one raising on all those paths. A single unmatched decrement would wrap Linux’s word below zero, borrowing into the interrupt-nesting fields, so that Linux would believe it is in an interrupt for as long as the kernelet runs there; the endovisor’s measurement, below, catches that only when the carrier next leaves kernelet code. With the flag, the worst a mistake costs is one preemption Linux was not asked to defer.

The flag is set after the increment and cleared before the decrement, so that it never claims more than the count holds: whenever the flag is set, Linux’s count is raised.

The mirror exists only while kernelet code runs. A service may sleep. Linux forbids sleeping with the preemption count raised. OSTD holds a preemption guard while it edits a page table, and the service that maps a page under it may have Linux allocate memory. So the service body, on the Linux stack, takes out of Linux’s count what the kernelet’s guards added, and puts it back on return.

The endovisor measures the amount itself: it recorded Linux’s count when the carrier entered kernelet code, and the excess over that is the kernelet’s. It does not ask the kernelet.

Simplified from prototype/linux/endovisor/carrier.c: klet_mirror_in, klet_mirror_out, klet_svc_body.

static void klet_mirror_in(struct klet_carrier *c)     /* on the way into kernelet code */
{
	c->pc_base = preempt_count();
	if (c->excess > 0) { preempt_count_add(c->excess); c->excess = 0; }
}

static void klet_mirror_out(struct klet_carrier *c, bool forever)   /* on the way out, in task context */
{
	int excess = preempt_count() - c->pc_base;         /* measured, never read from the kernelet */

	if (excess < 0 || excess > 1) {                    /* the kernelet corrupted host state: re-normalize */
		preempt_count_set(c->pc_base);
		c->excess = 0;
		return;
	}
	if (excess > 0) preempt_count_sub(excess);
	c->excess = forever ? 0 : excess;
}

void klet_svc_body(struct klet_svc_args *args)
{
	c->depth++;
	klet_mirror_out(c, false);     /* the service may sleep now */
	switch (args->op) { /* ... */ }
	klet_watch_arm(c);             /* back in kernelet code soon: make sure this processor is watched (defensive) */
	klet_mirror_in(c);
	c->depth--;
}

A kernelet guard therefore promises only that no kernelet task switch happens on this virtual CPU until it drops. Across a service, which may sleep, and at a forced yield (Problem 3, below), the carrier can still lose the processor while a kernelet guard is held. The kernelet is correct under that weaker promise, as a guest kernel is correct when its hypervisor deschedules a virtual CPU. The memory services need to sleep under a guard, which only this weaker promise allows. The chapter that builds them states it precisely.

The test make sched-coop shows the mirror working. It runs four kernelet tasks hammering one spin lock for ten seconds, under the full model, while two competitors in a sibling control group make Linux preempt the carriers constantly. It counts, in the preemption notifier, every time a carrier is switched out involuntarily, outside a service, while vOSTD’s mirrored flag says it is in a critical section. It counts by the flag rather than by the guard count because Linux’s count goes up just after the kernelet’s first guard and comes down just before its last one, and a switch in those few instructions is Linux’s right; since Linux’s count is raised whenever the flag is set, every switch the test counts is a real failure. With the mirror on, the test asserts that the count is zero. With it off (the module parameter klet_mirror=0, under which vOSTD still keeps the flag but skips the increment), the last run counted 2,025.

Problem 3: a critical section that never ends

The mirror lets a kernelet defer Linux’s preemption, so a kernel proper whose logic the tenant controls could defer it forever by entering a critical section and never leaving.

The watch timer bounds the deferral at two of its one-millisecond periods when ticks arrive on time, three when one is late, from interrupt context whatever the count. A tick that finds a carrier in kernelet code in a critical section with need_resched set notes the time; if the next tick finds the same, and at least a millisecond has passed since the note (now is the monotonic clock), it forces the yield. A tick that arrives late, because Linux had interrupts off or the machine under the test VM was busy, lengthens the grace, and a second strike that comes less than a millisecond after a late first one is skipped, so the grace can reach three ticks; the second strike is skipped whenever the first strike’s callback ran later than the second’s, which any jitter can cause.

In the callback, the bound replaces chapter 10’s last branch. Before it, a requested firing goes straight to again, and so does a tick that finds no need_resched, which first drops the note:

Simplified from prototype/linux/endovisor/watch.c: klet_watch_fn.

	/* a critical section, and Linux wants the processor */
	if (!c->strike1_ns) { c->strike1_ns = now; goto again; }     /* strike one */
	if (now - c->strike1_ns < NSEC_PER_MSEC) goto again;           /* less than a tick ago */
	c->strike1_ns = 0;
	c->yield_ip = regs->ip;
	c->forced = true;                                              /* strike two: yield anyway */
	regs->ip = (unsigned long)klet_yield_stub;

Nothing in the stub changes for a forced yield: the service body lifts the mirror for every service, so here, where the kernelet is inside a critical section, it takes the kernelet’s increment out of Linux’s count before schedule() and puts it back after.

The count of strikes restarts whenever the carrier stops deferring Linux: both strikes must come from ticks that each find the carrier holding Linux off, with no tick in between that found otherwise. The note of the first strike is dropped whenever a tick finds the carrier out of a critical section or Linux no longer wanting the processor, and when the carrier leaves the processor, since a carrier that has given the processor back is deferring nothing.

make sched-coop’s third boot measures the bound. It adds an overstayer, a task that holds a preemption guard for about 8 ms at a time (nominally 10). It was forced to yield over a thousand times, and its longest deferral, measured from the first strike, was about 2 ms, against the 4 ms the test allows (measured on the booted prototype).

Time a kernelet keeps the processor past Linux’s wish delays its neighbors but does not shrink their share. Linux accounts the extra run time to the sandbox’s control group like any other. make sched-fair boots the sandbox three times, with 1 kernelet task, with 50, and with 50 plus an overstayer, each against one competitor of equal weight in a sibling group on the same two processors, so the competitor’s due is one processor. Its share was 0.994 and 0.995 of a processor in the boots without the overstayer; with it, the only boot with forced yields, 0.884 in the last bench and 0.986 and 0.990 in two reruns, a variance the last chapter discusses. The test asserts a spread under 3 % and the last bench failed it (measured on the booted prototype). What a neighbor can lose is at most the grace, per preemption.

Forced yields are counted and reported in the kernel log only when the endovisor unloads, since a print from the timer would lengthen the very deferrals it reports, so the operator sees after the fact which carriers, by process identifier and virtual CPU, collected them.

The backstop: do not spin on an absent lock holder

A spin lock that keeps failing may be waiting for a lock holder that is off its processor: after a forced yield, or while the lock holder’s carrier is in a service it called under the lock, asleep or preempted. After a thousand failed attempts the lock says so with the service vcpu_on_spin, and keeps spinning.

Linux: yield_to(). yield_to() asks the scheduler to run a named runnable task next in place of the caller, a hint the scheduler may decline. With the scheduler’s default features it pushes the caller’s deadline back, if other tasks share its run queue, and reschedules; it does not make Linux pick the named task. Its second argument says whether to reschedule the named task’s processor as well; KVM passes true. So with the argument false, the call only gives up the caller’s own turn.

The endovisor answers the hint with a directed yield in the shape of KVM’s, kept cheap. It applies a limit of one call per jiffy, Linux’s own scheduler tick (4 ms in this build, HZ=250), per virtual CPU. It picks the first sibling carrier of the same sandbox that is runnable but not running and passes it to yield_to() with the second argument false, and failing that calls cond_resched(), which gives the processor up only if Linux already wants it, and under the full model does nothing.

Simplified from prototype/vostd/src/sync/spin.rs: acquire_lock.

fn acquire_lock(&self) {
    let mut spins: u32 = 0;
    while !self.try_acquire_lock() {
        core::hint::spin_loop();
        spins += 1;
        if spins == SPINS_BEFORE_ON_SPIN {       // 1000
            spins = 0;
            crate::vcpu::on_spin();              // "my lock holder may not be running"
        }
    }
}

The lock is correct without the service: whether or not the endovisor finds a sibling to run, the loop goes on trying. A lock holder asleep in a service is not runnable, so for it the hint finds nothing.

A spinning waiter holds Linux off like any critical section, because it spins with its lock’s guard held and Linux’s count raised. At most one vcpu_on_spin call per jiffy can yield, so in practice the forced yield takes the processor first, within two or three ticks.

No test of this book exercises the path; in every make sched-coop boot, the counters of spins that called the service and of calls to yield_to() were zero.

Recap. On a Linux that does not preempt kernel code, the watch timer gives the processor up for a carrier that Linux wants, through the upcall when it can and otherwise through a yield stub, which saves everything, reschedules on the Linux stack, and resumes the kernelet exactly where it was. To keep Linux from preempting a carrier inside a critical section, vOSTD mirrors whether the kernelet is in one into Linux’s own preemption count, as one increment, with the same instruction preempt_disable() uses. It yields the moment the section ends if Linux was waiting. Every service lifts the mirror for its duration so that it may sleep. A section that outlasts two ticks while Linux waits, three if a tick arrives late, is forced to yield. A waiter that spins too long tells the endovisor, which gives up the waiter’s turn with yield_to, naming a sibling that Linux may ignore, or else calls cond_resched(); the lock is correct without it.

Stopping a kernelet

However a kernelet ends, every carrier stops, everything the kernelet held goes back, and Linux is left exactly as it was. A kernelet ends in one of three ways: its kernel asks to, by powering off; its kernel fails, with a panic nothing catches; or the host decides, because the operator killed it. The hard case is a carrier that is running kernelet code and will not come out.

The shape of a death

  1. The kernelet is marked stopped or dying, which is a single store.
  2. Every carrier is stopped, at a point where it holds nothing of Linux’s.
  3. When no carrier is left, the sandbox has exited: what the kernelet held goes back and the holder can read the exit record from the sandbox descriptor.

A kernelet’s state is abandoned, not tidied: nothing is unwound and no destructor runs, because tidying would mean running the tenant’s kernel on the host’s behalf at the moment it is least trusted. Once a carrier has left the image for good, no code from it runs on that carrier again, and the endovisor never runs kernelet code on the host’s behalf. What the endovisor gave the kernelet it takes back as a whole, without looking inside: the address spaces, every heap block the kernelet still held, which the endovisor tracks in a table of its own, and the pool of kernelet stacks.

Stopping from inside

Both the kernel proper’s poweroff and a panic in the kernelet end in the service stop, which marks the instance dying and kills every carrier, its caller included. On the endovisor’s side it records the exit code for the holder to read from the sandbox descriptor, marks the instance as dying, sends SIGKILL to every carrier, the caller included, and arms the eviction sweep of the end of this chapter; then the calling carrier leaves its kernelet stack for the last time.

Simplified from prototype/linux/endovisor/carrier.c: klet_stop_instance, klet_svc_stop, klet_carrier_die.

void klet_stop_instance(struct klet_inst *inst, u64 code)
{
	inst->stopped = true;
	pr_info("kernelet: stopped, exit code %llu\n", code);
	klet_end(inst, KLET_END_EXITED, code, 0);    /* every end of a sandbox goes through klet_end: the next section shows it */
}

static void klet_svc_stop(u64 code)              /* the service, called by the kernelet */
{
	klet_svc_enter(KLET_SVC_STOP, code, 0, 0);   /* klet_stop_instance, on the Linux stack */
	for (;;)
		klet_leave(c, KLET_DEAD);                /* abandon this kernelet stack for good */
}

static void klet_carrier_die(struct klet_carrier *c)
{
	klet_detach(c);                              /* current->carrier_hooks = NULL; free the stack and the records */
	if (!fatal_signal_pending(current))
		force_sig(SIGKILL);                      /* a user task can only end by Linux's own exit path */
}

A carrier that leaves for good dies as any process does, by a fatal signal Linux acts on. klet_leave with the state DEAD switches to the Linux stack and lands, as always, inside whichever hook entered the kernelet. That hook sees the state and calls klet_carrier_die, which clears the task’s hooks pointer and lets Linux kill it. Linux offers a module no direct way to end a task that is not a kernel thread, so a carrier ends as any process does, by a fatal signal acted on in the exit loop; clearing it first keeps the hooks from running on a task that no longer carries anything.

Stopping from outside

A carrier killed from outside is noticed through its lifeline, which Linux closes when the carrier’s process exits. The operator kills a carrier, or the out-of-memory killer does, or the holder does it (make probe, at the end of this chapter): kill(pid, SIGKILL) on a carrier’s process id. The carrier dies in Linux’s exit path if the signal finds it in user mode, and Linux closes its descriptors, among them its lifeline; where Linux’s exit path cannot reach it, the endovisor looks for the signal itself, as the end of this section shows. The lifeline’s release is the endovisor’s notice:

Simplified from prototype/linux/endovisor/carrier.c: klet_carrier_lifeline_closed.

void klet_carrier_lifeline_closed(struct klet_carrier *c)
{
	/* release what a carrier killed in user mode never detached: its stack, its empty address space */
	list_del_init(&c->link);
	live = !inst->dying;                         /* the sandbox was running when this carrier died */
	last = atomic_dec_and_test(&inst->nr_carriers);
	if (!live)
		klet_check_exited_locked(inst, &claim);  /* the last carrier of a dying sandbox: its exit is this caller's to run */
	if (live)
		klet_end(inst, KLET_END_KILLED, 0, KLET_KILLED_CARRIER_LOST);   /* a carrier's death is the sandbox's death */
	else if (claim)
		klet_sandbox_exited(inst);               // Release the address spaces, heap blocks and stack pool; wake exit-record readers.
	if (c->task == current) {                    /* undo its attachment, which only its own task may do */
		current->carrier_hooks = NULL;
		klet_sched_detach(c);
	}
	if (!c->pnotifier_on && c->task->carrier_hooks != &c->hooks)
		klet_carrier_put(c);                     /* the carrier's own reference; the lifeline file holds the other */
	else
		pr_warn("kernelet: carrier record released away from its task; kept\n");
}

Simplified from prototype/linux/endovisor/sandbox.c: klet_end.

void klet_end(struct klet_inst *inst, u32 how, s32 code, u32 reason)
{
	if (!inst->exit.how) {                       // The first end records the final exit reason.
		inst->exit.how = how;
		inst->exit.code = code;
		inst->exit.reason = reason;
	}
	first_mark = !inst->dying;                   /* a test-and-set under the lock */
	inst->dying = true;
	klet_check_exited_locked(inst, &claim);      /* no carrier left? then the sandbox has exited already */
	if (first_mark) {
		klet_kill_carriers(inst);                /* SIGKILL to every carrier, and every sleep of theirs ended */
		klet_evict_arm(inst);                    /* for whoever is inside kernelet code */
	}
	if (claim)
		klet_sandbox_exited(inst);
}

Any carrier’s death while the sandbox is running ends it: a sandbox that had lost a virtual CPU would otherwise run on, with the others spinning on whatever locks the lost one held.

Every end of a sandbox goes through klet_end, which records why, marks it dying, kills every carrier and arms the eviction sweep. The sweep is armed even for the kernelet’s own stop, for a reason the next section makes clear: a virtual CPU that the stop left spinning in kernel mode never passes through a hook again to die, and only eviction gets it out.

The last carrier’s death is the sandbox’s exit. It releases what the kernelet held, makes the sandbox descriptor readable, and wakes the holder waiting for its exit record.

A carrier killed in user mode before any mark never detaches, so its lifeline’s release is where its records are freed and the sandbox is told to die. Such a carrier passes through the resume hook once more, since the signal counts as pending work, but the hook, finding no mark and (usually) no virtual interrupt pending, steps aside; Linux kills the task, and klet_detach never runs for it. (With a tick pending, the hook enters the kernelet, a service dooms the carrier, and it dies by the route of the next paragraph instead.) The lifeline’s release frees what the detach would have: this is why the death notice, not the detach, is the place where a carrier’s records are finally released, and, since the sandbox was running, where the rest of the sandbox is told to die.

A carrier’s record is freed only when nothing can still reach it through its task. The record holds two references, the carrier’s own, dropped here, and the lifeline file’s, dropped when the file is released, and goes when both are gone. The carrier’s own is dropped only if its task no longer points at the record: a lifeline released by some other task, through a copy of the descriptor, would leave the dying task’s hooks pointer and preemption notifier aimed at freed memory, so such a record is kept instead, with a warning; the endovisor counts records made and freed at unload, and every test checks that none is left.

Killed anywhere else, the carrier is out of Linux’s reach, since Linux acts on SIGKILL only on the way to user mode, and the endovisor has to notice the signal itself. Every service body, on its way back to the kernelet stack, tests for a pending fatal signal. If it finds one, it marks the sandbox dying, which kills the others, and marks the carrier doomed, and the stub then leaves the kernelet for good, through klet_leave, instead of returning into it. That covers a carrier asleep in vcpu_idle or vm_wait, whose sleeps are killable and so end at once, and one in the middle of any other service. A carrier running kernelet code and calling no service is caught by the watch timer of chapter 10: its callback, finding a fatal signal pending on a carrier, points the interrupted instruction at the eviction sweep’s exit stub (below), exactly as the sweep does, and the carrier’s death then ends the sandbox through its lifeline. With the watch timer turned off, such a carrier stays out of reach until it next calls a service.

Eviction

Linux: signals and kernel mode. Linux acts on a signal, even SIGKILL, only when the task is about to return to user mode. A task that stays in kernel mode is never killed by a signal, however long it stays. Linux’s own kernel code is written to come out: it sleeps in killable waits and passes voluntary preemption points. Code that Linux did not write does neither.

A carrier looping in kernelet code can be stopped only by force. Say it loops in a loop {} reached through a logic bug a tenant found: it never returns to user mode, Linux by itself would never kill it, and the sandbox could never be destroyed. The endovisor has the means from chapter 10: a timer interrupt on the carrier’s processor, and the right to change the interrupted instruction pointer.

The eviction sweep is one hrtimer per processor, pinned and hard like the watch timer, armed on every processor when a kernelet is marked dying, and re-armed every millisecond until no dying sandbox has a carrier left. Its callback checks four things about what it interrupted: that the task is a carrier of a dying kernelet, that the interrupted context is kernel mode, that the interrupted instruction lies inside the kernelet image’s text, and that the carrier’s service-call depth is zero. If all four hold, it overwrites the saved instruction pointer with the address of an exit stub, and nothing else.

Simplified from prototype/linux/endovisor/evict.c: klet_sweep.

static enum hrtimer_restart klet_sweep(struct hrtimer *timer)
{
	struct pt_regs *regs = get_irq_regs();

	if (atomic_read(&klet_sweeping) == 0)           /* no dying sandbox has a carrier left */
		return HRTIMER_NORESTART;
	if (!regs || user_mode(regs) || !klet_in_image_text(regs->ip) || !current->carrier_hooks)
		goto again;
	c = klet_current_carrier();
	if (!inst->dying || c->depth != 0 || c->evicted || c->state != KLET_RUNNING)
		goto again;

	c->evicted = true;
	regs->ip = (unsigned long)klet_exit_stub;    /* the only register the endovisor touches */
again:
	hrtimer_forward_now(timer, ns_to_ktime(KLET_SWEEP_INTERVAL_NS));
	return HRTIMER_RESTART;
}

The interrupt then returns to the stub instead of the loop. The stub realigns the stack pointer, because an interrupt can land between any two instructions, and leaves through the ordinary stack switch, never to come back:

Why this is safe to do at an arbitrary instruction: at depth 0, in kernelet text, a carrier holds nothing of Linux’s. It cannot hold a Linux lock, because kernelet code cannot call Linux; the only thing it may hold is the one increment of Linux’s preemption count from chapter 11, and klet_leave with the state DEAD runs klet_mirror_out with forever set, which measures and removes it. The kernelet’s own half-finished state, its locks and its data, does not matter: the kernelet is dying, and no kernelet code runs afterwards. Kernelet code never masks hardware interrupts: the kernel proper is safe Rust, and vOSTD, the only code beneath it, has no interface that would; so there is no state in which the timer cannot land.

The sweep is needed only for a carrier that was in kernelet code; every other carrier is caught on another path. A carrier that is not on a processor at that instant is interrupted by nothing; it is caught by the sweep when it next runs, since the sweep is on every processor. A carrier inside a service call is left alone by the depth test, and finishes the service; by then the SIGKILL the mark sent is pending on it, so the service body dooms it and the stub leaves for good, as the previous section said.

The test

make probe boots one probe kernel three times and ends its sandbox a different way each time. The kernel, in prototype/kernels/probe/src/lib.rs, has a handler for system call number 1000 that is loop {}. In the first boot the holder waits a second and then sends SIGKILL to the carrier of virtual CPU 0, which is spinning in kernelet code; the log shows the watch timer finding the signal on it and killing it there, its lifeline closing and ending the sandbox, and the module unloading with its reference count at zero. In the second boot the tenant runs under a seccomp filter that kills on its endless system call, and the sandbox ends by that signal. In the third the holder asks the endovisor instead, with KLET_KILL: the log then shows the sweep being armed and the spinning carrier evicted by an early sweep, at an address the endovisor places a few kilobytes into the kernelet image’s text. The build checks those lines and that Linux printed no warning, a check that means something only because the Linux the tests boot is built with CONFIG_BUG on, which the minimal configuration it starts from turns off.

The same test exercises the other mechanisms of chapter 8 that the hundred-line kernel never reaches: a demand-paging fault, which the next chapter builds, an illegal instruction (ud2, twice, so that the drain’s re-ignoring of chapter 8 is exercised), a breakpoint (int3) and a privileged instruction (hlt), the last two being exceptions Linux reports with SI_KERNEL; the kernel proper steps past the three instructions, and the test reads the carrier’s signal dispositions back and checks that everything but SIGKILL and SIGSTOP is ignored. The tenant also asks for a 4 MiB write, which the kernel proper refuses for want of memory rather than letting the host warn.

One of the memory tests, make mem-kill, kills a virtual CPU’s carrier while its sibling is taking page faults in the same address space, and checks that the whole sandbox ends cleanly, with the module’s reference count at zero.

The same test checks that the signals chapter 8 discards never reach the carrier. On the way it sends that carrier SIGTERM and SIGUSR1, and then two thousand rounds of SIGQUIT, SIGABRT, SIGTSTP, SIGTTIN and SIGTTOU, which chapter 8 said are discarded, and checks that it lives and that none of them reached its queue.

Two more boots of the same test kill the carrier where Linux by itself would never act on the signal: once while it is idle in vcpu_idle with nothing to run, and once while it runs a kernel task that loops and calls no service. The log must show the sandbox ending within a bounded time after the kill, the endovisor’s counter saying which path caught it, no stall report from Linux, and a clean unload.

Recap. A kernelet ends by the stop service or by the death of any of its carriers; either marks the instance and sends SIGKILL to every carrier. A carrier in user mode dies by Linux’s own exit path, after a hook sees the mark and detaches it; one asleep in a killable service is woken and leaves for good on its way back, as does one that was running a service. A carrier running kernelet code is evicted: a timer on its processor finds the interrupted instruction in the image’s text at depth 0 and points it at an exit stub, which leaves through the stack switch for good. The last lifeline’s release is the sandbox’s end, and returns everything the kernelet held.

Tenant memory on Linux’s page tables

This chapter and the next are what the book has been building toward. The hundred-line kernel’s VmSpace::new(), cursor.map(frame, prop) and vm_space.activate() are the kernel proper’s whole view of a tenant’s memory, and they are the same calls a kernel makes on a machine. What they do inside Linux is the central mechanism of the design.

The problem

On a machine, a VmSpace is a page table. The kernel proper writes its entries, through OSTD’s cursor, and the processor walks it when the tenant’s program runs. OSTD’s job is to write the entries in hardware format and load the table’s root into the page-table register at activate.

Inside Linux, none of that is available. A carrier runs on the page table of its Linux address space; the processor walks that table and no other; and only Linux writes it, under its own locks, with its own bookkeeping of what every entry means. vOSTD cannot write a Linux page-table entry, and it cannot make the processor walk a table of its own.

So the design turns the relationship around. A VmSpace is a Linux address space. Its page table is the tenant process’s Linux page table, the one the processor walks; there is no other. vOSTD never writes an entry of it. Every change the kernel proper’s cursor makes becomes a memory service, in which the endovisor checks what it is asked for against the kernelet’s grant and then makes the change with Linux’s own functions, under Linux’s own locks. vOSTD reads the table, through the direct map, as a processor would; that is the next chapter.

That is a stronger position than the one a kernel has on a machine, where a bug in the framework could map any frame into a tenant. Here, no translation reaches the hardware without trusted host code having checked the frame.

Linux: address spaces, areas, and page faults. A process’s user memory is described by an address space, struct mm_struct, which holds the page table’s root (mm->pgd) and a set of virtual memory areas (VMAs): contiguous ranges with uniform permissions, each optionally backed by a file.

Linux fills page tables lazily: touching an address with no entry raises a page fault, Linux finds the VMA, and asks it for the page, by calling the fault function of the VMA’s operations table (struct vm_operations_struct). A driver that implements mmap on its device file supplies those operations, and so decides what appears at each address of its area.

A VMA can be marked as holding raw frame numbers (VM_PFNMAP). Linux then maps exactly the frames it is told to, with vmf_insert_pfn_prot(), and takes no further interest in them: no reference counting, no swapping, no migration. The driver removes entries again with zap_vma_ptes(). This is how device drivers give a process a window onto their memory, and it is the right contract here, because the frames’ lifetime belongs to the kernelet.

Every change to an address space is made under its lock, mmap_lock. An address space is freed, page tables included, in exit_mmap() when its last user lets go; a user reference, taken with mmget() and dropped with mmput(), is what keeps that from happening.

Creating a space

VmSpace::new() is the service vm_create. The endovisor makes three things: an empty Linux address space, a file to own the area, and the area itself, one VMA over the whole user range.

s64 klet_do_vm_create(struct klet_carrier *c)

static int klet_space_make_area(struct klet_space *sp)
{
	/* vm_mmap() maps into the *calling* task's address space, so adopt the new one for a moment */
	mmget(sp->mm);
	prev = kernelet_switch_mm(sp->mm);
	ret = vm_mmap(sp->file, KLET_AREA_START, KLET_AREA_END - KLET_AREA_START,    /* [0x10000, 2^47 - 4 KiB) */
		      PROT_READ | PROT_WRITE | PROT_EXEC, MAP_SHARED | MAP_FIXED, KLET_AREA_START);
	back = kernelet_switch_mm(prev);                           /* and switch back */
	mmput(back);
	sp->start = KLET_AREA_START;
	sp->end = KLET_AREA_END;
	return 0;
}

static int klet_space_mmap(struct file *file, struct vm_area_struct *vma)   /* the file's mmap: sets up the area */
{
	vm_flags_set(vma, VM_PFNMAP | VM_IO | VM_DONTEXPAND | VM_DONTDUMP | VM_DONTCOPY);
	vma->vm_ops = &klet_space_vm_ops;                          /* fault and pfn_mkwrite, below */
	return 0;
}

Four choices in this code each close a hole.

The owner. Each space’s owner is the holder’s main thread, never the carrier that created it. Linux records in each address space an owner task, through which the memory controller finds the control group to charge faults and reclaim to. The function Linux uses to make an address space would store the creating task there, without a reference, and that task is a carrier that may die while the space lives on; every later fault would then read a freed task. So the patch’s kernelet_mm_alloc() takes the owner as an argument, and the endovisor passes the main thread of the holder, the process that created the sandbox, which the endovisor pins with a task reference from the sandbox’s creation to its exit, after it is cleared from every space.

The file’s inode. Each space gets an inode of its own. The plain anonymous-inode helper hands every caller one shared inode, and Linux keeps, per inode, the list of areas that map it, so every space’s area would sit in one list, and an operation on one space’s file could reach the others’.

The area’s flags. Two of the area’s flags are there for the host’s sake. VM_SHARED, which the MAP_SHARED in the vm_mmap call sets, is required for the host’s sake: inserting a raw frame number into a private, copy-on-write area is a BUG_ON in Linux, an assertion whose failure (an oops) kills the calling task with the address-space lock held, and halts the machine if the host is configured to panic on an oops, rather than returning an error. VM_DONTCOPY keeps a fork of a carrier while it is in a tenant’s space, which never happens but could, from copying entries that belong to the kernelet.

The area’s extent. The area covers exactly the range the kernel proper can map, so that a vm_map outside it can be refused, and zap_vma_ptes(), which silently does nothing for a range not wholly inside its area, is always inside.

The address-space switch

A carrier must run in the address space of the process whose thread it carries, and kernelet_switch_mm(), the first of the patch’s two helpers, is how it changes space. A carrier is born with an empty address space of its own; to run a tenant thread it must run in that process’s space. Two of the lines above call the helper, and both hooks call it, through klet_space_adopt below, before they apply the registers on a trip to user mode in which the virtual CPU has activated a different process than the carrier is in (chapter 9).

Linux: changing a task’s address space. Linux switches a task’s address space in two places, neither usable by a user task, and a module cannot write a third. Linux has the operation twice: for a kernel thread that borrows a user address space (kthread_use_mm()), and for execve (exec_mmap()), which replaces a process’s address space with a fresh one. Neither will do for a user task that wants to swap between address spaces it holds references to: the first warns if its caller is not a kernel thread and takes the references a kernel thread needs, which a user task must not, and the second is private to exec and drops the task’s reference to the old space. And a module cannot write its own, because everything the switch touches is private to the core kernel.

The helper does what the two have in common: under the task’s lock and with interrupts off, set the task’s mm and active_mm to the new space, load the new page table with the architecture’s switch_mm_irqs_off(), and keep Linux’s per-space bookkeeping in step. It consumes the caller’s reference on the new space and hands back the old one, for the caller to drop in a context that may sleep.

Simplified from prototype/linux/patches/0001-carrier-hooks.patch: kernelet_switch_mm, kernelet_mm_alloc.

struct mm_struct *kernelet_switch_mm(struct mm_struct *mm)
{
	struct task_struct *tsk = current;
	struct mm_struct *old_mm;

	if (tsk->mm == mm)
		return mm;
	sched_mm_cid_before_execve(tsk);      /* release the old space's concurrency id ... */
	task_lock(tsk);
	local_irq_disable();
	old_mm = tsk->active_mm;
	tsk->active_mm = mm;
	tsk->mm = mm;
	membarrier_update_current_mm(mm);
	switch_mm_irqs_off(old_mm, mm, tsk);  /* load the page table */
	local_irq_enable();
	task_unlock(tsk);
	lru_gen_use_mm(mm);
	sched_mm_cid_after_execve(tsk);       /* ... and take one in the new */
	return old_mm;
}

struct mm_struct *kernelet_mm_alloc(struct task_struct *owner)
{
	struct mm_struct *mm = mm_alloc();
	WRITE_ONCE(mm->owner, owner);
	lru_gen_add_mm(mm);                   /* once, here; never per switch */
	return mm;
}

The two lru_gen_* calls are for Linux’s multi-generational page reclaim, which keeps a list of the address spaces it may scan: a new space is put on it once, and a switch marks the space as in use.

The two sched_mm_cid_* brackets are not optional. Linux gives each address space a small pool of concurrency ids, one per processor currently running one of its tasks, which programs may use to index per-processor data; a task that changes address space must return its id to the old space and take one from the new. Without the brackets a carrier would leak one concurrency id per switch, invisibly, until the pool ran dry and the scheduler spun forever under a run-queue lock. That is the kind of bookkeeping that makes the helper belong in Linux rather than in a module.

Simplified from prototype/linux/endovisor/space.c: klet_space_adopt.

int klet_space_adopt(struct klet_carrier *c, u64 id)       /* called by both hooks before user mode */
{
	sp = klet_space_get(c->inst, id);                      /* the space must be this kernelet's */
	if (current->mm != sp->mm) {
		mmget(sp->mm);                                    /* a reference for the helper to consume */
		old = kernelet_switch_mm(sp->mm);
		mmput(old);                                       /* the one it handed back */
		if (c->blank_mm) { mmput(c->blank_mm); c->blank_mm = NULL; }   /* the empty one is never needed again */
	}
	klet_space_put(sp);
	return 0;
}

Every carrier holds one reference on the space it is in, which the endovisor drops when the carrier leaves it and Linux when the carrier exits; the endovisor holds one more on every live space, from vm_create to vm_destroy. That second reference is what pins the page tables for the next chapter’s lockless reads.

The four edits

Everything the kernel proper’s cursor does to a space is one of four services. Each of the first three takes the address space’s lock, finds the area afresh (the discipline Linux’s own code follows, rather than trusting a stored pointer), checks its arguments, and calls one Linux function.

vm_map(space, va, paddr, prot). The protection crosses as three bits, readable, writable, executable; the endovisor builds Linux’s page protection from its own constants and never from bits the kernelet supplies, because one such bit, global, would make a translation visible to every process on the machine.

Simplified from prototype/linux/endovisor/space.c: klet_prot_to_pgprot, klet_space_insert, klet_do_vm_map.

static int klet_prot_to_pgprot(u32 prot, pgprot_t *out)
{
	unsigned long vm_flags = VM_SHARED | VM_READ;
	if (!(prot & KLET_PROT_READ)) return -KLET_INVALID;     /* a page without read permission has no entry: next chapter */
	if (prot & KLET_PROT_WRITE) vm_flags |= VM_WRITE;
	if (prot & KLET_PROT_EXEC)  vm_flags |= VM_EXEC;
	*out = vm_get_page_prot(vm_flags);                         /* Linux's own idea of a user page with these rights */
	return 0;
}

static s64 klet_space_insert(struct klet_space *sp, struct vm_area_struct *vma, u64 va, u64 paddr, pgprot_t pgprot)
{
	if (!klet_in_grant(sp->inst, paddr, PAGE_SIZE))            /* THE check: the frame must be the kernelet's */
		return -KLET_NOT_OWNED;
	if (va < sp->start || va >= sp->end)
		return -KLET_INVALID;
	ret = vmf_insert_pfn_prot(vma, va, paddr >> PAGE_SHIFT, pgprot);
	if (ret & VM_FAULT_OOM) return -KLET_LIMIT;                /* Linux could not allocate a page-table page */
	/* insert_pfn() leaves an existing entry alone and still reports success, so look: */
	if (!slot_holds(sp->mm, va, paddr)) return -KLET_INVALID;  /* a vOSTD bug: two maps of one page */
	return 0;
}

s64 klet_do_vm_map(struct klet_carrier *c, u64 id, u64 va, u64 paddr, u32 prot)
{
	klet_prot_to_pgprot(prot, &pgprot);
	sp = klet_space_get(c->inst, id);
	vma = klet_space_lock_area(sp);                            /* mmap_read_lock, then vma_lookup */
	err = klet_space_insert(sp, vma, va, paddr, pgprot);
	mmap_read_unlock(sp->mm);
	klet_space_put(sp);
	return err;
}

vmf_insert_pfn_prot() may sleep, when a page-table page must be allocated; the next chapter says why that is allowed although the kernel proper calls map under a preemption guard.

vm_unmap(space, va, len) clips the range to the area and calls zap_vma_ptes(), which clears every present entry and flushes the TLB before it returns, through Linux’s own gather-and-finish. It reports no count; the number of pages that were mapped is vOSTD’s own, from a walk it makes before the call.

vm_protect(space, va, prot) rewrites one present entry in place. Linux’s helpers for taking a page-table lock are not exported to modules, so the endovisor uses apply_to_page_range(), which is exported and takes that lock itself, here over the one entry, and in its callback replaces the entry with one atomic compare-and-exchange:

Simplified from prototype/linux/endovisor/space.c: klet_pte_protect.

static int klet_pte_protect(pte_t *pte, unsigned long addr, void *data)
{
	pte_t old = ptep_get(pte), new;
	if (!pte_present(old))
		return -EINVAL;
	do {
		new = pte_modify(old, ctx->prot);      /* keeps the frame number, the special bit, and the accessed and dirty bits */
	} while (!try_cmpxchg64((u64 *)&pte->pte, (u64 *)&old.pte, pte_val(new)));
	return 0;
}

pte_modify() matters: an entry rebuilt from the frame number would lose the special bit that marks a raw-frame-number entry, and the next zap would then treat a grant frame as a Linux page and drop a reference it never took.

The rewrite is one store, so a lockless reader on another virtual CPU never sees the entry absent. It does not flush; the kernel proper issues its flushes separately, as on a machine.

vm_flush(space, va, len) is flush_tlb_mm_range() over the range, or over the whole space, on every processor where the address space is loaded, which switch_mm_irqs_off() keeps track of. It is not exported in a stock kernel, which is why the patch exports it. It never sleeps, and so may be called while the kernel proper still holds a cursor.

Two more services complete the set.

vm_activate(space) only records the space in the virtual CPU’s record, where the hooks of chapter 8 find it, and never sleeps, because a full kernel proper, such as Asterinas’s, calls activate from the handler it runs right after a task switch, with interrupts off, and vOSTD must allow for that.

vm_destroy(space) clears the whole area, waits for calls in flight, and drops the endovisor’s reference on the address space.

Faults

A tenant’s fault on the area reaches an endovisor handler whose whole job is to report it to the kernel proper. The tenant touches an address with no entry, or writes a page whose entry is read-only. Linux calls the area’s fault for the first and pfn_mkwrite for the second, on the carrier, in kernel mode, with the address-space lock held; a write to a present read-only entry reaches the handler only because the area supplies pfn_mkwrite, and without it Linux would make the entry writable on its own authority. The handler has nothing to look up: Linux’s table is the only table, and a fault on this area means the kernel proper has not mapped the page.

Simplified from prototype/linux/endovisor/space.c: klet_space_report.

static vm_fault_t klet_space_report(struct vm_fault *vmf, bool mkwrite)
{
	struct klet_carrier *c = klet_current_carrier();
	bool user = !!(vmf->flags & FAULT_FLAG_USER);

	if (!user)                                        /* Linux's own access to a tenant address (a get_user) */
		return VM_FAULT_SIGBUS;                       /*   fails cleanly, as an -EFAULT in that code */

	c->exc_trap = X86_TRAP_PF;                        /* for the kernel proper: a page fault ... */
	c->exc_addr = vmf->address;                       /*   at this address ... */
	c->exc_error = (mkwrite ? 1 : 0) | (write ? 2 : 0) | 4 | (exec ? 16 : 0);   /*   with the processor's error-code bits: 1 present, 2 write, 4 user, 16 fetch */
	c->exc_pending = true;
	set_thread_flag(TIF_NOTIFY_RESUME);               /* run the resume hook on the way back */
	return VM_FAULT_NOPAGE;                           /* "handled": Linux returns to user mode without installing anything */
}

The handler cannot run the kernel proper where it stands, inside Linux’s fault path with Linux’s lock held. So it records the fault, flags the carrier, and tells Linux the fault is handled. Linux heads back to user mode to retry the instruction, passes through the exit loop, and the resume hook of chapter 8 enters the kernelet with user_run returning an exception. The kernel proper’s own fault handler runs as a normal task, free to sleep, maps the page with its ordinary cursor, which is a vm_map, and calls execute again. The retried instruction finds the entry where the processor looks and does not fault a second time.

What vOSTD adds on top

This chapter is about what vOSTD must do for the kernel proper that Linux does not, now that the last chapter has put the tenant’s page table in Linux’s hands: read the table, copy to and from the tenant’s memory, keep track of which frame each entry holds, wait for copies in progress before a frame is freed, lock a range for the kernel proper’s cursor, hold the one kind of page Linux cannot represent, dispose of an address space at a moment when sleeping is not allowed, and say when a service may sleep under a guard. Each of these is a few dozen lines. The walk, the copy, the frame count, the grace period and the withheld set are what keep the design sound; the rest keep the kernel proper correct or the host responsive.

Reading the table

vOSTD answers a cursor’s questions by reading Linux’s page table itself, through the direct map, from the root whose physical address the space’s record holds. The kernel proper asks a cursor what is at an address (query), where the next mapped page is (find_next), and how many pages an unmap removed; on a machine OSTD reads its own page table for these. It is the walk a processor does, in software, four dependent loads:

Simplified from prototype/vostd/src/mm/page_table.rs: read_entry, child, leaf_of, walk.

fn read_entry(node: Paddr, idx: usize) -> u64 {
    unsafe { read_volatile((paddr_to_vaddr(node) as *const u64).add(idx)) }   // one 64-bit load
}

fn child(e: u64) -> Option<Paddr> {                       // the next table down, if the entry points at one
    if e & PRESENT == 0 || e & HUGE != 0 { None } else { Some((e & ADDR_MASK) as Paddr) }
}

fn leaf_of(e: u64) -> Option<Leaf> {                      // a present, user-accessible page
    if e & PRESENT == 0 || e & USER == 0 { return None; }
    let mut flags = PageFlags::R;
    if e & WRITE != 0      { flags |= PageFlags::W; }
    if e & NO_EXECUTE == 0 { flags |= PageFlags::X; }
    Some(Leaf { paddr: (e & ADDR_MASK) as Paddr, flags })
}

pub(crate) fn walk(root: Paddr, va: Vaddr) -> Option<Leaf> {
    let mut node = root;
    for level in (2..=4).rev() {                          // four levels; vOSTD refuses a five-level host at start
        node = child(read_entry(node, index(va, level)))?;
    }
    leaf_of(read_entry(node, index(va, 1)))
}

The walk takes no lock, and two facts about Linux make that safe. First, a page the walk reads is never freed under it. Second, Linux writes an entry with a single 64-bit store and clears it with an atomic exchange, so a load never sees half an entry.

Linux frees an area’s page-table pages in four cases, and none applies here. (1) When an area is unmapped or moved, which only a system call to Linux does; the tenant’s system calls go to the kernel proper, not to Linux. (2) At exec, which never runs in this address space. (3) When khugepaged, Linux’s background thread that replaces a last-level table of 4 KiB entries with one 2 MiB huge entry, collapses a range, which it refuses for raw-frame-number areas. (4) In exit_mmap(), which the endovisor’s reference on the address space (the last chapter’s second reference) holds off. zap_vma_ptes() clears entries but leaves the tables.

The walk need not handle huge entries. The area holds only 4 KiB entries, since vm_map inserts one page at a time, so child treats a huge entry as absent.

Linux: page-table isolation. To blunt Meltdown, Linux gives each address space a second top-level page for user mode. Whenever it writes a user entry into mm->pgd, it writes the same entry into the second page, so both point at the same lower-level tables; below the top level there is one table, the one the last chapter described. In the kernel-mode copy only, Linux sets no-execute on those top-level user entries, so that a return to user mode on the wrong table faults. mm->pgd is the kernel-mode copy, and it is the root the endovisor publishes for vOSTD.

Permissions are taken from the leaf only, never combined down the levels. Linux makes every upper-level user entry readable, writable and user-accessible, so only the leaf restricts anything, with one exception: the no-execute bit on the kernel-mode table’s top-level user entries, which vOSTD reads. Combined down the levels, that bit would make every tenant page non-executable. The prototype’s Linux is built without the mitigation, so this case is argued, not tested.

Copying to and from the tenant

Linux: copying from user memory. Linux’s copy_from_user rests on two mechanisms. The processor feature SMAP, supervisor-mode access prevention, faults any kernel-mode access to a user page unless the kernel has opened a window for it with stac, which it closes again with clac. And the copying instruction is listed in the exception table, the list of instructions allowed to fault and where to resume, so that a fault inside it resumes at a fixup that returns an error; Linux keeps a table for its own code and for each module’s.

Inside Linux, vOSTD may not dereference a tenant address as OSTD does on a machine. On a machine OSTD dereferences the address and lets the fault handler catch a bad one; for example, the hundred-line kernel’s write handler reads the program’s buffer through vm_space.reader(addr, len). vOSTD could open an SMAP window and could list an assembly copy in an exception table, but two deeper obstacles remain. First, the address space the processor is in is not necessarily the one being copied, because a carrier adopts its virtual CPU’s space only on the way to user mode. Second, a kernel-mode fault in the area never reaches the kernel proper: the endovisor’s fault handler fails it (the last chapter’s -EFAULT), and Linux then resumes at the instruction’s exception-table fixup or, for an instruction with none, oopses the host, so the copy would fail where on a machine the kernel proper’s handler would have mapped the page.

Instead, a copy walks the page table from the tenant address to the frame, and copies through the frame’s direct-map alias, an ordinary kernel address.

On a bad address, vOSTD returns the page-fault error at once, where OSTD would first call the kernel proper’s own page-fault handler and retry. An unmapped or read-only address is a result of the walk, not a fault.

Returning the error is enough for kernels that map eagerly, not for one that maps on demand. Asterinas’s full kernel proper maps on demand, so before it can run as a kernelet vOSTD must call its handler outside the read section described below and walk again. This prototype does not do that.

Simplified from prototype/vostd/src/mm/io.rs: Region, resolve, copy_regions, copy_opaque.

enum Region {
    Kernel { cursor: usize, end: usize },                  // a kernel buffer
    User { root: Paddr, cursor: Vaddr, end: Vaddr },       // tenant memory, to be walked through `root`
}

impl Region {
    fn resolve(&self, write: bool) -> Option<(*mut u8, usize)> {   // the head of the region, as a kernel pointer
        match *self {
            Region::Kernel { cursor, end } => Some((cursor as *mut u8, end - cursor)),
            Region::User { root, cursor, end } => {
                let leaf = page_table::walk(root, cursor & !(PAGE_SIZE - 1))?;    // None: a page fault
                if write && !leaf.flags.contains(PageFlags::W) { return None; }
                let offset = cursor % PAGE_SIZE;
                let len = (PAGE_SIZE - offset).min(end - cursor);               // up to the end of this page
                Some(((paddr_to_vaddr(leaf.paddr) + offset) as *mut u8, len))
            }
        }
    }
}

fn copy_regions(dst: &mut Region, src: &mut Region) -> (usize, bool) {
    while copied < total {
        let done = rcu::read(|| {                                      // run inside a read section (below)
            let (dptr, dlen) = dst.resolve(true)?;
            let (sptr, slen) = src.resolve(false)?;
            let n = dlen.min(slen).min(total - copied);
            unsafe { copy_opaque(dptr, sptr, n) };
            Some(n)
        });
        let Some(n) = done else { return (copied, false) };            // a fault: how far we got
        dst.advance(n); src.advance(n); copied += n;
    }
    (copied, true)
}

unsafe fn copy_opaque(dst: *mut u8, src: *const u8, n: usize) {
    asm!("rep movsb", inout("rcx") n => _, inout("rdi") dst => _, inout("rsi") src => _);
}

The copy is one rep movsb in assembly rather than a Rust copy, so that the compiler cannot assume tenant memory holds still. Tenant memory may change under the copy, since another virtual CPU’s thread may be writing it; a plain copy of memory that changes is a data race in Rust’s terms, and the optimizer is then free to assume the source did not change. It could, for instance, compile “copy a length out, check it, use it” into a check of the copy and a re-read of the source for the use, and a tenant that changed the length in between would have passed the check with a value it never had. An assembly copy is opaque to the compiler, so the code after the copy can read only the destination, never the source again.

Who holds the frame

Inside Linux, vOSTD counts each Linux entry as holding the reference that OSTD’s page table holds on a machine; Linux knows nothing of the count. A full kernel proper such as Asterinas’s relies on it: its copy-on-write path reuses a frame in place when the count is one.

The reference changes hands with the entry. map turns the handle into a raw address after the service succeeds, so the reference passes to the entry only once the entry exists. unmap reads the entries back before the service clears them. It turns each address into a handle again and drops it after the wait described below.

Simplified from prototype/vostd/src/mm/vm_space.rs and prototype/vostd/src/mm/frame.rs: CursorMut::map, CursorMut::unmap, Frame::into_raw, Frame::from_raw.

pub fn map(&mut self, frame: UFrame, prop: PageProperty) {
    let va = self.core.va;
    /* ... a page without read permission goes to the withheld set, below ... */
    space.backend().map(va, frame.paddr(), prot_bits(&prop));   // the vm_map service; panics the kernelet on failure
    let _ = frame.into_raw();                                    // the entry owns the reference now
    self.core.va += PAGE_SIZE;
}

pub fn unmap(&mut self, len: usize) -> usize {
    let mut frames: Vec<Paddr> = Vec::new();
    page_table::for_each_present(space.root(), start, end, &mut |_, leaf| frames.push(leaf.paddr));  // read first
    if !frames.is_empty() {
        space.backend().unmap(start, len);                       // the vm_unmap service: clears and flushes
    }
    /* ... plus the withheld set's pages in the range ... */
    rcu::synchronize();                                          // every copy in progress is done
    let n = frames.len();
    for p in frames { drop(UFrame::from_raw(p)); }               // now the frames may go back
    self.flusher.dispatch_tlb_flush();                           // issue flushes the kernel proper queued earlier on this cursor; this range was flushed by the zap
    n
}

pub(crate) fn into_raw(self) -> Paddr { let p = self.paddr; core::mem::forget(self); p }

pub(crate) fn from_raw(paddr: Paddr) -> Self {
    assert!(allocator::refcount(paddr).unwrap() > 0);          // the frame is the grant's and in use
    Self::from_raw_unchecked(paddr)
}

This is sound only if Linux never clears an entry of the area on its own initiative, and for this area it does not. The entries are marked special, so Linux finds no page of its own behind them. Every scanner that walks address spaces skips the area by its flags: the multi-generational LRU walk, khugepaged, same-page merging, NUMA balancing, the out-of-memory reaper. Reclaim finds pages to evict through its LRU lists and the entries that map a page through its reverse mapping; the grant’s frames are ordinary RAM on no LRU list, and no reverse mapping leads from a frame to this area, so swap-out never sees them. Compaction, which moves pages to make free memory contiguous, does pass over them and skips them as neither on an LRU list nor movable.

Memory pressure leaves the area’s entries alone: make mem-pressure tries to drive the Linux under test into swap with a host process while a tenant has 512 pages mapped, and afterwards every entry is present with the same frame and the same contents. The log reports how much was swapped; the check does not require it.

Freeing a frame a copy may be reading

unmap waits for every copy in progress before it frees a frame. A copy takes no cursor, since that would serialize every copy against every cursor, so it may still be reading the frame whose entry the unmap just cleared. The wait is a minimal RCU (read-copy-update: readers take no lock, and a writer waits until every reader in progress has finished before it frees anything): the rcu::read around each page of a copy, and the rcu::synchronize() in unmap before the frames are freed, which waits a grace period, until every reader in progress has finished.

synchronize waits for every virtual CPU that was inside a read section when it was called. Each virtual CPU has a sequence word, odd while it is inside one. synchronize skips its own virtual CPU: its caller is not in a read section, and since a read section holds a preemption guard, no other task on this virtual CPU can have been switched out partway through one.

The wait is short, one page’s walk and copy, unless Linux has descheduled the reader’s carrier; then the waiter spins, telling the host through vcpu_on_spin, until that carrier runs again.

The grace period holds in the test: make mem-conc runs copies without pause on one virtual CPU against map-and-unmap cycles on the other and finds no torn page, that is, no copy still reading a frame when the test rewrote it after its unmap returned (the rewrite stands in for reuse). A second phase frees the frames for real while copies write into the space, reallocates them, and finds none overwritten; in this run no grace period of that phase found a copy to wait for.

The range lock

vOSTD keeps a range lock of its own per space, because no Linux lock can stand in for a cursor’s locks. On a machine, a cursor holds the page table’s node locks for its whole life, and a full kernel proper such as Asterinas’s relies on that in two places: its page-fault handler queries, allocates and maps under one cursor, so two threads faulting on one page never both map it; and its page cache commits a page and maps it atomically under one cursor while its eviction and truncation unmap through another. A Linux lock cannot stay held while the carrier is back in kernelet code, where a tenant-controlled kernel could hold it forever against Linux’s own users of the address space.

The lock is sixteen 64-bit words in the space’s shared record. Each 2 MiB region, the span of one last-level table, is guarded by word (region number mod 16), so sixteen words stand for every region: a striped lock. Each word holds a count of readers in its low bits (READERS is their mask) and three flags: WRITER, set by an exclusive holder; WRITER_WAITING, which holds new readers off while a writer waits; and WAITERS, which says that someone is asleep in vm_wait on this word.

A cursor takes every word its range touches, exclusively for a cursor_mut and shared for a cursor. It takes them in ascending order, a total order, so two cursors cannot deadlock. It releases them when it is dropped. Uncontended, taking a word is one compare-and-swap on the shared record and no crossing.

Simplified from prototype/vostd/src/mm/vm_space.rs: lock_word, unlock_word.

fn lock_word(&self, idx: usize, exclusive: bool) {
    let w = &self.backend().words()[idx];
    loop {
        let cur = w.load(Ordering::Acquire);
        let free = if exclusive { cur & (WRITER | READERS) == 0 } else { cur & (WRITER | WRITER_WAITING) == 0 };
        if free {
            let new = if exclusive { (cur | WRITER) & !WRITER_WAITING } else { cur + 1 };
            if w.compare_exchange(cur, new, Ordering::Acquire, Ordering::Relaxed).is_ok() { return; }
            continue;
        }
        // Contended: say so in the word, then sleep in the host until it changes. Nothing spins.
        let want = cur | WAITERS | if exclusive { WRITER_WAITING } else { 0 };
        if want != cur && w.compare_exchange(cur, want, Ordering::Relaxed, Ordering::Relaxed).is_err() { continue; }
        self.backend().wait(idx, want);                       // the vm_wait service
    }
}

fn unlock_word(&self, idx: usize, exclusive: bool) {
    let (old, last) = if exclusive { (w.fetch_and(!(WRITER | WAITERS), Ordering::Release), true) }
                      else { /* decrement the readers, clearing WAITERS with the last; last: was this the last reader? */ };
    if old & WAITERS != 0 && last { self.backend().wake(idx); }   // the vm_wake service
}

A contended cursor sleeps rather than spins, because the lock’s holder may itself be asleep in Linux inside a vm_map. The waiter’s whole virtual CPU sleeps with it, which costs no more than spinning on a machine’s page-table lock would.

The slow path is a futex, Linux’s “sleep only if this word still holds this value” primitive. It is rebuilt for carriers because Linux’s futex keys on a user address in the caller’s address space and this word lives in kernel memory. A waiter sets the WAITERS bit and calls vm_wait(space, word, expected); the endovisor takes the space’s wait-queue lock, reads the word, returns at once if it no longer equals expected, and otherwise puts the carrier to sleep, killably. A releasing cursor clears the bit with one atomic read-modify-write and, if it was set and no reader remains, calls vm_wake, which wakes every waiter under the same lock.

No wake-up can be lost, by the argument chapter 9 made for vcpu_idle: one side marks, then checks; the other changes, then checks the mark; so one of the two always sees the other. Here the mark is the WAITERS bit, the check is the read under the lock, and the change is the single read-modify-write on release.

A cursor that waits behind a sleeping lock holder sleeps too, and takes the lock after the release without a single kernelet task switch: make mem-conc has one virtual CPU hold a cursor while its vm_map sleeps (a test hook makes it), and the other virtual CPU’s cursor on the same region sleeps in vm_wait and takes the lock after the release.

A page without read permission

A page without read permission has no Linux entry; vOSTD keeps it in a per-space withheld set instead. Such pages are of two kinds: PROT_NONE pages, with every permission cleared, and write-only pages, which x86 cannot express because a present entry is always readable. To the kernel proper both are mapped; on a machine OSTD encodes them as valid but not-present entries.

Linux has no usable encoding for them in this area. On a Linux built with NUMA balancing, Linux periodically makes entries no-access, so that the next touch faults and tells it which processor uses the page. Its fault handler therefore treats every no-access entry in an accessible area as such a marker, even in an area the balancer never scans, and rewrites it with the area’s page protection: read and execute here, because the area’s pfn_mkwrite makes Linux hold write back, plus write if the entry is dirty. A page encoded that way would become readable on its first touch. Without NUMA balancing, as in the prototype’s Linux, the entry is no better: Linux takes it for present and a read fault on it for spurious, so the access faults forever without reaching the area’s fault handler.

The set stands in for the table wherever a page has no entry. It is an ordered map from address to frame and property, in the kernelet’s heap (Linux’s kmalloc, charged to the sandbox). It holds the frame’s reference exactly as an entry would. It is under the range lock, which orders cursors on one region, and a spin lock of its own, because cursors on different regions share one map; the lock is taken per statement, never across a service. query, find_next, protect_next and unmap consult the set beside the table:

A space that is dropped at the wrong moment

The last reference to a VmSpace can be dropped with virtual interrupts off, where Drop may do nothing that may sleep, yet vm_destroy sleeps. The drop can come from activate, which keeps one reference per virtual CPU to the space active there and drops the previous one’s when a new space is activated. A full kernel proper, such as Asterinas’s, activates with virtual interrupts off, from the handler it runs right after a task switch, so that drop can be the last; the test kernels of this book activate from main, but vOSTD is not written for them alone.

A helper task to do the work later is not available. A task spawned before the kernel proper calls inject_scheduler would make OSTD install its default scheduler, and the injection would then fail. A task spawned afterwards is never run by a kernel proper like Asterinas’s, whose scheduler enqueues only its own threads; a kernel proper that did accept it would still schedule it by its own policy, at no moment vOSTD can choose, so a busy higher-priority task could hold the frames and the Linux address space indefinitely.

Drop pushes the space onto a per-kernelet retire list, lock-free and without allocating, since an allocation is mem_alloc, which may sleep (the list node was allocated at new).

The list is drained at the next point where sleeping is allowed: every sleeping memory service’s wrapper (vm_create, vm_map, vm_unmap, vm_protect, vm_wait, vm_destroy) and vcpu_idle, whenever the caller holds no guard and no spin lock, has virtual interrupts on and is not in an upcall. A guard is excluded although a memory service may sleep under one (rule 1, below), because the drain may take long and the caller did not ask for it.

The drain is not prompt, but it is bounded. A sandbox that never idles keeps its retired spaces, but vm_create is a drain point, so a new space never waits behind retired ones, and the backlog is at most the 64 spaces a kernelet may hold, all charged to the sandbox’s own grant and to page tables Linux already counts.

The drain unmaps the whole space, which flushes and releases every frame, the withheld set’s included, and then calls vm_destroy.

pub(crate) fn drain_if_safe() {                            // called from sleeping stubs and vcpu_idle
    if HEAD.load(Ordering::Relaxed).is_null() || !safe() { return; }   // safe: no guard, no spin lock, interrupts on, not in an upcall
    let mut p = HEAD.swap(core::ptr::null_mut(), Ordering::Acquire);
    while !p.is_null() { let node = unsafe { Box::from_raw(p) }; p = node.next; destroy(*node); }
}

fn destroy(mut node: Node) {
    let backend = node.backend.take().unwrap();
    page_table::for_each_present(backend.root(), 0, MAX_USERSPACE_VADDR, &mut |_, leaf| frames.push(leaf.paddr));
    backend.unmap(0, MAX_USERSPACE_VADDR);
    frames.extend(node.withheld.values().map(|&(p, _)| p));
    rcu::synchronize();
    for p in frames { drop(UFrame::from_raw(p)); }
    backend.destroy();                                     // vm_destroy
}

The rule about sleeping

Inside Linux, a memory service may sleep even when the kernel proper calls it under a preemption guard, which OSTD forbids on a machine. The kernel proper calls map holding a preemption guard, because every cursor takes one. Every memory service except vm_flush, vm_activate and vm_wake may sleep in Linux: vm_map, vm_unmap and vm_protect wait for the address-space lock; vm_map may wait for a page-table page; vm_unmap’s zap may be preempted between page-table pages; and vm_wait sleeps by design. The design states the rule in four parts:

  1. A service may sleep whenever its work needs it. Its prologue lifts the mirror of chapter 11, so Linux sees nothing wrong, and its epilogue restores it.
  2. A service that may sleep must not be called while the caller holds a kernelet spin lock or has virtual interrupts off; under a plain preemption guard it may. The reason for the spin lock is lock-holder preemption: a spin lock held across a Linux sleep makes every other virtual CPU that wants it spin for the sleep’s length. The reason for the interrupts is a promise: with interrupts off the kernel proper is promised that no handler runs before it unmasks, so a kick sent during the sleep would be delayed past the carrier’s return until the unmask, where rule 3’s delay ends with the return.
  3. A sleep delays this virtual CPU’s pending virtual interrupts until the carrier returns, exactly as a Linux preemption does; the design accepts that.
  4. The mirror remains a latency optimization and is load-bearing for correctness nowhere.

Rule 1 is sound because a kernelet’s critical section promises only that no kernelet task switch happens on this virtual CPU until the guard drops, as Problem 2 of chapter 11 argued. A sleep in Linux is the same event as a Linux preemption, which the kernelet already survives at any instruction. On a machine a guard has a second job: OSTD frees page-table pages only after every processor has switched tasks, so a guard keeps them alive. Here no table is freed, and vOSTD’s grace period watches each virtual CPU’s sequence word rather than task switches, so a guard held across a Linux sleep changes nothing.

Rule 2 is the one place where vOSTD asks more of the kernel proper than OSTD does: a kernel proper that maps under a spin lock or with virtual interrupts off runs on a machine and is stopped here.

vOSTD asserts the rule before every sleeping memory service, with a count of spin locks held that is separate from the guard count, and stops the kernelet rather than counting violations, so a kernel proper under the tenant’s control cannot break the rule through the memory services; only the sandbox’s own virtual CPUs would spin, within its own share. Whether Asterinas’s full kernel proper keeps the rule everywhere has not been checked.

The heap services break rule 2, a known gap that costs latency, not soundness. They may sleep inside kmalloc, carry no assertion, and are called under spin locks, the withheld set’s insert among them. By rule 4 that costs latency only: a virtual CPU that wants the lock spins, and hands its turn on through vcpu_on_spin, for as long as kmalloc sleeps.

Two tests exercise the rule. make mem-func runs on a Linux built with CONFIG_DEBUG_ATOMIC_SLEEP, which complains whenever Linux code might sleep with Linux’s preemption count raised. Inside a preemption guard it maps a page into a fresh 2 MiB region, which makes Linux allocate a page-table page, and Linux reports nothing. make mem-r2 does the same under a spin lock, and vOSTD stops the kernelet before the call crosses.

Recap. vOSTD reads Linux’s page table through the direct map with a four-level walk that needs no lock, because the endovisor’s reference keeps the table alive and Linux writes entries with single stores. Copies walk to the frame and go through its direct-map alias with an opaque rep movsb, inside an RCU read section, and unmap waits a grace period before it frees a frame. vOSTD counts the Linux entry as holding the frame’s reference. A cursor takes a striped range lock whose waiters sleep in Linux through vm_wait and vm_wake. Pages without read permission live in a withheld set, not in the table. A dropped space goes on a retire list and is destroyed at the next point where sleeping is allowed. A memory service may sleep under a preemption guard, never under a spin lock or with virtual interrupts off; the heap services break that rule, a known gap that costs latency.

What the rows say, one at a time.

A page the kernel mapped costs nothing at its first touch. The entry is in Linux’s page table from the moment vm_map returns, so the tenant’s first access is a TLB miss and a hardware walk, 82 cycles, with no fault. That is a container’s cost, and it is the design’s whole reason: any scheme that let Linux’s page table be filled lazily, on demand, would pay a fault, many times the cost of a walk, at the first touch of every page.

A map costs a crossing. 780 cycles is one service call: the stub, the address-space lock, the grant check, and Linux’s insert. A kernel that maps 512 pages under one cursor pays it 512 times. That is the price of letting trusted code check every frame, paid once per page, where the first-touch saving is collected once per page too.

A protect costs a crossing per page and saves a refault per page. 2 MiB read-only is 512 vm_protect calls and one flush, about 111 µs; the reads afterwards take 80 cycles and no fault, because the entries were rewritten in place and never removed.

Copies cost a walk. 184 cycles for 64 bytes is the software walk of chapter 14 plus the copy; a direct copy on a machine would be a fraction of that. For 4 KiB the walk disappears into the copy.

fork is the trade-off. The fork and unmap rows are the test kernel doing what Asterinas’s full kernel proper does for those system calls, not Linux’s. A fork of a process with 64 MiB mapped costs two crossings per page, a protect of the parent and a map into the child, and takes 10 ms. In exchange, neither the child’s first read pass over the memory nor the parent’s re-read takes a single fault: half a millisecond each, which is the cost of the TLB misses and walks alone, since the grant is small and the 64 MiB are 256 frames mapped over and over, so the data never leaves the cache. (A write to a shared page after the fork still faults, as copy-on-write requires.) A design that made the fork cheap by deferring the work to faults would pay it back, with interest, the first time either process touched its memory. A kernel that forks and never touches the memory, as a shell does before exec, loses by it; everything else gains.

Recap. The stack switches of a crossing cost a few nanoseconds; a memory service, with Linux’s lock and its work, costs several hundred cycles. A kernelet task switch costs under two thousand cycles and never involves Linux. A sandbox’s share of the processors does not depend on what its kernel does, in all but one unexplained run of this build and two of earlier ones. A page costs a crossing to map and nothing to touch; a copy costs a walk; a fork costs two crossings per page and makes every later read free.

The target is approximate, because native getpid takes Linux’s faster entry and exit path and a carrier does not.

The handoff’s 78.5 ns has three causes.

Two kernels’ models meet at the handoff

Linux assumes that each task has its own kernel stack, and that this stack is empty whenever the task is in user mode. The prototype breaks both assumptions. A carrier runs many kernelet tasks on one Linux stack. The kernel proper’s call to execute returns only at the program’s next system call, so the frames of this call stay on a stack while the program runs. The prototype translates between the two models on each system call, in the five ways listed below the figure; the figure shows the first two.

A Linux thread (a) and the prototype’s carrier (b), both while the program runs in user mode. The red numbers mark the first two items of the list below.

  1. Resuming the suspended call: steps 5 and 6a, 9.7 ns. Each system call returns into the user_run and execute that wait on the kernelet stack (Appendix, execute and Two stacks). These 13 instructions take 9.7 ns. The stack switch itself costs little.

  2. Copying the registers: steps 3 and 11, about 9 ns. The hook copies 18 registers from pt_regs to UserContext on entry, and back on exit. The cost is plain work: 95 instructions in about 30 cycles.

  3. Checking the address space: step 10, 22.9 ns. The kernel proper may call vm_activate with the vCPU’s interrupts off; Asterinas calls it right after a task switch (Tenant memory on Linux’s page tables). Switching the carrier to another address space can sleep in Linux: if the carrier drops the last reference to the old space, mmput() frees it, and mmput() may sleep (Linux v6.12 kernel/fork.c). A sleeping carrier stops its whole vCPU, so no kernelet task runs there until Linux wakes it. With interrupts off, vOSTD forbids that sleep, so that other tasks do not wait on it: a request from another vCPU, such as the wake-up of a task that runs here, would wait until the carrier wakes and the kernel proper unmasks its interrupts (What vOSTD adds on top, rule 2). The prototype’s vm_activate therefore only writes the space’s ID into the vCPU record, and the hook switches before each return to user mode, where the carrier may sleep.

    The hook cannot tell whether vm_activate has run since the carrier last returned to user mode, because vm_activate only writes an ID. Before each return to user mode, the hook therefore checks the address space in the five steps of the figure. Steps 2, 3 and 5 protect the hook from the kernelet: the kernelet can write any ID into the record, and another vCPU of the same kernelet can destroy the address space with vm_destroy during the check. The two updates of the reference count are atomic instructions on memory that the vCPUs share, and take 16.7 ns of the 22.9 ns (steps 10b and 10d).

    The prototype’s address-space check before each return to user mode. The red steps are the two atomic instructions.

    The address space changes only when the kernelet switches to a task of another process, so almost every check finds the carrier already in the right address space. The hook pays the 22.9 ns on each system call all the same.

  4. Ordering the event check: part of step 8. Before the carrier leaves for user mode, user_run executes a full memory barrier, lock addl, on each system call. The barrier keeps a virtual interrupt raised at that moment from going unnoticed by both the carrier and the raiser (Appendix, Virtual interrupts). Without the barrier, such an interrupt would still be handled at the watch timer’s next tick, within 1 ms: the tick raises an interrupt of its own, and its raiser then asks Linux to hand the carrier to the kernelet. The barrier is paid on every system call to shorten a rare delay.

  5. Calling through the service table: step 7b, 7.3 ns. The endovisor accepts only self-contained images: their relocations are relative and they import no symbol. It can then check an image when the image is registered, and share the image’s code pages between sandboxes (The endovisor UAPI). The kernelet therefore cannot call user_run by name, and calls it through the service table that it receives when it starts. The call loads the table’s address, then the address of user_run, and jumps there: two dependent loads before the jump.

Two schedulers share the processor

Linux schedules the carriers, and the kernelet schedules its own tasks on them. Linux cannot see inside kernelet code, so two mechanisms tell it what it needs (Appendix): the mirror tells Linux when kernelet code holds a lock, and the watch timer gives the processor back to Linux when Linux wants it. The prototype maintains both on each crossing between user mode and the kernelet.

  • The mirror. On each entry into kernelet code, klet_enter reads Linux’s preemption count and adds back the kernelet’s share. On each exit, user_run removes the share. This work is part of steps 4 and 8.
  • The watch timer. On each entry, klet_enter calls hrtimer_active to check that the timer runs. This takes about 2 ns of step 4.

The build

Two costs come from how the image was built, not from the design. In step 6b, execute calls RawUserContext::run, which is in another crate. The image was compiled as shared-library code (relocation-model = pic), so this call goes through the global offset table (The endovisor UAPI), although the image is one executable that could call it directly. In step 7a, the build’s integer-overflow checks add a test to each arithmetic operation.

The rest

The remaining steps cost about 6.5 ns in all: the call of the hook in step 2, the checks in step 7a, and the switch back to the Linux stack in step 9. They are small and hard to remove.

Proposed change

Design overview

One system call through the prototype (a) and through this design (b). Steps on the same row do the same job. Red steps are gone from the path; the blue box lists work that now happens only when its cause does.

The kernelet user task

What a task holds in the prototype (a) and in this design (b).

To remove the copy of item 2, each kernelet user task gets a Linux stack of its own, 16 KiB in Linux’s format. Its pt_regs is the task’s UserContext. The task needs a whole stack, not only a register area, because Linux runs its entry and exit code on the stack where it saves the registers. Below pt_regs, the stack holds only the hook, the services the task calls and Linux’s exit work.

Linux saves the registers into the stack that it takes to be the carrier’s own. When the kernelet makes a user task current on a carrier, it registers the task’s Linux stack as the carrier’s (Task switch); a kernel task runs with the carrier’s own Linux stack. Both stacks of a user task come from the sandbox’s stack pool, within its limit on tasks, and are charged to the sandbox’s memory cgroup.

Linux returns to user mode from these registers, so they must always hold safe values. The kernel proper writes them only through UserContext, and only during the task’s own handler call; UserContext keeps the segment fields and the privileged flag bits fixed, so no write can make them unsafe.

The vOSTD interface

In the prototype, the kernel proper enters user mode itself, through execute. Its call stays on the kernelet stack while the program runs, and each system call must resume it. This design separates the two jobs. The kernel proper only handles events: it implements one handler, which handles one system call, exception or event and returns. vOSTD runs user mode: it calls the handler for each event of a kernelet user task, and enters user mode after the handler returns. No kernel context then waits on a stack while the program runs, so nothing is saved or resumed across user mode. vOSTD also owns the whole path between user mode and the handler, so it can optimize that path without changes to the kernel proper:

Proposed: vOSTD’s interface for user events.

pub trait UserEventHandler: Sync {
    /// Handles one event of the current task; returns when done.
    fn handle(&self, event: UserEvent, user: &mut UserMode);
    /// Asked before every return to user mode: whether the task ends.
    fn should_exit(&self, user: &UserMode) -> bool;
    /// Asked after a virtual interrupt: whether the handler has work.
    fn has_kernel_event(&self, user: &UserMode) -> bool { false }
    /// Called with interrupts masked just before user mode, to load
    /// the task's floating-point and segment state.
    fn pre_user_run(&self, user: &UserMode, guard: &DisabledLocalIrqGuard) {}
}

pub enum UserEvent { Syscall, Exception, KernelEvent }

A kernel proper declares its handler once, as it declares its main, and vOSTD calls it directly:

UserMode gives access to the current task, its user registers and the exception that ended a run. Only vOSTD can create a UserMode, and it passes the handler a reference that lasts one call. UserMode is neither Send nor Sync, so no other task can reach a task’s registers.

The handoff protocol

The handler leaves nothing waiting on the kernelet stack, but the prototype also leaves a call waiting on the Linux stack: the hook’s call, which Linux returns through to run its exit work. Linux does not need that call. To finish a system call, it needs only the task’s pt_regs and its exit work, and the exit work can run on a fresh frame just below pt_regs. So the hook abandons its call when it hands the event to the kernelet, and the kernelet later starts Linux’s exit work from just below pt_regs. While kernelet code runs, the Linux stack holds nothing below pt_regs.

In: from the hook to the handler

The syscall hook enters the kernelet by a jump, not a call. It masks the vCPU’s virtual interrupts, moves to the top of the current task’s kernelet stack, and starts vOSTD’s entry there with the kind of event. The hook’s own frames stay on the Linux stack and are never resumed. The resume hook enters the same way for exceptions and virtual interrupts. vOSTD’s entry finds the current task, unmasks the interrupts, and calls the kernel proper’s handler. The interrupts stay masked until then, so that no virtual interrupt switches tasks before vOSTD has found the current one.

Out: from the handler to user mode

Proposed, simplified: vOSTD’s entry for a user event.

extern "C" fn user_event_entry(event: UserEvent) -> ! {
    let mut user = UserMode::for_current_task();
    HANDLER.handle(event, &mut user);          // the kernel proper's handler returns
    if HANDLER.should_exit(&user) {
        exit_current_task();
    }
    assert_no_guard_held();                    // a guard kept alive with mem::forget
    preempt_if_wanted();                       // the scheduler's chance before user mode
    let guard = mask_virtual_interrupts();
    HANDLER.pre_user_run(&user, &guard);
    user_run()                                 // never returns
}

After the handler returns, vOSTD leaves for user mode through a new Linux entry. The entry runs Linux’s exit work on a fresh frame just below the task’s pt_regs, and returns to user mode as Linux returns from any system call or interrupt. No frame of the event remains on either stack.

Task switch

Linux saves a carrier’s user registers on the stack that it takes for the carrier’s own. For example, the kernelet switches the carrier from task A to task B. Linux does not see the switch and still takes A’s Linux stack for the carrier’s. B’s next system call then saves B’s registers in A’s pt_regs.

At each task switch, the kernelet therefore registers the next task’s Linux stack with Linux as the carrier’s stack. Linux does the same at each switch of its own threads. A switch to a kernel task registers the carrier’s own Linux stack. The endovisor accepts only a stack that belongs to the instance and that no other carrier uses. The old stack holds nothing below pt_regs while kernelet code runs, so the switch leaves no Linux call behind.

Switching the address space

The kernel proper calls vm_activate to name the address space of the next task. A full kernel proper calls it during a task switch, with interrupts off, so vm_activate must not sleep. A switch can sleep in one case: the carrier drops the last reference to the old space, and Linux frees the space. The prototype’s vm_activate therefore only records the space. The hook then finds the space and compares it before each return to user mode (step 10). Processes switch rarely, but this check runs on each system call.

Only that last drop can sleep, and Linux can give it to a background worker with mmput_async. vm_activate therefore switches the address space at once and gives the old space to the worker. The return to user mode checks nothing.

Interrupts raised while leaving

In the prototype, the raiser of a virtual interrupt sets the flag only if the carrier is in user mode. The raiser must therefore read the carrier’s state, and the carrier must publish its state before it checks the pending bits. This exchange needs the barrier on each return to user mode. In this design, the raiser always sets the flag, whatever the carrier is doing. The carrier then publishes no state, checks no pending bits, and executes no barrier on its way out.

Linux checks the flag before each return to user mode. If the raiser set the flag before that check, Linux hands the carrier to the kernelet at once. If it set the flag after the check, the interrupt waits for the carrier’s next entry into the kernel, at the latest the watch timer’s next tick; an interrupt raised in user mode waits in the same way in the prototype. The cost is small: an interrupt that the kernelet has already handled can leave its flag set, and the next return to user mode then passes once through the resume hook for nothing.

Bookkeeping at each crossing

The mirror adds one to Linux’s preemption count while kernelet code holds a lock (Appendix). The prototype adjusts the count on each entry into kernelet code and on each exit. A task holds no lock at the two user-mode crossings: it enters from user mode with none, and its handler releases its locks before it returns. The kernelet’s share of the count is therefore zero at these crossings, and they skip the adjustment. The return to user mode keeps one check that Linux’s count is zero. Critical sections, services and yields inside the kernelet keep the mirror.

The prototype also checks on each entry that the watch timer runs. Linux’s notification of a carrier’s scheduling already re-arms the timer each time the carrier gets a processor. The timer is therefore armed once, when the vCPU starts. Neither change alters what the mirror and the watch timer protect against.

Building the image

The image is compiled as a position-independent executable, the form in which it is linked, so its calls between crates are direct and no longer go through the global offset table (step 6b). It uses Asterinas’s benchmark profile, release-lto: link-time optimization, one code-generation unit, and no overflow checks (step 7a). The kernelet’s memory safety does not depend on overflow checks, because vOSTD bounds user ranges with checked_add and saturating_add.

What stays

  • The hook’s place. Linux still calls the hook after seccomp, so the sandbox’s filter still bounds what a carrier can ask of Linux.
  • The service table. The kernelet still calls user_run through it.

Alternatives and tradeoffs

  • One Linux task per kernelet task. Each task would have its own Linux stack, with no registration. Each task switch of the kernelet’s own scheduler would then become a Linux sleep, a wake-up and a Linux context switch, against fewer than 2,000 cycles for that switch today (What it costs), and a sandbox would put one Linux task on the host for each tenant thread.
  • Shorten Linux’s own part. Linux’s entry and exit take about 38 ns of a system call. Two designs could shorten them. The kernelet could point IA32_LSTAR at its own entry while a carrier runs; seccomp would then no longer bound the carrier. Or a small switcher in the host, as in PVM (Huang et al., SOSP 2023), could take a carrier’s system call, save the user registers in the task’s pt_regs, and enter the kernelet directly. The switcher would return to user mode the same way, and fall back to Linux’s full entry and exit only when Linux has work for the carrier, such as a signal or a reschedule. Both designs change Linux’s entry code.

Implementation and integration

Linux gets two more patches. The first adds the exit entry, and moves the SYSRET conditions of do_syscall_64 into a function that both share. The second adds the stack registration; Linux puts a carrier’s own stack back before it frees it, however the carrier ends, and keeps accounting the carrier’s own stack.

In the endovisor, two stack primitives replace klet_switch: one jumps to a stack without returning, and the other calls a function on another stack and returns. The carrier’s state flags become one state. The sandbox frees its tasks’ Linux stacks only after no carrier refers to them.

In vOSTD, UserContext takes the layout of pt_regs, with private fields.

Each kernel proper that runs user code is ported to the handler. kernels/mem, which tests tenant memory, ran user code as a function call, and now waits for the program’s report through a mailbox. kernels/sched, which has its own scheduler, saves floating-point state when it switches tasks, and loads it in pre_user_run.

Open questions

  • Shortening Linux’s entry and exit. Which of the two designs in Alternatives and tradeoffs, an own IA32_LSTAR entry or a PVM-style switcher, saves more, and at what cost to Linux’s entry code, to seccomp and to the host’s safety argument.

Appendix: the prototype’s mechanisms

A system call of a tenant program passes through these mechanisms of the prototype.

  • Kernelet. The tenant’s kernel, linked into one image: the kernel proper, written in safe Rust, and vOSTD, the framework under it that provides OSTD’s interface on Linux.

  • Carrier. A Linux task that runs one virtual CPU of the kernelet. The tenant program runs on it in user mode (Carriers).

  • Endovisor. The Linux module that serves kernelets. The syscall hook and every klet_* function in the figure belong to it.

  • Syscall hook. Our Linux patch adds this hook to the system-call entry. Linux calls it for each system call of a carrier, after seccomp. The hook gives the call to the kernelet, and Linux skips its own system-call table (Carrier hooks and patch overview).

  • execute. OSTD’s interface for running user code. The kernel proper calls it in a loop. execute enters user mode and returns when the program makes a system call or raises an exception, or when an event for the kernel proper arrives. The kernel proper handles the event and calls execute again (Into user mode and back). The loop of the hundred-line kernel:

    Simplified from prototype/kernels/hello/src/lib.rs: create_user_task.

    let mut user_mode = UserMode::new(create_user_context());
loop {
    let return_reason = user_mode.execute(&DummyUserHooks);
    let user_context = user_mode.context_mut();
    if ReturnReason::UserSyscall == return_reason {
        handle_syscall(user_context, &vm_space);
    }
}

  • Two stacks. A task’s Linux kernel stack is empty each time the task returns to user mode. execute returns only at the program’s next system call, so its frames must stay on a stack while the program runs. Each kernelet task therefore runs on a kernelet stack of its own. klet_switch switches between two kernel-mode contexts: the hook’s, on the carrier’s Linux stack, and the current kernelet task’s, on that task’s kernelet stack. While the kernelet runs, the hook’s context waits. While the program runs, the task’s context waits inside execute (Two stacks).

  • UserContext. The kernelet’s copy of a task’s user registers. On each entry into the kernel, Linux saves the user registers in pt_regs, at the top of the carrier’s Linux stack. The hook copies them from pt_regs into the task’s UserContext, and copies them back before the carrier returns to user mode (Into user mode and back).

  • Service table. The kernelet image imports no host symbols. It calls the endovisor only through a table of function pointers that it receives when it starts. One entry is user_run, the service that enters user mode (The kernelet ABI).

  • Virtual CPU record. Memory that the carrier and the kernelet share, one for each virtual CPU. It holds the pending virtual interrupts and the address space that the kernelet last activated with vm_activate. Each tenant process has its own address space, a Linux mm. The carrier switches to the activated address space on its way to user mode (Tasks and virtual CPUs, Tenant memory on Linux’s page tables).

  • Virtual interrupts. The kernelet’s own interrupts: a timer tick, or a request from another virtual CPU. To raise one, the endovisor sets a pending bit in the virtual CPU record. Kernelet code checks this bit before the carrier returns to user mode. If the carrier is already in user mode, the endovisor also tells Linux to give the carrier to the kernelet at its next entry into the kernel. Linux does this through the endovisor’s resume hook. These two paths leave a gap. Kernelet code has already checked the bit, but the carrier is not yet in user mode, so the endovisor does not tell Linux. An interrupt raised in this gap would wait until the watch timer’s next tick, up to 1 ms. The prototype closes the gap with a memory barrier (step 8) (Virtual interrupts).

  • The mirror. Linux does not preempt a task whose preemption count is above zero. While kernelet code is in a critical section, for example holding a spin lock, vOSTD adds one to the carrier’s count. Linux then does not preempt the carrier, and other virtual CPUs do not spin on a lock whose holder is off its processor. Linux code that runs for the carrier must see only Linux’s own count. The endovisor therefore removes the kernelet’s share each time the carrier leaves kernelet code, and adds it back each time the carrier returns (Sharing a processor politely).

  • Watch timer. A per-processor timer of the endovisor that takes the processor back from kernelet code when Linux wants it. Under Linux’s none and voluntary preemption models, Linux does not preempt a task in kernel code. Linux’s own code gives up the processor where it calls cond_resched(). Kernelet code cannot call that function, so without the timer a carrier in kernelet code would keep its processor. The timer also delivers the kernelet’s timer tick. On each entry into kernelet code, the carrier checks that the timer runs (Sharing a processor politely, which also explains the preemption models).
