Building Kernelets on Linux

2026-11-16 Principles of API virtualization

  • Status: Draft
  • Author(s): Plucky923
  • Discussion: No public review opened yet.
  • Affected chapters: Why a kernel of your own, The kernelet ABI, Stopping a kernelet, Tenant memory on Linux’s page tables, What vOSTD adds on top, and What it costs.

This document synthesizes the accepted design, audits all 24 service-table entries, and generalizes six companion proposals (Reduce syscall overhead, Coordinate the two schedulers, TypedIO, FPU state management, Direct page-table updates in vOSTD, and Allocate the kernelet heap from the grant). The LMbench measurements cover the integrated prototype.

Summary

API virtualization turns OSTD into vOSTD for multi-tenant sandboxes on a shared host kernel. Unlike a machine hypervisor that combines protection and multiplexing at one trap boundary, a kernelet splits them by resource ownership. vOSTD confines kernel proper at the upper API boundary without crossing, and the endovisor checks only the host-owned objects it multiplexes. Two principles define these boundaries:

  1. Principle 1 (kernel proper → vOSTD): virtualize tenant OS semantics. Strip machine-global authority, keep tenant-scoped OS contracts, and replace hardware-coupled or unchecked signatures with safe OS abstractions.
  2. Principle 2 (vOSTD ↔ host): delegate coarse containers to the host; keep tenant confinement and fine-grained state local. Cross the host boundary only for whole-reclaimable containers, host-owned CPU/MMU/privilege control, or peer fault domains.

Applied to OSTD and the 24-entry service table, these principles derive the six companion proposals and leave 13 multiplexing and cross-domain services.

Problem and motivation

Virtualization: protection vs. multiplexing. A multi-tenant system performs two distinct jobs. Protection confines each tenant to its own resources so it cannot read, corrupt, or crash the host or sibling tenants. Multiplexing shares scarce physical hardware and global kernel state across tenants, including CPU time, physical memory quotas, MMU/TLB contexts, interrupt gates, and shared devices. In classical machine virtualization (Popek and Goldberg, 1974), the guest kernel is an untrusted binary, so the hypervisor enforces both protection and multiplexing at one expensive hardware trap boundary.

Why a cheap boundary still fails when protection and multiplexing stay coupled

In a classical VM, trapping across the hypervisor boundary is expensive, so it is natural to assume that replacing that trap with a cheap call would remove the overhead. In a kernelet, a null service call switches stacks in only 36 cycles (What it costs). Following that intuition, a design can keep single-machine OSTD unchanged above and forward every privileged or hardware-facing operation across the service table to the endovisor, which validates each request and executes it inside Linux’s shared kernel subsystems.

Making the jump cheap removes only the 36-cycle call cost. Pushing OSTD semantics across the host multiplexing boundary still fails in two ways:

  1. Duplicate structures and host paths inflate latency. Because vOSTD cannot touch host internals yet must preserve OSTD semantics, while the host loses Rust type and ownership guarantees across C calls, both sides duplicate locks, tracking tables, and side structures. Every forwarded call also runs boundary checks, staging copies, and Linux subsystem paths instead of updating memory directly. Thus a 64 MiB fork slows to 7.85 ms vs. 0.34 ms natively (Direct page-table updates in vOSTD), 64-byte mem_alloc/mem_free pairs take 449 cycles (Allocate the kernelet heap from the grant), and FPU staging adds ~330–340 ns per syscall (FPU state management).
  2. Conflicting OS and host semantics force extra bridging mechanisms. Host subsystems enforce their own rules for concurrency, object lifetimes, and state representation, which often conflict with OSTD’s single-OS contracts. Reconciling those mismatches requires extra cross-boundary shims and restrictions, such as host waiting helpers (vm_wait) and lock aborts when sleepable host paths meet kernelet spin locks, deferred queues and per-object scans where abrupt kill demands whole-container teardown (What vOSTD adds on top), or software side-maps where host formats cannot encode an OSTD permission state.

How API virtualization decouples them

Unlike a binary VM, a kernelet moves the virtualization boundary up to OSTD’s safe-Rust API on Linux. Three structural conditions let it separate protection from multiplexing:

  1. Safe Rust splits the VM’s single boundary into two. Safe Rust forces untrusted kernel proper through vOSTD, which sits inside the TCB (Why a kernel of your own). vOSTD can therefore enforce tenant protection locally at kernel proper → vOSTD with zero crossings, leaving vOSTD ↔ host for host multiplexing.
  2. The upper boundary is a source-level Rust API. Because kernelets compile both layers from source, vOSTD can reshape bare-metal assumptions (such as UserMode::execute, unchecked FpuContext, and IoMem) into host-friendly Rust abstractions.
  3. vOSTD stays decoupled from Linux internals below. Unlike a Linux kernel module, vOSTD compiles as a PIE image with zero host symbol imports and cannot touch Linux runqueues, mm_struct lists, or IDT gates (The kernelet ABI). Because the host can also kill a sandbox immediately without running Drop destructors (Stopping a kernelet), Linux hands out coarse containers that the host multiplexer schedules and reclaims whole.

Earlier kernelet-book blueprints observe that 22 of 38 virtualized OSTD items do not call the host, without stating the underlying rule. Separating protection from multiplexing supplies that rule.

Proposed change

Core thesis: decouple protection from multiplexing

API virtualization places tenant protection at kernel proper → vOSTD and host multiplexing at vOSTD ↔ host, splitting them by resource ownership:

Two principles define these boundaries:

Principle 1: Virtualize tenant OS semantics

At the kernel proper → vOSTD boundary, vOSTD enforces tenant confinement while keeping kernel proper portable:

  1. Strip machine-global authority. vOSTD omits APIs over physical hardware topology or host-global kernel state (Absent) so unauthorized calls fail at compile time.
  2. Keep tenant-scoped OS contracts. vOSTD keeps safe-Rust contracts for single-OS abstractions, reshaping a signature only when a single-machine assumption conflicts with running on a host.

As a result, pure-software abstractions built over lower vOSTD primitives compile unchanged (Identical), while vOSTD reimplements the underlying primitives (Virtualized) under Principle 2.

Principle 2: Delegate coarse containers to the host; keep tenant confinement and fine-grained state local

At the vOSTD ↔ host boundary, resource ownership sets placement, crossings, and checks:

  1. Delegate coarse containers; keep fine-grained state local. Because Linux must reclaim sandbox resources whole on abrupt kill without running Drop destructors, the host provides only coarse containers, while vOSTD handles all fine-grained updates locally inside them to avoid Linux paths and locks.
  2. Cross only for external ownership. vOSTD and the host cross the runtime boundary if and only if an operation touches a host container, host-controlled CPU/MMU/privilege multiplexing, or another fault domain.

Each side checks only what it owns: vOSTD confines the tenant over sandbox state locally, and the endovisor checks host-owned objects during required crossings.

Changes relative to the Accepted Design

This taxonomy retires 11 entries from the 24-entry Services table in The kernelet ABI. Heap blocks (mem_alloc, mem_free), single-page PTE updates (vm_map, vm_unmap, vm_protect, vm_wait, vm_wake), FPU switches (fpu_save, fpu_load), and task stacks (kstack_alloc, kstack_free) do not manage host multiplexer units, so they move into local grant memory and intra-carrier XSAVE/XRSTOR, leaving 13 host-multiplexing and cross-domain calls (vcpu_*, vm_create/destroy/activate/flush, user_run, console_write, log_write, stop).

Implementation and integration

This proposal introduces no standalone code. The six companion proposals implement all runtime, ABI, and subsystem changes:

  • Upper-boundary changes (Principle 1): Reduce syscall overhead, TypedIO, and FPU state management.
  • Lower-boundary changes (Principle 2): Coordinate the two schedulers, FPU state management, Direct page-table updates in vOSTD, and Allocate the kernelet heap from the grant.

Once those companion proposals are accepted, this framework updates Why a kernel of your own (protection vs. multiplexing, Principle 1, and the vOSTD taxonomy) and The kernelet ABI (Principle 2, the 13-entry service table, and ownership-based endovisor checks).

Validation and evidence

LMbench measurements

On 2026-11-18, Linux, native Asterinas, and Kernelet ran the same 19 LMbench workloads, with five accepted measurements per workload and system. All three used the same payload from the Asterinas LMbench fork at afb47eddaf10 with the timing and resource-use patch.

Each VM used QEMU 10.2.1 with KVM, two pinned vCPUs, and 2 GiB of preallocated memory on one Intel Xeon Platinum 8259CL host. We set both frequency limits to 3.2 GHz on the assigned host CPUs and accepted per-boot effective VM execution frequencies of 3.168–3.232 GHz.

Linux and Kernelet shared the Linux 6.12 kernel binary. Kernelet ran in a separate campaign with Direct page tables and a fresh sandbox with a 512 MiB memory grant for each workload. Native Asterinas used an earlier source snapshot.
